## 检索用的向量模型

RAG 检索**需要**向量模型，只是不用你再配一个 Embedding API。

```
文档 / 用户问题
  → Chroma 默认本地向量模型（Sentence Transformers，all-MiniLM-L6-v2）
  → 写入 / 检索 ChromaDB
  → 取出相近文档
  → Agnes 根据资料生成回答
```

|步骤|用什么|
|---|---|
|把文字变成向量、做相似度检索|Chroma 自带的本地小模型|
|根据检索到的资料写回答|Agnes（`LLM_MODEL`）|

所以 `col.add` / `col.query` 时 Chroma 会在本地自动做 embedding，第一次可能下载模型文件。Agnes 只负责对话生成，`.env` 里不用再加 Embedding 相关配置。后面若要换成更适合中文的向量模型，再给 collection 显式指定 Embedding Function 即可。

新建 `services/kb_service.py`。集合是空的就自动导入 `data/kb` 下的 md。资料只有 4 篇，检索时全部取出，避免漏掉开放时间。

```python
from pydoc import doc
from typing import final
from chromadb.api.models.Collection import Collection
from chromadb.utils import embedding_functions
import chromadb
from app.config import BASE_DIR

KB_DIR = BASE_DIR / "data" / "kb"
CHROMA_DIR = BASE_DIR / "data" / "chroma"

_collection = None

_embedding_fn = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="BAAI/bge-small-zh-v1.5"
)

def get_collcetion() -> Collection:
    """向量库的初始化"""

    global _collection
    if _collection is not None:
        return _collection
    KB_DIR.mkdir(parents=True, exist_ok=True)
    CHROMA_DIR.mkdir(parents=True, exist_ok=True)
    client = chromadb.PersistentClient(path=str(CHROMA_DIR))
    col = client.get_or_create_collection(
        name="lab_kb", embedding_function=_embedding_fn
    )
    if col.count() == 0:
        ids = []
        docs = []
        metas = []
        for path in sorted(KB_DIR.glob("*.md")):
            text = path.read_text(encoding="UTF-8").strip()
            if not text:
                continue
            docs.append(text)
            ids.append(path.stem)
            metas.append({"source": path.name})
        if docs:
            col.add(ids=ids, documents=docs, metadatas=metas)
    _collection = col
    return col

def search(query: str):
    """根据关键字去检索向量库"""
    col = get_collcetion()
    if col.count() == 0:
        return ""
    limit = min(5, col.count())
    res = col.query(query_texts=[query], n_results=limit)
    docs = (res.get("documents") or [[]])[0]
    metas = (res.get("metadatas") or [[]])[0]
    distances = (res.get("distances") or [[]])[0]

    """
    以下是检索出来的资料：
    [预约规则.md]

    # 实验室预约规则...

    
    [安全规范.md]

    安全规范....
    """
    score_parts = []
    for doc, metas, dist in zip(docs, metas, distances):
        # 0-1 越接近1表示越相关
        score = 1 / (1 + dist)
        if score < 0.5:
            continue
        name = metas.get("source") or ""
        score_parts.append({"score": score, "content": f"[{name}]\n{doc}"})
    print(f"检索出来的 score_parts：{score_parts}")
    score_parts.sort(key=lambda x: x["score"], reverse=True)
    final_parts = [item["content"] for item in score_parts[:2]]
    return "\n\n".join(final_parts)
```

```python
from openai import OpenAI
from app.common.exceptions import BusinessException
from app.config import settings
from app.schemas.ai import ChatMessage, ChatRequest
from app.services import kb_service

SYSTEM_PROMPT = """你是智能实验室预约系统的助手，回答要简洁。
如果下面提供了实验室资料，请依据资料回答，不要编造资料里没有的时间、规则、设备。
你目前查不到真实的实验室空闲、设备库存、预约记录。
如果用户问现在哪些实验室能约、某台设备此刻有没有空，请说明去「实验室列表」查看。
除了实验室相关的问题之外，不要回复无关的问题。
"""

def get_client() -> OpenAI:
    """创建OPENAI的客户端"""
    if not settings.LLM_API_KEY:
        raise BusinessException(message="未获取到大模型的API Key")
    return OpenAI(api_key=settings.LLM_API_KEY, base_url=settings.LLM_BASE_URL)

def chat(data: ChatRequest):
    """大模型对话"""
    if not data.messages:
        raise BusinessException(message="对话内容为空")
    history = []
    for message in data.messages:
        if message.role in ("user", "assistant") and message.content.strip():
            history.append(message.model_dump())
    if not history:
        raise BusinessException(message="请输入您要对话的内容")

    # 取出用户最新的一条提问内容
    question = next(
        (item["content"] for item in reversed(history) if item["role"] == "user"), ""
    )

    knowledge = kb_service.search(query=question)

    print(f"检索到的向量库的内容：{knowledge}")

    system_prompt = SYSTEM_PROMPT
    if knowledge:
        system_prompt += "\n\n以下是检索到的实验室的资料：\n" + knowledge

    client = get_client()

    try:
        res = client.chat.completions.create(
            model=settings.LLM_MODEL,
            messages=[
                {"role": "system", "content": system_prompt},
                *history,
            ],
        )
        content = res.choices[0].message.content
        if not content.strip():
            raise BusinessException(message="大模型没有返回内容")
        return content
    except Exception:
        raise BusinessException(message="大模型调用失败，请稍后重试")
```

# 解析
## kb_service

**需求情景**

✅ 原来 AI 助手的问题：问到【计算机实验室几点开门、预约取消规则】这类知识库内容，大模型没有资料，只会让你去网页对应部分查看。
✅ 本节目标：给 AI 接入简易 RAG，不改动原有前端、不新增接口，继续复用 POST /api/ai/chat
✅ 流程： 用户提问 → `kb_service.search()` 去本地 Chroma 向量库检索相关文档 → 把检索到的资料拼进 System Prompt → 丢给大模型，让**模型只基于给到的资料回答**
<br>
### 1、pathlib路径拼接
```python
KB_DIR = BASE_DIR / "data" / "kb"
CHROMA_DIR = BASE_DIR / "data" / "chroma"
```
- `KB_DIR`：源文件目录（人写的 markdown 原文）
- `CHROMA_DIR`：向量库存储目录（Chroma 自动生成的向量数据）
这里是**路径定义**，用的是 Python `pathlib` 的写法（`/` 是路径拼接运算符）

老式字符串写法（容易出跨平台问题，Windows 和 Linux 斜杠不一样）

```python
# 老式
kb_dir = os.path.join(BASE_DIR, "data", "kb")
```

`pathlib` 用 `/` 拼接，自动适配 Windows / Linux，更干净

---

### 2、全局变量+单例实现缓存（懒加载）
**需求分析**
Chroma 集合对象、中文 BGE 向量模型加载开销很大，不能每次用户提问都新建一遍
所以，我们需要：
- 1、提供一个获取 Chroma 集合的函数，**整个服务运行期间，只创建一次集合对象**；
- 2、后续所有检索请求，都复用这同一个对象。
- 3、外部代码不能直接随便操作这个集合，统一通过 `get_collection()` 获取
- 4、【新增懒加载需求】推迟初始化时机：**后端启动时不加载模型、不初始化向量库，第一次调用检索时才初始化**，避免启动阶段阻塞、HuggingFace网络超时卡死

```python
_collection = None

def get_collcetion() -> Collection:
    """向量库的初始化"""
    global _collection
    if _collection is not None:
        return _collection
        
# 懒加载版本只是在if return之间添加了代码，不满足if则直接最后return，满足if则进行中间的初始化代码
```

#### 私有变量再理解
`_collection`
Python 私有约定（不是强制语法，是代码规范）：
- 变量 / 函数名**单下划线开头 `_xxx`**：代表**内部私有变量** 
- 👉 含义：**这个变量只是给本文件（kb_service.py）自己内部用的，不要在别的文件 import 之后直接去读写它** 
- 别人看到下划线，就知道：不要直接碰 `_collection`，想要集合，老老实实调用 `get_collcetion()` 获取

> 对比： 
> `collection`：普通名字，暗示外部也可以直接使用 
> `_collection`：内部私有，对外隐藏，只供内部使用

**再理解**
看上面需求分析第3点，那么为什么要让外部代码不能直接随便操作这个集合，统一通过 get_collection() 获取？为什么要这样设计呢？

**1. 保护单例逻辑**（最贴合你这段 RAG 代码的理由）

我们整套代码的目标：`_collection` 有且只能有一个，全程复用。 如果外部可以直接操作 `_collection`：

- 别的地方写一句 `kb_service._collection = None`
- 或者外部重新新建一个 collection 赋值给它 👉 缓存直接被破坏，单例失效，后续又会重复初始化、重复导入文档、向量模型重复加载，甚至 Chroma 文件锁报错。

把获取入口收窄成唯一函数 `get_collection()`： **所有地方拿集合，只能走这个函数，单例判断逻辑被封装在函数里面，外部没法绕过。**
<br>

**2. 统一收口，封装**

假设以后你要加功能：
- 拿到集合之前打印日志
- 加异常捕获、自动重连
- 切换不同的向量库实例 

如果外部到处都是直接访问 `_collection` 的代码，你要改所有地方，工作量巨大
统一入口之后：**改逻辑只改一处，比如这里只修改 `get_collection()` 内部，所有调用方自动生效**

内部细节藏起来，对外只暴露简单接口，符合**封装思想（面向对象基础思想）**
使用者只需要 `col = get_collection()`，不用关心底层怎么实现缓存

#### 全局变量再理解
`global _collection`

✅ **需求情景**
我们需要一个**在函数多次调用之间，能保留状态的地方——就是缓存**
- 如果是在函数内部创建的局部变量，函数跑完就销毁了，存不住 “已经创建好的集合”
- 把它放到函数外面，成为模块级全局变量，进程活着，这个变量就一直存在
>`global` 作用：允许函数内部修改这个顶层全局变量的值

#### 单例模式再理解
（整套结构：全局变量 + if 判断 + return）
✅**先说，单例模式是什么？**
- 单例**是一种设计模式（固定的代码思路、结构范式）**；
- 控制目标：**整个程序生命周期内，实例最多只有一个**
- 不是只能给初始化函数用，只是非常适合「**只需要一份的、初始化开销大**」的东西

#### 懒加载
✅ 懒加载是什么？ 
懒加载是**初始化时机策略**：不是程序启动/模块导入时立刻创建实例，而是等到第一次真正需要使用资源的时候，才去初始化。 它解决【什么时候创建实例】的问题。 
对比两种单例写法： 
 - 预加载单例：模块顶层直接实例化（上面原版kb_service），导入就加载模型，启动容易卡死 
 - 懒加载单例：初始值None，第一次调用函数才初始化（我们最终版本），启动不阻塞

**总结**
现在这个写法
- 全局变量 + if 判断 + return，就是说，**如果有，则直接return，如果没有，再往下走初始化代码**，这个就属于**单例的简易实现版本**（适合小项目）
	- 正规写法还有类里面重写 `__new__`、用装饰器等，本质目标不变
- 全局变量 + if判断 + 延迟初始化，就是**懒加载版本的简易单例**
<br>

再看看这里我们需要做什么？
✅**需求情景**：上面需求分析的1、2点

资源（Chroma 集合、向量 Embedding 模型）初始化成本高：
- 重复加载 BGE 向量模型很慢
- 反复新建 Chroma 客户端容易出现文件锁冲突
- 重复读取 md、导入向量会产生大量重复数据 
	- 单例目标：**全局保证只有这一个集合实例**，所有请求共享它 
	- 懒加载目标：推迟加载，不让模型加载阻塞后端启动
	- 第一次调用：`_collection` 是 None → 往下走创建集合； 
	- 之后任意次调用：直接返回已经存在的对象，不再重复初始化

<br>

**总结单例模式**
1. 它是一套**约定好的代码结构**，目标只有一条：

> 保证整个程序运行期间，这个类 / 对象**最多只有一个实例**，所有人拿到的都是同一个

2. 它**很适合初始化开销大的资源**（你现在的场景）： 向量模型、数据库连接、Chroma 集合、redis 连接池、日志实例。 这些东西加载慢、占资源、开多份还容易冲突（文件锁、连接爆满），所以优先上单例。
3. 但！**不是专门只给初始化函数用**，它是通用模式： 只要业务要求「全局唯一一份」，就可以用单例。 举别的例子：
	- 全局配置管理器，整个项目就一份配置
	- 全局消息通知器


#### 对比pickle 序列化缓存
- **pickle 序列化缓存**
	- 把【计算出来的结果 / 对象】存到**磁盘文件**
	- 程序重启之后，读文件把对象恢复出来；解决「重启之后数据丢了」
	- 属于**持久化缓存**
- **`_collection` 全局变量缓存**
	- 只存在**内存里**。服务一旦重启，`_collection` 变回 `None`，缓存直接消失
	- 它只解决**同一次服务运行内，多次请求重复初始化**的问题
	- 是**内存缓存**

#### embedding和TF-IDF
**需求情景**
联想之前的红楼梦图书检索那个项目，**RAG的底层**就是
**文本 →  通过模型 → 向量，再做相似度计算**

而这里的代码，就在做**将集合和模型（embedding）绑定**，还没有输出向量，后续会传入md文件，再调用这里即可进行**文本向量化**
- 图书检索那里，用的是**TF-IDF**完成文本向量化
- 而这里用的是**embedding模型**

TF-IDF
- 本质：**基于词频的统计方法**，不是 AI 模型
- 逻辑：统计每个词在当前文档出现频率、以及在全部文档里的稀有程度
- 特点：只认字面单词，**不懂语义**
- 优点：轻量、快、不需要训练模型、不需要 GPU
- 缺点：同义词、近义词、转述，匹配不到；长文本效果差
>举例子
>`计算机实验室几点开门` 和 `机房开放时间` TF-IDF 看到单词不一样，会判定完全不相似；哪怕意思相同

Embedding
- 本质：**预训练语言模型（神经网络）输出的语义向量**
- 逻辑：模型在海量文本上学过语言，把**语义含义**编码进向量
- 优点：理解语义，同义改写、换说法也能检索出来，RAG 首选
- 缺点：需要加载模型，开销比 TF-IDF 大
>同样上面例子：`计算机实验室几点开门` 和 `机房开放时间` 语义相近，算出来的向量距离很近，可以匹配上。

1. `PersistentClient(...)`：只是打开 / 连接本地的向量库文件夹
2. `get_or_create_collection(..., embedding_function=xxx)`：

3. 真正产生向量，发生在下面两个地方：
	- `col.add(documents=[...])`：把 md 文档文本喂进去 → 自动调用 BGE → 生成文档向量，存入 Chroma
	- `col.query(query_texts=[...])`：把用户提问文本喂进去 → 自动调用 BGE → 生成 query 向量，再去比对相似度

### 6、search 检索函数

**需求情景**

前面 `get_collection + col.add` 是**入库、建向量索引（一次性）**；
`search` 是**用户提问阶段，检索阶段**： 
- 接收用户的问题文本，交给 Chroma，自动把问题转成 query 向量
- 和库里已经存好的文档向量做相似度比对
- 筛选出相关知识库文本，格式化之后返回给上层 AI 接口
- 用来拼进 prompt 给大模型

> 一句话分工：add 是存资料；search 是拿问题找资料


```python
def search(query: str):
    """根据关键字去检索向量库"""
    col = get_collcetion()
    if col.count() == 0:
        return ""
    limit = min(5, col.count())
    res = col.query(query_texts=[query], n_results=limit)
    docs = (res.get("documents") or [[]])[0]
    metas = (res.get("metadatas") or [[]])[0]
    distances = (res.get("distances") or [[]])[0]

    score_parts = []
    for doc, meta, dist in zip(docs, metas, distances):
        # 0-1 越接近1表示越相关
        score = 1 / (1 + dist)
        if score < 0.5:
            continue
        name = meta.get("source") or ""
        score_parts.append({"score": score, "content": f"[{name}]\n{doc}"})
    print(f"检索出来的 score_parts：{score_parts}")
    score_parts.sort(key=lambda x: x["score"], reverse=True)
    final_parts = [item["content"] for item in score_parts[:2]]
    return "\n\n".join(final_parts)
```

```python
def search(query: str):
    """根据关键字去检索向量库"""
```

函数入参 `query`：用户原始提问字符串，例如 `"实验室怎么预约？"`

```python

```

<br>

`col.query()`：检索核心方法
- `query_texts=[query]`：传入用户问题文本（放到列表里是Chroma接口规范，支持批量查询）

>重点区分： 
>`col.add()`：文档向量化，入库（启动阶段） 
>`col.query()`：问题向量化，相似度检索（用户提问时）

#### 处理二维嵌套列表
```python
docs = (res.get("documents") or [[]])[0]
metas = (res.get("metadatas") or [[]])[0]
distances = (res.get("distances") or [[]])[0]
```

`col.query` 返回的res是字典，里面的 documents / metadatas / distances 都是**二维嵌套列表** 
格式示例：

```python
{
  "documents": [["文档1文本","文档2文本"]],
  "metadatas": [[{"source":"预约规则.md"},{"source":"安全规范.md"}]],
  "distances": [[0.2, 0.7]]
}
```

- `[0]`：取第一条查询对应的结果（我们只传了1个query）
- `or [[]]`：防御写法，如果key不存在，给一个空列表兜底，防止索引报错
- 三个列表一一对应：同下标，是同一条文档的【文本、元数据、距离】
<br>
#### zip并行遍历
```python
for doc, meta, dist in zip(docs, metas, distances):
```
`zip()`：并行遍历三个等长列表，把同一条文档的文本、元数据、距离打包拿到一起。
<br>

#### 距离→相似度/ 阈值过滤
欧氏距离dist → 相似度score转换公式 `1/(1+dist)`
```python
score = 1 / (1 + dist)
if score < 0.5:
    continue
```

距离转相似度分数： Chroma返回的是L2欧氏距离 
`dist`：**dist越小，向量越相似**，距离不能直接当相似度给人看
公式 `score = 1/(1+dist)`：映射到0~1区间

- score越接近1：越相关
- score < 0.5：相关性太低，直接丢弃这条文档（过滤低相关噪声）
<br>

```python
name = meta.get("source") or ""
score_parts.append({"score": score, "content": f"[{name}]\n{doc}"})
```

从元数据取出 `source`（就是md文件名），拼接内容：`[预约规则.md]\n文本内容`，存入列表，带上分数，方便后续排序。

<br>

```python
score_parts.sort(key=lambda x: x["score"], reverse=True)
```

按相似度分数从高到低排序（reverse=True 降序），最相关的排在最前面。

<br>
#### 切片
```python
final_parts = [item["content"] for item in score_parts[:2]]
```

切片，只取**相关性最高前2条**，**控制传给大模型的上下文长度**，防止prompt太长
>这里可以联想`图书检索`那个项目，也是取的`top_k`

<br>

```python
return "\n\n".join(final_parts)
```

把两条结果用换行隔开，拼成一个字符串返回，给`ai_service`拼进`System Prompt`，交给大模型

---

**知识点总结**

1. col.query()：检索核心，自动对用户query做Embedding向量化、相似度计算
2. query返回结果结构：二维嵌套列表，为什么取 `[0]`
3. 欧氏距离dist → 相似度score转换公式 `1/(1+dist)`
4. 阈值过滤：丢弃低相关文档，减少噪声
5. **zip并行遍历**：一一匹配文档、元数据、距离
6. sort + lambda：按相似度分数降序排序
7. 切片取TopN：控制检索上下文长度
8. **防御性写法**：col.count判空、min限制条数、or [[]]兜底

**误区提醒**

❌ 误区：dist就是相似度 
✅ 纠正：Chroma默认返回L2距离，距离越小越相似，需要手动换算成0~1的分数 

❌ 误区：检索出来多少条全部丢给大模型 
✅ 纠正：做过滤+取TopN，是RAG常规优化，控制上下文、降低幻觉、节省token
>这里可以联想`图书检索`那个项目，也是取的`top_k`

```python
    (item["content"] for item in reversed(history) if item["role"] == "user"), ""
```


✅ 作用：拿到**最新一条用户消息**

- `reversed(history)`：把对话历史倒序遍历（从最后一条往前找）
- 生成器表达式：找第一个 role=user 的内容
- `next(..., "")`：找到就返回文本；如果找不到用户消息，默认返回空字符串，防止报错

> 为什么只取最新一条？
> RAG 检索只拿用户当前这一轮的问题去搜知识库，不需要拿全部历史去检索。


#### 生成器再理解2
- `yield` 写的函数，是**生成器函数**； 
- 而 `(xxx for x in ... if ...)` 这种括号写法，叫 **生成器表达式**
>二者本质都是生成器：**惰性求值、按需产出，不会一次性把所有结果全部放到内存**

#### 生成器表达式
先看这一段代码里的生成器表达式
```python
(item["content"] for item in reversed(history) if item["role"] == "user")
```

这就是生成器表达式。 
- 它**不会立刻循环、不会把所有符合条件的结果全部算出来存成列表**。
- 它只是一个 “待执行的迭代流水线”： 只有外面要它拿一个值的时候，它才往前走一步，判断条件，产出一个结果

对比：

```python
# 列表推导式：一次性全部算完，全部放进内存，用的中括号[]
[item["content"] for item in reversed(history) if item["role"] == "user"]

# 生成器表达式：惰性，要一个，算一个,用的小括号()
(item["content"] for item in reversed(history) if item["role"] == "user")
```


**为什么这里不用列表推导式？**

- 列表推导式会**遍历全部历史，把所有 user 消息全部收集出来**，我们其实只需要第一个。 history 消息很多的时候，那就是做了多余的循环。
- 生成器 + next 找到第一个就直接停，效率更高，也更节省内存

#### next再理解
`next(生成器, 默认值)` 
作用：**向生成器索要下一个值**。

执行流程套进这行代码：
```python
question = next(
    (item["content"] for item in reversed(history) if item["role"] == "user"), 
    ""
)
```

1. `reversed(history)`：从最后一条消息（最新消息）开始往前遍历
2. 生成器开始逐个取 item，判断 `item["role"] == "user"`
3. **找到第一个满足条件的，立刻把这个 content 返回，生成器直接停下，不再继续循环！** 
	1. 👉 重点：找到就停，不会把剩下所有 user 消息全部遍历一遍！
	2. 这是这个写法的优势：我们只想要**最新一条用户消息**，找到就结束，不用遍历全部历史。
4. 如果从头到尾遍历完，一条 user 消息都没有，生成器耗尽了。 这时 next 会返回第二个参数 `""`（空字符串），而不是抛出 `StopIteration` 报错

```python
system_prompt = SYSTEM_PROMPT
```
