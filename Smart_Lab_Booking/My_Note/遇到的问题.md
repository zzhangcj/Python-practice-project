# 4、更新邮箱后，仍然带有旧的数据
## 问题现象

使用 PUT 接口实现用户局部信息更新，在 ApiPost 的请求 Body 里修改 JSON 中 `email` 的值并发送请求：

- ApiPost 编辑页面明明填写了新邮箱，但是接口返回、数据库最终保存的邮箱，始终是一串带有问题的数据（新邮箱+旧邮箱数字组合）
- 重启 uvicorn 后端服务后，异常现象依旧存在。

## 排查过程

1. 在 service 更新函数添加日志，打印后端真实接收的更新字典、更新前后数据库对象的值；
2. 发现关键线索：后端日志打印拿到的 `email`，并不是 ApiPost 编辑框输入的新值，而是上一次请求的旧邮箱；
3. 新建一条全新请求，重新配置地址、请求体，后端正常接收新邮箱，更新结果符合预期

## 根本原因

ApiPost 的请求缓存 / 历史请求体残留问题：**编辑面板上展示的 JSON 内容 ≠ 它实际发给后端的请求内容**。 界面上你修改好了新参数，但 ApiPost 底层发送的仍然是上一次的旧请求数据，后端拿到旧值，就把数据库更新成旧邮箱。

## 解决方法

1. 调试铁则：**以后端控制台打印的入参日志，作为真实收到请求的判断标准，不要只相信 ApiPost 界面**；
2. 直接新建一条全新请求，重新配置地址、请求体，避免旧缓存干扰；


## 补充
**为什么是邮箱这一行有问题，而 name 这里没问题呢**

✅ 一句话： 不是 ApiPost 只缓存 email、不缓存 name。**name 新旧内容相同，掩盖了缓存 bug；email 前后值不一样，所以缓存问题一眼就暴露出来了。**


举个例子：

- 旧报文：`{"name":"李四","email":"123456@xx.com"}`
- 你界面改成：`{"name":"李四","email":"new@qq.com"}`
- 但实际发出还是旧报文
    - name：都是李四 → 返回看着没问题，你察觉不到
    - email：旧值和你界面写的新值不一样 → 明显看出不对劲

# 6、RuntimeError

## 报错结论

`RuntimeError: 'cryptography' package is required for sha256_password or caching_sha2_password auth methods` 

👉 **你的 MySQL 用户用的是 `caching_sha2_password` 加密方式，pymysql 连接这种认证方式，必须额外装 cryptography 包**

## 原因拆解

MySQL8.0 默认账号密码插件是 `caching_sha2_password`，不是老的 `mysql_native_password`。 pymysql 原生不支持这个加密的密码握手，需要 `cryptography` 库做 RSA 加密，缺少它就启动直接报错。 报错触发点：

```
Base.metadata.create_all(bind=engine)
```

启动 main.py 的时候，一尝试连接数据库、建表，立刻连库失败。

## 解决方案

虚拟环境里面直接安装：

```bash
pip install cryptography
```

装完，重新执行

```bash
uvicorn app.main:app --reload
```

大概率直接解决。

**问题现象**
提交预约接口返回 500，前端只看到状态码 500，看不到详细报错文本；
后端日志打印 `sqlalchemy.exc.IntegrityError: (1048, "Column 'equipment_id' cannot be null")`；

**排查过程** 
- 先查看后端控制台日志，拿到完整异常信息，确认 MySQL 原生错误码 1048； 
- 查看日志里 parameters，确认后端传给数据库的 equipment_id 确实是 None； 
- 打开 Navicat 核对 reservations 表，检查 equipment_id 字段【不是 null】勾选状态； 
- 核对 SQLAlchemy ORM 模型，查看 equipment_id 的 nullable 配置； 
- 排查隐性干扰项：uvicorn 代码缓存、后端连接库和 Navicat 操作库是否为同一个。

**根本原因**
**数据库表约束、ORM模型约束需要同步放开**，只要任意一处设置了非空，就无法插入NULL。

1. 数据库：取消 `equipment_id` 的NOT NULL勾选，允许为空；
2. ORM模型：修改 `equipment_id` 为 `nullable=True`，类型标注 `int | None`，关联relationship同步改为 `Equipment | None`；
3. 彻底停止uvicorn再重启，消除代码缓存；
4. 确认后端数据库连接配置，和Navicat操作的是同一个库；
5. 重新提交预约，验证功能。

# 9、LLM消息角色错误
（来自` 第21、20章`）
LLM对话system提示词role写成assistant，导致指令约束力不稳定

## 问题现象

实验室AI助手对话接口，系统提示词使用`role="assistant"`传入；
表现为：AI经常忽略业务规则、回答简短随意，多轮对话后更容易不遵守预设要求，改成`role="system"`后，AI能够稳定按照预设规则回答、回复内容符合预期。对话记忆功能本身正常。

## 排查过程

1. 前端调试：对话上下文history正常传递，记忆可以承接上一轮提问；并排查AIChat.vue
2. 定位后端ai_service.py：发现业务规则提示词被封装为`role="assistant"`塞进消息列表；
3. 查阅LLM消息角色规范：`assistant`代表AI历史回复，属于对话记忆，权重低；`system`才是顶层全局指令，不受对话轮次影响；
4. 修改role为`system`，重启后端测试，指令约束生效。

## 解决方案

将系统规则提示词的`role="assistant"`修改为`role="system"`，放在messages数组最前面，history数组继续存放user/assistant对话记录，保证规则和对话记忆分开。

```python
messages=[
    ChatMessage(role="system", content=SYSTEM_PROMPT),
    *history,
]
```


**知识点补充**
### 区分 OpenAI messages 三个角色的定位

1. `role="system"`：**全局固定指令、人设、格式规则** 不属于对话历史，**不会被当成用户 / 助手的聊天记录**，模型会把它当成底层规则，全程生效，**不属于对话记忆**。 👉 适合放：你是谁、回答格式要求、业务规则（就是你这段 SYSTEM_PROMPT）
2. `role="user"`：用户发的消息（你的提问）
3. `role="assistant"`：AI 上一轮回复（AI 的回答） ✅ **真正的记忆，靠的是后面 `*history` 这一段**，history 里面存的就是一轮一轮 `user/assistant`，这才是对话记忆！


# 10、HuggingFace网络超时卡死
来自 22. 用RAG给实验室助手接入知识库

**完整问题：RAG向量库初始化写在模块顶层，导致后端启动时HuggingFace网络超时卡死、服务无法正常拉起**

## 问题现象 
原始代码将BGE嵌入模型实例直接写在py文件顶层；执行`uvicorn`启动后端时，程序一加载这个kb_service模块就立刻去HuggingFace拉取模型

1. 网络不通/国内访问huggingface超时，持续重试，后端日志报 `WinError 10060` 连接失败；
2. 虽然控制台打印了 `uvicorn running on 8000`，但是服务实际没有完全就绪，访问`/docs`转圈打不开；
3. 登录、预约等其他接口全部无法使用；
4. 临时注释掉向量库相关代码，后端才能正常启动、docs页面正常打开。 后续改成懒加载版本后，又出现新报错：`UnboundLocalError: cannot access local variable '_embedding_fn' where it is not associated with a value`，AI聊天接口500。

## 排查过程

1. 启动卡住的时候，观察日志，发现阻塞点是请求huggingface下载`BAAI/bge-small-zh-v1.5`模型；
2. 定位代码：`_embedding_fn = embedding_functions.SentenceTransformerEmbeddingFunction(...)` 写在模块顶层，**导入这个文件的时候就执行加载**，不是调用函数时才加载；
3. 在`ai_service`临时注释向量库相关的代码(`kb_service`相关的)，后端可以正常启动，确认问题根源就是顶层加载模型；
4. 改造为懒加载：把模型加载逻辑移到函数内部，只有调用AI检索的时候才加载；
5. 改造懒加载时踩坑：函数内修改全局变量但是忘记写`global`声明，同时函数名`get_collcetion`拼写错误，触发UnboundLocalError变量异常；
6. 配置HF镜像地址`hf-mirror.com`，解决HuggingFace国内网络访问问题。

## 根本原因

1. 模型初始化代码写在**模块顶层**：Python import这个文件的时候，代码立刻执行，uvicorn启动阶段就触发模型下载，网络差就阻塞整个服务启动流程，导致服务假活、docs打不开；
2. 懒加载改造初期语法错误：函数内部使用全局变量`_embedding_fn`但缺少`global`声明，Python把它识别为局部变量，赋值前读取直接报错；
3. 额外笔误：函数名`get_collcetion`拼写错误，存在调用风险；
4. 国内网络直接访问HuggingFace官方地址不稳定，容易超时
## 解决方案

## 两种解决方案对比


**前提**
问题根源一致：模型写在模块顶层，import时直接加载，阻塞uvicorn启动
方案A：纯懒加载（无预热，我修改的） 
方案B：懒加载 + lifespan预热（博主推荐版本，现在在用的）

### 方案A：纯懒加载（不执行warmup）

核心逻辑： 模型、向量集合**第一次用户提问时才加载**，后端启动完全不碰向量库。

- 启动流程：uvicorn启动 → 直接完成 startup，`Application startup complete` 秒出，登录、实验室列表等接口立刻可用
- 用户侧体验：重启后端之后，**第一条AI消息会卡住很久**（加载模型+建库+读md），容易前端超时；后面对话速度正常
- 优点：
    1. 后端启动极快，网络差、模型拉取失败也**不会阻塞整个服务**，其他业务功能不受影响
    2. 稳定性最高，适合校园网、家用不稳定网络；预热失败也不影响系统基础功能
    3. 不需要处理lifespan、异步线程，逻辑简单
- 缺点：
    1. 用户第一次发AI消息等待时间长，容易504前端超时
    2. 答辩演示时，如果刚重启后端，第一句对话容易卡顿
- 适用场景：本地开发、网络不稳定、优先保证【预约/实验室管理】基础功能可用

### 方案B：懒加载 + lifespan预热

核心逻辑： 代码本身依旧是懒加载（模型不在顶层），但是在`lifespan`启动生命周期里，用`asyncio.to_thread`调用`warmup()`，**服务启动阶段主动提前加载模型**

- 启动流程：uvicorn启动 → 启动协程去预热向量库（单独线程，不卡死async事件循环）→ 预热完成后，服务就绪
- 用户侧体验：后端启动的时候慢慢加载模型；预热成功后，用户发任何AI消息都秒响应
- 优点：
    1. 用户使用AI对话时没有等待，体验更好，答辩演示很顺滑
    2. 底层依旧是懒加载结构，不是顶层硬加载，比原版顶层加载更安全
    3. 预热加try-except捕获：就算HF网络超时、模型加载失败，**服务依然可以正常启动**，只是RAG知识库失效，AI还能正常回答基础问题
- 缺点：
    1. 后端启动时间变长，要等模型加载；如果网络极差，预热会持续很久、打印大量重试日志
    2. 必须正确写`asyncio.to_thread`，如果直接同步调用warmup，会阻塞FastAPI事件循环（严重bug）
    3. 启动日志容易被HF的10060警告刷屏，看着吓人
- 适用场景：答辩演示、服务器部署、网络稳定环境，优先保证AI对话体验

---

**精简对比表**

| 对比项      | 方案A 纯懒加载（无预热）                | 方案B 懒加载+lifespan预热                |
| -------- | ---------------------------- | --------------------------------- |
| 模型加载时机   | **第一条AI消息请求时**               | 后端服务启动阶段（lifespan）                |
| 后端启动速度   | 很快，秒启动                       | 偏慢，需要等待模型加载                       |
| 首次AI对话速度 | 慢（加载模型）                      | 快，预热完成后对话无等待                      |
| 网络差的容错   | ⭐⭐⭐⭐⭐  <br>就算模型拉不下来，基础业务完全正常 | ⭐⭐⭐⭐  <br>预热失败会捕获，服务依旧能启动，只是知识库失效 |
| 阻塞风险     | 无，启动阶段完全不碰向量库                | 只要用`to_thread`放到子线程，不会阻塞主事件循环     |
| 适合场景     | 本地开发、校园弱网、基础业务优先             | 答辩演示、稳定服务器、追求用户对话体验               |

**一句话总结**

两种方案都解决了【顶层导入模型直接卡死服务】的核心问题，都用懒加载把模型加载从模块导入阶段剥离； 区别只在于**加载时机**：

- 纯懒加载：把加载开销交给第一个用户；
- 预热方案：把加载开销挪到服务启动阶段，提前加载，牺牲启动速度换取用户对话体验，同时加异常捕获兜底，不会因为知识库问题导致整个系统瘫痪。
