# 本节内容

第22节能根据资料回答规则和开放时间。但问「现在有哪些开放的实验室」「某实验室有哪些设备」，知识库里没有实时数据。

这一节加 **Tool Calling**：模型自己决定要不要调工具，工具里查 MySQL，再组织回答。还是同一个 `POST /api/ai/chat`，不新建页面。还不做提交预约，那是后面 Agent 的事。

```
用户问题 →（可选）RAG 资料 → 模型判断要不要调工具
         → 调工具查库 → 把结果还给模型 → 生成回答
```

## 思路

OpenAI 兼容接口支持 `tools`。流程是：

```
1. 把工具定义和对话一起发给模型
2. 模型若要查数据，返回 tool_calls（函数名 + 参数）
3. 后端执行对应函数，把结果以 role=tool 塞回 messages
4. 再调一次模型，得到最终文本
```

本课只做两个只读工具，复用第15、16、17节已有的 service：

```
list_open_labs       查开放中的实验室
list_lab_equipments  查某个实验室下的设备
```

注意：这里的「开放」是 `labs.status=1`，不是「某个时段一定空闲」。时段冲突检测仍在预约接口里，下一阶段 Agent 再接。

```python
def chat(db: Session, data: ChatRequest):

    if not data.messages:
        raise BusinessException(message="对话内容为空")
    history = []
    for message in data.messages:
        if message.role in ("user", "assistant") and message.content.strip():
            history.append(message.model_dump())
    if not history:
        raise BusinessException(message="请输入您要对话的内容")

    # 取出用户最新的一条提问内容
    question = next(
        (item["content"] for item in reversed(history) if item["role"] == "user"), ""

    knowledge = kb_service.search(query=question)

    messages = [

                messages=messages,
                tools=TOOLS,

            msg = res.choices[0].message
            tool_calls = msg.tool_calls or []
            if not tool_calls:  # 没有工具调用 则直接返回大模型的输出结果内容
                content = msg.content
                if not content or not content.strip():
                    raise BusinessException(message="大模型没有返回内容")
                return content
            messages.append(
                {
                    "role": "assistant",
                    "content": msg.content or "",
                    "tool_calls": [
                        {
                            "id": call.id,
                            "type": "function",
                            "function": {
                                "name": call.function.name,
                                "arguments": call.function.arguments,
                            },
                        }
                        for call in tool_calls
                    ],
                }
            )
            for call in tool_calls:
                result = run_tool(db, call.function.name, call.function.arguments)
                messages.append(
                    {"role": "tool", "content": result, "tool_call_id": call.id}
                )
    except Exception as exc:

        raise BusinessException(message="大模型调用失败，请稍后重试")
```

#### bug修复
**修正：三轮工具调用结束后仍须返回回答**

上面的 `return` 只在模型没有调用工具时执行。
如果三轮都调用工具，循环结束后函数会隐式返回 `None`。
本课程的 `ChatMessage.content` 是 `str`，接口构造响应时会校验失败，不能保证返回空回答。
应在最后一次 `messages.append(...)` 之后、`except` 之前添加以下代码；缩进与 `for _ in range(3):` 对齐，使它在循环结束后执行：

```python
        # 三轮工具调用已结束，使用已有结果生成回答，禁止继续调用工具。
        res = client.chat.completions.create(
            model=settings.LLM_MODEL,
            messages=messages,
            tools=TOOLS,
            tool_choice="none",
        )
        content = res.choices[0].message.content
        # 模型仍可能没有返回正文，此时交给已有异常处理返回错误提示。
        if not content or not content.strip():
            raise BusinessException(message="大模型没有返回内容")
        return content
```

这样最多执行三轮工具调用，另加一次禁止工具调用的回答请求。
验证时模拟连续三轮返回 `tool_calls`，第四次返回正文，应得到非空回答；
第四次返回空内容或调用失败时，应进入已有异常处理，返回“大模型调用失败，请稍后重试”。

# 解析
## Tool Calling理解（重点）
Tool Calling 完整时序
```
用户提问 
→ （可选 RAG）
→ 带上 tools 发给模型 
→ 模型返回 tool_calls 
→ 后端执行函数,匹配并执行对应工具函数
→ 把结果以 role=tool 塞回 messages 
→ 再次请求大模型，生成最终回答
```
我的理解：
1. 我们首先要定义TOOLS，是一份工具使用的说明书（包含有哪些工具，怎么使用这些工具）
2. 大模型在拿到`tools+问题+RAG资料`后，如果判断需要查调用工具，就返回了一个`tool_calls`
3. `tool_calls`需要解析，解析之后才能得到它想要调用的一系列工具名称和参数
4. 将解析出来的工具和`run_tool`里面工具进行匹配
	-  ✅ 匹配成功：执行对应的工具逻辑（查询 MySQL），拿到结果
	-  ❌ 匹配失败（说明模型出现幻觉了不存在的工具）：生成错误信息
5. 调用`run_tool`会返回工具使用完成后的结果，（成功的查询结果 / 错误信息），统一包装成 `role="tool"` 的消息，追加到上下文 `messages` 里
6. 带着拼接的完整上下文，再次请求大模型，由大模型整合信息生成最终回答

> 疑问：为什么要进行匹配工具这个操作呢？
>发给模型的 TOOLS 就是后端全部支持的工具，理论上模型只能从里面选择。
>但模型偶尔会幻觉，写出清单里不存在的工具名，所以需要匹配校验

## 工具定义
### TOOLS 数组

**需求情景**
对应上面Tool Calling 完整时序的`→ 带上 tools 发给模型`,这里只是定义`tools`
- RAG 只能读提前存好的静态文档；
- 当模型**需要实时 MySQL 数据**（开放实验室、实验室设备），模型不知道怎么调用你后端的 Python 查询函数。 
- OpenAI 兼容接口约定：你把**函数的说明书**打包成这个 `TOOLS` 数组，一起发给大模型。 
- 模型看懂说明书之后，自己判断：要不要调用、调用哪个、填什么参数。

> 重点：**这一段只是说明书，不是可执行代码！模型不会跑这里的代码。**


**逐字段拆解**

```json
{
  "type": "function",
  "function": {
    "name": "list_open_labs",
    "description": "查询当前开放中的实验室列表，可以按名称关键字来筛选",
    "parameters": {
      "type": "object",
      "properties": {
        "keywords": {
          "type": "string",
          "description": "实验室的名称关键字，可以为空"
        }
      }
    }
  }
}
```

1. `"type": "function"` 固定标识：这是一个**函数工具**，OpenAI协议规定，目前工具类型就function。
2. `"name": "list_open_labs"` 工具名字，**唯一标识**。 模型决定调用时，会把这个name返回给后端；后端`run_tool`里面靠这个name匹配对应的查询逻辑。 
>✅ 要求：名字要和你run_tool里面if判断的名字完全一致，不能写错。
3. `"description"` 给模型看的自然语言说明：这个工具能干什么、适合什么时候调用。 **写得好不好直接决定模型会不会正确选择这个工具**。 写模糊了，模型就该调的时候不调、不该调的时候乱调用。
4. `"parameters"`：JSON Schema，描述参数结构
    - `"type": "object"`：所有参数打包成一个对象（{}）
    - `"properties"`：里面放每一个参数定义
        - key：参数名（`keywords` / `lab_id`），后端拿到arguments之后用这个key取参数
        - `type`：数据类型 `string / integer / boolean`，模型会按这个类型生成参数
        - `description`：告诉模型这个参数是什么含义
    - 你这里省略了 `required` 字段！

 > 补充知识点：`required` 数组标记哪些参数是必填。 比如 `list_lab_equipments` 必须要lab_id，规范写法要加上：

```
"required": ["lab_id"]
```
不加required，模型有可能不传必填参数，后端要做参数校验（你run_tool里已经做了判断）

### 底层原理（协议层面）

这是**OpenAI Tool Calling协议标准的JSON Schema描述**：

1. 你把这个TOOLS数组和messages一起传给大模型接口；
2. 模型在推理的时候，会对照这份schema，判断用户问题是否匹配工具能力；
3. 如果决定调用，模型输出 `tool_calls`：里面包含 name + arguments（符合这个schema的json字符串）；
4. 后端拿到后，`json.loads(arguments)` 解析参数，匹配name，执行对应的业务函数；
5. 工具结果包装成 `role:tool` 的消息塞回对话，再发给模型继续回答。

> 一句话：TOOLS = 给模型看的接口文档，约束模型输出参数的格式。

### TOOLS模板

```json
{
  "type": "function",
  "function": {
    "name": "你的工具名",
    "description": "清晰描述：什么时候调用、能干什么",
    "parameters": {
      "type": "object",
      "properties": {
        "param1": {
          "type": "string",
          "description": "参数说明"
        }
      },
      "required": ["param1"] // 必填参数列表，非常建议加上
    }
  }
}
```


## run_tool，工具的执行
**前置背景**
TOOLS 是说明书，是发给模型的 → 模型判断需要查实时数据，输出 `tool_calls`（工具名字 + 参数 json 字符串） (`tool_calls`在后面修改`chat`里面)
👉 **模型只会生成调用指令，模型没有能力去连 MySQL、执行 Python 查询代码**

**需求情景**
后端拿到模型返回的 `tool_calls` 之后，需要一段代码，来完成：

1. 解析模型给的 `arguments` 字符串
2. 根据工具名称，找到对应的业务查询逻辑（查开放实验室 / 查实验室设备）
3. 调用你已经写好的 `service`（`lab_service /equipment_service`）访问数据库
4. 精简返回字段，不要把整张表原始数据丢给大模型（省` token`、减少干扰）
5. 哪怕出错（参数缺失、参数非法、数据库报错），也不能直接抛异常打断对话；把错误信息包装成`json` 字符串，作为工具结果交给模型，模型拿到错误后再组织语言回复用户

一句话： **run_tool = 专门用来执行模型下发的 tool_calls 指令的分发执行器**

### 骨架框架（整体结构）

```python
def run_tool(db: Session, name: str, arguments: str) -> str:
    # 第一层：解析模型传过来的arguments字符串，转成字典
    try:
        args = json.loads(arguments or "{}")
    except JSON解析异常:
        return 错误json字符串
    
    # 第二层：根据工具名分发，执行对应业务查询
    try:
        if 工具A:
            调用service查库 → 挑选需要字段 → 打包json返回
        elif 工具B:
            参数校验（lab_id）→ 调用service查库 → 挑选字段 → 打包json返回
        else:
            工具不存在，返回错误json
    except 任意业务异常:
        return 异常信息json字符串
```

入参：

- `db: Session`：sqlalchemy数据库会话，给service查询用
- `name: str`：模型传过来的工具名字，和TOOLS里的name一一对应
- `arguments: str`：是**JSON 格式的字符串**，不是 Python 字典！
>是模型输出的 返回值：永远是 `str`（json字符串），保证统一格式，后面塞进 `role=tool` 的消息

```python
def run_tool(db: Session, name: str, arguments: str) -> str:
    try:
        args = json.loads(arguments or "{}")
    except json.JSONDecodeError:
        return json.dumps({"error": "参数不是合法的json"}, ensure_ascii=False)

    try:
        if name == "list_open_labs":
            keywords = (args.get("keywords") or "").strip() or None
            page = lab_service.get_lab_page_list(
                db, page=1, page_size=10, keywords=keywords, status=1
            )
            rows = [
                {
                    "id": item.id,
                    "name": item.name,
                    "location": item.location,
                    "capacity": item.capacity,
                    "open_time": item.open_time,
                    "close_time": item.close_time,
                }
                for item in page.list
            ]
            return json.dumps({"total": page.total, "labs": rows}, ensure_ascii=False)

        if name == "list_lab_equipments":
            lab_id = args.get("lab_id")
            if not lab_id:
                return json.dumps(
                    {"error": "参数缺少实验室 lab_id"}, ensure_ascii=False
                )
            keywords = (args.get("keywords") or "").strip() or None
            page = equipment_service.get_equipment_page_list(
                db, page=1, page_size=10, lab_id=int(lab_id), keywords=keywords
            )
            rows = [
                {
                    "id": item.id,
                    "name": item.name,
                    "lab_id": item.lab_id,
                    "lab_name": item.lab_name,
                    "spec": item.spec,
                    "quantity": item.quantity,
                    "status": item.status,
                }
                for item in page.list
            ]
            return json.dumps(
                {"total": page.total, "equipments": rows}, ensure_ascii=False
            )

        return json.dumps({"error": f"未找到工具：{name}"}, ensure_ascii=False)
```

```python
    except Exception as exc:
        return json.dumps({"error": exc.message}, ensure_ascii=False)
```

5. **最外层业务捕获 except Exception as exc** 数据库报错、service内部报错、类型转换报错，全部捕获，包装成 `{"error": exc.message}`。

#### 参数ensure_ascii=True
默认 `ensure_ascii=True` 的时候：**中文会被转成 \u 编码** 示例对比：

```python
# ensure_ascii=True（默认）
json.dumps({"name":"物理实验室"})
# 输出：{"name":"\u7269\u7406\u5b9e\u9a8c\u5ba4"}

# ensure_ascii=False
json.dumps({"name":"物理实验室"}, ensure_ascii=False)
# 输出：{"name":"物理实验室"}
```

放到 `run_tool`里的需求情景
返回给大模型的内容里有中文：实验室名称、地点、错误提示（`参数缺少实验室 lab_id`）
- 如果不加 `ensure_ascii=False`：中文变成 `\uXXXX` 转义字符
- 大模型虽然也能识别，但可读性差、看着乱，不方便模型理解内容


### 重要知识点 

✅ 1. 为什么只返回少量字段？ 
token是计费的，给模型无关字段：费钱、上下文变长、模型容易被冗余信息干扰。**工具返回结果是给模型看的，不是给前端看的**。

✅ 2. 所有结果（正常+错误）统一是json字符串 
协议要求tool的content必须是字符串

✅ 3. 两层try的区别
- 外层try：专门抓 `json.loads` 解析错误（参数格式错）
- 内层try：抓数据库、业务查询的所有运行时异常
	- 设计目的：解析失败和业务失败分开处理，全部不抛出`BusinessException`打断对话

✅ 4. 职责边界：`run_tool` 只做【分发+字段裁剪+异常封装】 
真实**查询**逻辑(就是去数据库查东西的函数这些)依然放在 `lab_service / equipment_service`

✅ 5. 模型的参数描述 ≠ 后端校验 
哪怕`TOOLS`写了`schema`，后端**必须再校验**：必填参数、类型转换（`lab_id`转`int`），模型偶尔会输出不合规参数。

✅ 6. 分页控制` page_size=10` 限制返回条数，防止一次性查出几百条数据，上下文爆炸。


❌ **坑点记录**

1. `exc.message` 会报错，修正写法：`json.dumps({"error": str(exc)})`
2. `name`必须严格和TOOLS的`name`一模一样，大小写敏感
3. 不要直接返回ORM对象，ORM对象不能序列化，必须手动构造字典

**总结**

- `run_tool`是工具分发函数，接收模型传来的工具名和`json`字符串参数；
- 先解析参数，再根据工具名调用对应的`service`查询数据库，手动筛选必要字段，把正常数据或者异常信息统一包装成JSON字符串返回给模型；
- 所有异常不直接抛出，交给模型感知错误，保证`tool`调用的对话流程不中断


## 改 chat：接入工具循环

**原本chat需求场景**
只做**RAG 问答**： 用户提问 → 提取最新问题 → 去向量库检索静态文档（实验室规则、预约流程、开放说明这类写死在 md 里的资料）→ 把检索到的资料拼进 system 提示词 → 一次性发给大模型，模型直接输出回答。 
✅ 能力：回答知识库里面提前写好的固定文本 
❌ 短板：**拿不到 MySQL 里的实时数据**，没法查当前开放实验室、设备列表这类动态数据；全程只和大模型交互一次，没有调用工具的能力

**改动之后的chat**
RAG + Tool Calling 混合
保留原来 RAG 全部能力，新增工具调用能力
用户提问 → 先 RAG 拿静态文档资料拼 system 提示词 → 进入最多 3 轮的**工具循环**：

1. 带上`tools`描述发给大模型，让模型自己判断：只用现有资料回答，还是需要查数据库
2. 如果模型选择调用工具：后端执行`run_tool`，用 db 会话查 MySQL 实时数据
3. 把查询结果以`role=tool`消息追加到对话上下文，再次发给模型
4. 循环最多 3 轮，防止模型无限调用工具死循环
	1. ✅新增能力：模型自主决策，查询 MySQL 实时业务数据（开放实验室、实验室设备等） 
	2. ✅ 保留能力：静态知识库 RAG、原有消息校验逻辑不变

<br>

**代码解析**

> 前置：原有校验、RAG检索、拼接system提示词逻辑不变，下面只解析改动新增代码

**1. 函数签名改动**

```python

# 新

```

新增`db: Session`数据库会话。
SQLAlchemy的会话对象，传给`run_tool`，工具执行查询实验室、设备等SQL时使用

### 可变上下文列表 messages
**2. 新增messages上下文列表**

```python

    {"role": "system", "content": system_prompt},
    *history,
]
```

对话记忆本身已经存在：`history` 是前端传入的用户、助手历史消息。 
旧版写法：messages 是在调用大模型时临时组装的一次性数组，请求结束就丢弃，无法追加内容

新版改动：把消息容器抽成独立可变列表，作为**本轮工具流程的上下文容器，支持中途追加新消息**
- 工具调用记录、数据库返回的 tool 结果，都可以用`append()`追加进这个列表。 
- 每一轮向大模型发起请求时，都会传递这份完整、不断变长的上下文，模型才能知道前面调用了什么工具、拿到了什么数据，保证工具调用链路不中断

### 工具调用的循环逻辑
**骨架结构**
```python
for _ in range(3):
    # 1. 请求大模型
    res = client.chat.completions.create(...)
    ...
    # 2. 如果有tool_calls，执行工具、append两条消息
    for call in tool_calls:
        result = run_tool(...)
        messages.append(...)
# 上面全部代码都包裹在 for 循环里面
# 一轮工具执行、追加完 messages 之后，本轮循环体跑完，自动进入下一次迭代
# 下一轮迭代，会再次执行 client.chat.completions.create，传入已经变长的 messages
```

**3. 替换原有单次大模型请求，新增工具循环主体**

```python
for _ in range(3):
```

限制最大3轮工具调用。工程上的保护机制，防止模型逻辑异常，无限循环调用工具，卡死接口
### 工具循环最大轮次限制
```python
for _ in range(3):
    发请求给大模型
    if 模型不调用工具：
	    return 答案，整个函数直接结束
    如果模型要调用工具：执行工具、追加消息，继续走下一轮循环
```
**为什么选 3 轮？**

**1、需求情景**

Tool Calling 允许模型拿到结果后继续调用下一个工具，很容易形成连环调用：

> 问 A → 查工具 1 → 拿到结果 → 模型觉得还不够 → 再查工具 2 → 拿到结果 → 还要查工具 3…… 
> 
> 如果不加上限，模型幻觉、逻辑跑偏的时候，会**无限循环调用工具**，接口一直不返回、占数据库连接、超时、服务器资源耗尽。所以必须加最大循环次数。

<br>
**2、循环原理**
**为什么选 3，不是 1、2、5、10？**
首先需要明白，**这个循环到底是什么原理**
工具只有两个：`list_open_labs`、`list_lab_equipments`
**核心规则**
👉 **能进入下一轮循环的唯一条件：上一轮模型选择了调用工具** 
👉 只要某一轮模型不想调工具，直接 return，循环提前终止，不会跑完 3 次

✅ **场景 1**：一轮就结束（最常见）

用户问：**实验室几点开门？**
1. 第 1 轮循环： 模型看 RAG 知识库里面已经有开门时间，不需要调用 MySQL 工具 → 没有 tool_calls → 直接 return 回答，循环结束 只用了 1 轮，剩下 2 轮根本不跑

✅ **场景 2**：两轮结束（典型正常连环调用）

用户问：**现在开放的物联网实验室里面有哪些设备？**
1. 第 1 轮循环： 模型判断：我不知道物联网实验室的 lab_id，要先查开放实验室 → 返回 tool_calls，调用`list_open_labs`，拿到物联网实验室的 id 追加消息，进入第 2 轮
2. 第 2 轮循环： 上下文里已经有实验室 id 了，模型判断：我要拿这个 id 查设备 → 返回 tool_calls，调用`list_lab_equipments`，拿到设备列表 追加消息，进入第 3 轮
3. 第 3 轮循环： 模型现在已经拿到实验室 + 设备全部数据，不需要再调用工具 → 直接 return 文字回答，循环结束

> 这个就是我们业务里最多的连环查询：查实验室 → 查设备，两轮工具调用，在第 3 轮生成答案。 
> 所以预留 3 轮，刚好覆盖这个标准链路。
<br>

**3、行业通用经验值（工程惯例）** 
大部分`RAG+Tool` 项目默认都是 2～4 轮，**3 是一个折中常用值**
- 设 1：只能调用一次工具，连续多步查询的场景直接失败，不够灵活
- 设 2：够用，但容错偏少，复杂链式工具容易卡断
- 设 5/10：风险变高，一旦模型幻觉疯狂调用，耗时变长、数据库压力大、容易超时
<br>

**4、补充边界**
- 3 不是硬性标准，是**业务权衡出来的经验值**，不是协议规定
- 上线之后如果发现业务经常需要多轮，可以改成 4；
- 如果稳定性差、超时多，可以降到 2
- 本质：**在「满足业务多步查询」和「防止无限循环、控制耗时 / 资源」之间取平衡**


#### bug修复
工具循环耗尽后缺少兜底返回，函数隐式返回 None
**问题现象**
只要连续三轮，模型每一轮都选择调用工具，循环跑完，函数没有返回值，返回 None，接口校验失败。 正常情况模型不会这样，但是模型有幻觉，这个边界情况必须兜底。

**根本原因**
首先需要明白，这个循环到底是什么原理，去看上面**2、循环原理**
这个时候，如果
用户提问，模型连续三次都选择调用工具（属于模型幻觉，不是业务需要）

1. 第 1 轮：调用工具 A → 追加消息，进入第 2 轮
2. 第 2 轮：调用工具 B → 追加消息，进入第 3 轮
3. 第 3 轮：**模型明明已经拿到全部数据，但是它幻觉了，依然还要调用工具** 执行工具、追加消息 
	- ❌ 现在：`for _ in range(3)` 的 3 次循环**全部跑完了** ，没有 return，函数返回 None，接口报错

✅**修复方案**
三轮名额用完之后，强制再发一次请求，并且 `tool_choice="none"`： 告诉模型：**不许再查任何东西了！你就拿现在手里所有查到的资料，整理一句话回答我！** 
然后拿到回答，return 出去，保证一定有字符串返回，不会返回 None

调用大模型接口，传入上下文、工具定义与工具选择策略

- `tools=TOOLS`：把提前定义好的工具说明书（函数名、描述、入参）发给大模型

拿到模型返回结果。判断是否存在工具调用：
- 无`tool_calls`：模型不需要查数据库，直接返回回答，结束整个对话流程
- 有`tool_calls`：进入工具执行分支`messages.append`

```python
    {
        "role": "assistant",
        "content": msg.content or "",
        "tool_calls": [
            {
                "id": call.id,
                "type": "function",
                "function": {
                    "name": call.function.name,
                    "arguments": call.function.arguments,
                },
            }
            for call in tool_calls
        ],
    }
)
```

解析
OpenAI协议强制要求：**模型发起工具调用这件事，要写入上下文**。 
把`assistant`的`tool_call`记录追加进`messages`，带上唯一`id`，后面工具返回结果需要用这个`id`配对

```python
for call in tool_calls:
    result = run_tool(db, call.function.name, call.function.arguments)
    messages.append(
        {"role": "tool", "content": result, "tool_call_id": call.id}
    )
```

解析：
1. 遍历每一个工具调用，调用`run_tool`：解析参数、匹配对应的业务查询方法、操作MySQL
2. `run_tool`返回JSON字符串形式的查询结果
3. 追加一条`role="tool"`消息，**tool_call_id必须和上面assistant调用的id一一对应**，大模型才能匹配上哪条结果对应哪一次工具调用
4. 追加完成后，回到循环开头，带着新的上下文再次请求大模型


### 为什么要两次messages.append
或者说为什么 tool 消息需要 `tool_call_id` 绑定调用记录

两次`messages.append`
- 第一次 `append（assistant 消息，带 tool_calls）`
	- 含义：**记录【大模型决定要调用工具】这件事**
- 第二次 `append（role="tool"）`
	- 含义：**记录【工具执行后的返回结果】**
	- 并且用 `tool_call_id` 和上面那条调用记录绑定
>为什么要绑定呢？
>不是用来校验，是**遵循 OpenAI 对话协议，构建完整的工具调用上下文**，下一轮传给大模型的时候，模型能看懂：我之前调用了哪个工具、拿到了什么数据。


### traceback异常堆栈打印
**需求场景**
旧版本
代码报错的时候，后端只会直接抛出一句提示给前端：`大模型调用失败，请稍后重试`。 
后端控制台看不到详细报错：不知道是参数错了？数据库查崩了？大模型接口超时？还是 tool 调用参数解析失败？很难排查问题。

但是我们不能把原始报错堆栈直接返回给前端，因为：
1. 堆栈信息里面有内部代码、路径、数据库细节，属于敏感信息，暴露出去不安全
2. 前端只需要给用户一句友好简单提示，用户看不懂技术堆栈

👉 所以改动的目标
**后端自己打印完整报错堆栈（给开发看，用来 debug），对外仍然返回统一、简洁的业务提示（给前端 / 用户看）。**


**4. 异常代码改动**

```python
# 旧
except Exception:
    raise BusinessException(message="大模型调用失败，请稍后重试")
# 新
except Exception as exc:
    traceback.print_exc()
    raise BusinessException(message="大模型调用失败，请稍后重试")
```

解析
捕获异常时接收异常对象`exc`，`traceback.print_exc()`打印完整报错堆栈，开发阶段方便定位bug；最后依然对外抛出统一业务异常，前端拿到固定提示

**5. 新增导入**

```python
import traceback
```

Python内置模块，用来打印异常完整堆栈信息，配合上面的异常代码使用

**于是**

1. 新增导入
```python
from sqlalchemy.orm import Session

```
`
2. 调用 `ai_service.chat` 时，多传第一个参数 `db`

```python
# 旧
content = ai_service.chat(data)

content = ai_service.chat(db, data)
```
