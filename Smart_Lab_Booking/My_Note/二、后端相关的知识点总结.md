# 1、写第一个FastAPI接口 并测试
（来自  04. 搭建后端FastAPI工程）

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def root():
    return {"message": "Hello FastAPI"}
```

启动测试

```bash
uvicorn app.main:app --reload --port 8000 --host 127.0.0.1
```

---

**第2行：`app = FastAPI()`**

```python
app = FastAPI()
```

- 调用这个类，**实例化，创建一个应用对象**

**第3行：`@app.get("/")` 装饰器（重点）**

```python
@app.get("/")
```

`@xxx` 是 Python 的**装饰器语法**

1. `app.get` 是 app 对象提供的一个装饰器方法
2. `get`：代表 HTTP 请求方法 —— `GET` 请求（浏览器直接在地址栏访问就是GET）
3. `"/"`：接口的路由路径，也就是根路径，对应地址 `[http://127.0.0.1:8000/](http://127.0.0.1:8000/)`

✅ 装饰器做的事情： 把下面这个 `root` 函数，**注册绑定到 app 的路由表里** 告诉app：

> 当收到 GET 请求、访问路径 `/` 的时候，就执行下面这个函数

> 补充：还有 `@app.post()`、`@app.put()`、`@app.delete()` 对应其他请求方式

**第4~5行：接口处理函数**

```python
def root():
    return {"message": "Hello FastAPI"}
```

- `root`：只是函数名字，可以随便取（比如 index、home），没有强制要求
- 这个函数就是**接口的视图函数 / 处理函数**，请求来了就执行它
- `return {"message": "Hello FastAPI"}` 返回一个Python字典； 
- ✨ FastAPI自动做了两件事：
    1. 把字典自动转换成 **JSON 字符串**
    2. 自动设置响应头 `Content-Type: application/json`

## 完整执行流程
**（请求来了之后发生了什么）**

1. 启动服务：`uvicorn app.main:app --reload`，uvicorn 是ASGI服务器，把app跑起来，监听8000端口
2. 浏览器访问 `[http://127.0.0.1:8000/](http://127.0.0.1:8000/)` → 发送一个 GET 请求，路径 `/`
3. uvicorn把请求交给 `app` 这个FastAPI实例
4. app去自己的路由注册表匹配：找到 `@app.get("/")` 绑定的 `root` 函数
5. 执行 `root()`，拿到返回的字典
6. FastAPI自动序列化字典为JSON，返回给浏览器
7. 浏览器收到JSON展示出来

## Pydantic + BaseModel

FastAPI 本身不是从零写的，它是套壳工具： 底层依托两个核心东西：
-  **Starlette：ASGI Web 框架** —— 负责网络通信，接收浏览器 / 前端发过来的 HTTP 请求、最后把响应发回去（相当于网络搬运工）
-  **Pydantic：数据校验库** —— 负责校验请求参数、格式化输出数据（数据检查员）
>`BaseModel` 是 Pydantic 库里面的**基础父类**。 
>只要你的类继承 `BaseModel`，它就自动获得：**数据校验、类型转换、序列化（转 JSON）** 的能力。
> Pydantic 就是做「数据模型、校验」的库，`BaseModel` 是它最核心的起点


### 底层&开发知识点补充
1. 自动打包返回数据给前端
前端只看得懂 JSON 格式的数据。
如果你在接口里 return 字典、列表、或者我们写的 Pydantic 模型对象，FastAPI 会自动帮你把这些 Python 数据，整理成前端能看懂的 JSON，不用我们自己写代码转换。

2. 自动生成接口调试页面

## `__init__.py`
目录下创建`__init__.py`

**为什么这么做？**
>`__init__.py` 是 Python 的**包标识文件**。 只要文件夹里面有 `__init__.py`，这个文件夹就不再只是普通文件夹，变成一个 **Python 包（package）**，可以用 `import` 导入里面的代码。

**总结`__init__.py` 的作用：**
>标记当前文件夹为 Python 包，支持 `import` 导入，保证 `uvicorn app.main:app` 这种导入写法稳定生效，属于 Python 后端项目的规范约定，空文件即可。

`uvicorn app.main:app` 格式为 `包名.模块名:实例对象`，代表导入 `app/main.py` 中名为 `app` 的 FastAPI 实例并启动服务；
依赖`__init__.py`把 app 文件夹识别为 Python 包，才能支持这种导入写法。

**为什么pycharm使用的过程中没这样操作？**
>PyCharm 可手动标记源码根目录，IDE 额外处理导入路径，屏蔽了这个要求；但在终端、uvicorn 等原生 Python 运行环境下，该文件依然是识别 Python 包的标准要求。

关于database.py的代码解析

**绝大多数 FastAPI + SQLAlchemy 2.0 的项目，数据库部分基本都是这套模板**
>固定套路：`create_engine` 创建连接引擎 → `sessionmaker` 生成会话工厂 → `get_db` 作为依赖函数管理会话生命周期 → 定义 `Base` 基础模型类

## database.py

```python
from sqlalchemy.orm import sessionmaker, DeclarativeBase, Mapped, mapped_column
from sqlalchemy import create_engine, DateTime
from app.config import settings
from datetime import datetime

engine = create_engine(settings.DATABASE_URL)
# 数据库session会话的连接工厂
SessionLocal = sessionmaker(bind=engine, autoflush=False)

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

class Base(DeclarativeBase):
    id: Mapped[int] = mapped_column(
        primary_key=True, autoincrement=True, comment="主键ID", sort_order=-1
    )
    create_time: Mapped[datetime] = mapped_column(
        DateTime, default=datetime.now, comment="创建时间", sort_order=1
    )
    update_time: Mapped[datetime] = mapped_column(
        DateTime, default=datetime.now, onupdate=datetime.now, comment="更新时间", sort_order=2
    )
````
>Base 类就是所有数据库模型的公共父类，用来统一定义所有表都会拥有的公共字段和数据库配置。

>和FastAPI先关的内容： **依赖注入 Depends**

#### 生成器再理解1
这里是生成器yeild再理解
```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

- 这是**依赖函数**，给 FastAPI 的 Depends 使用
> `Depends()` 是 FastAPI 内置的工具，专门用来做【依赖注入】
>
 使用方式：`Depends(你写好的函数)`，这里就是 `Depends(get_db)`
 >
 逻辑： 当请求进来，走到这个接口的时候，FastAPI 会**自动执行你传给 Depends 的函数（get_db）**，拿到函数 yield 返回的 db 对象，传给接口参数。
>
>比如：def login(db = Depends(get_db))

- `yield`：生成器，先把 db 会话交给接口函数使用
>yield 属于生成器关键字
>生成器常见优势：按需取值，不需要一次性加载全部数据，**节省内存**
>但在 get_db 这个依赖函数里，**使用 yield 不是为了节省内存**，而是利用生成器**暂停、恢复执行**的能力
>
>执行流程：
>1. 创建 db 会话；
>2. 执行 `yield db`：把 db 会话向外传递，**函数在这里暂停，停住不动** → 也就是**「先把 db 交给接口函数使用」**
>3. 接口内部逻辑全部执行完成（正常结束 / 抛出异常都算）
>4. 回到暂停位置，继续往下走，进入 finally，执行 `db.close()`，释放数据库连接。
>
> 关键对比： 
> 如果用 return，return 之后函数直接终止，关闭连接的代码永远无法执行。
> yield 实现了：先给资源，等资源用完，自动收尾释放。
> 
>`finally`：无论接口正常执行还是报错，最后一定会执行 `db.close()`，释放数据库连接，防止连接泄露

5、
```python
class Base(DeclarativeBase):
    id: Mapped[int] = mapped_column(
        primary_key=True, autoincrement=True, comment="主键ID", sort_order=-1
    )
    create_time: Mapped[datetime] = mapped_column(
        DateTime, default=datetime.now, comment="创建时间", sort_order=1
    )
    update_time: Mapped[datetime] = mapped_column(
        DateTime, default=datetime.now, onupdate=datetime.now, comment="更新时间", sort_order=2
    )
```

- 所有模型（User 等）都继承这个 Base，自动带上这三个公共字段
- `sort_order`：控制数据表字段展示顺序，**数值越小，字段越靠前**
    - id 设置 sort_order=-1
    - 我们自己写的业务字段（username、password）没有指定 sort_order，默认值是 0
    - 大小对比：`-1 < 0 < 1 < 2`
    - 需要确保最终顺序：id → username、password → create_time → update_time
    - 如果不设置 sort_order=-1，默认 id 也是 0，那字段顺序就乱了，id 有可能跑到后面去


#### Mapped和mapped_column

✅ `Mapped[类型]`
- 作用：**标记这是数据库表的一个字段，同时声明 Python 侧的类型**
- `Mapped[int]`：
    - 告诉 Python / 类型检查工具：这个变量 `id` 是 `int` 整数类型
    - 告诉 SQLAlchemy：这是一个**映射到数据库的列**，不是普通的类属性
- 对比理解：
    
    ```python
    # 普通变量，只是Python变量，不会生成数据库字段
    name: str
    
    # Mapped包装：这是数据库表字段，会映射到mysql表里的一列
    name: Mapped[str]
    ```

> 简单一句话：`Mapped[]` 是**“标记身份”**：这个属性要同步映射到数据库，附带 Python 类型。

 ✅ `mapped_column(...)`
- 作用：**定义这个数据库列在 MySQL 里的规则、约束、附加配置**
- 里面传的参数，全部是数据库层面的设置：
    - `primary_key=True`：主键
    - `autoincrement=True`：自增
    - `comment="主键ID"`：数据库字段注释
    - `sort_order=-1`：控制生成表时字段先后顺序（前面有解析的）
    - `default=datetime.now`：新增数据时默认值
    - `onupdate=datetime.now`：更新行的时候自动赋值（update_time 专属）

# 5、users.py 和自动建表

models/user.py 是用户表的ORM模型文件，用来映射MySQL里的users表。

**提示**：其中重复性工作，可以直接让ai帮我们写就行
```python
from sqlalchemy.orm import Mapped, mapped_column
from sqlalchemy import String
from app.database import Base

class User(Base):
    __tablename__ = "users"
    __table_args__ = {"comment": "用户信息表"}

    username: Mapped[str] = mapped_column(String(50), comment="账号", nullable=False)
    password: Mapped[str] = mapped_column(String(50), comment="密码", nullable=False)
    name: Mapped[str] = mapped_column(String(50), comment="名称", nullable=False)
    role: Mapped[str] = mapped_column(
        String(50), comment="角色：student-学生，admin-管理员", nullable=False
    )
    email: Mapped[str | None] = mapped_column(String(50), comment="邮箱")
    phone: Mapped[str | None] = mapped_column(String(50), comment="手机号")
    avatar: Mapped[str | None] = mapped_column(String(50), comment="头像")
    status: Mapped[int] = mapped_column(default=1, comment="状态：0-禁用，1-正常")
```

1、先看导入部分： 
```python
from sqlalchemy.orm import Mapped, mapped_column
from sqlalchemy import String
from app.database import Base
```
String 对应 MySQL 的 varchar
从 app.database 导入 Base，Base 是我们之前写的基础模型类，继承它就自动拥有 id、创建时间、更新时间三个公共字段

2、class User (Base) 就是我们的用户模型类： 
- `__tablename__` 指定数据库里的表名叫 users。
- `__table_args__` 给整张表加注释，在 Navicat 里可以看到这个表的说明。

3、下面一行行是表里面的业务字段：
- `nullable=False` 代表这个字段必填，不能是 null。比如账号、密码、姓名、角色都是必填项。
- `str | None` 代表这个字段可以为空，邮箱、手机号、头像不是必填。
- `String(50)` 代表数据库里这个字符串最长 50 个字符。
- `default=1` 是默认值，新增用户时如果不传入 status，自动填 1，代表正常启用。

>字段排序上： 继承过来的 id sort_order=-1 排在最前面；这些业务字段没有设置 sort_order，默认是 0，排在 id 之后、create_time、update_time 之前。

这个文件写完之后，执行建表语句，SQLAlchemy 就会自动在 MySQL 生成 users 这张表，后续增删改查用户数据，直接操作 User 这个类就行，不用手写原生 SQL

#### 补充:什么是ORM模型
**Object Relational Mapping，对象关系映射**
通俗解释： 它就是把 Python 的类和对象，和 MySQL 的数据表做映射。
- 类 → 对应一张数据表
- 类里面的属性 → 对应表里的字段
- 创建这个类的实例对象 → 对应表里的一行数据

#### 怎么理解自动建表？
2、创建数据库 `lab_agent`
初次使用Navicat，需要注册，并连接MySQL，然后再创建

**既然是自动建表，为什么还要我专门取 navicat 新建 lab_agent 这个数据库**

> SQLAlchemy 的 `Base.metadata.create_all()` 只能建「数据表 (table)」，不能创建「数据库 (database)」
- `lab_agent`：这是**数据库（库）**，相当于一个文件夹。

# 6、`schemas目录下auth.py`和user.py

> 前置概念：`schemas` 在 FastAPI 项目里叫**数据模型/序列化模型**，基于 Pydantic。 作用：定义请求要接收什么字段、接口返回给前端什么字段；自动做类型校验；ORM对象 ↔ JSON 数据转换。

---
`schemas/auth.py`

```python
from pydantic import BaseModel

class LoginRequest(BaseModel):
    username: str
    password: str
```

逐行拆解：
1. `from pydantic import BaseModel` 导入Pydantic的基础模型类，所有自定义数据模型都要继承它。
2. `class LoginRequest(BaseModel):` 登录**入参模型**：专门用来接收前端POST提交过来的登录请求体（JSON）。
3. `username: str`：用户名，字符串类型，**必填**
4. `password: str`：密码，字符串类型，**必填**

✅ 功能：

1. 你的 Vue 前端登录的时候，axios 会发一段 JSON 给后端，长这样：
```json
{
  "username": "zhangsan",
  "password": "123456"
}
```

2. `LoginRequest` 就是提前跟 FastAPI 说好：
> 这个接口，我只接收这种格式的请求体（Body），必须有 username、password，而且都得是字符串。
    少字段、类型不对（比如username传数字）直接返回报错


---

`schemas/user.py`

```python
from pydantic import BaseModel, ConfigDict

class UserResponse(BaseModel):
    id: int
    username: str
    name: str
    role: str
    phone: str | None = None
    email: str | None = None
    status: int

    model_config = ConfigDict(from_attributes=True)
```

1、`class UserResponse(BaseModel):` 
>是登录**返回模型**：后端查询到用户数据之后，用来打包、返回给Vue前端的JSON结构

2、
```
id: int
username: str
......
```
这里，就是在**定义返回 JSON 的格式、类型、是否必填**

3、`model_config = ConfigDict(from_attributes=True)` 
>开启ORM自动转换：数据库查出来的SQLAlchemy用户对象，可以直接传给这个模型，自动转为给前端的JSON，不用手动一个个赋值。

✅ 功能： 后端从数据库拿到用户信息，通过 UserResponse 规范返回给Vue前端的JSON格式。
只会返回我们写在这里的字段，**不会返回数据库里的密码等敏感字段**，起到数据过滤保护的作用。 字段会自动校验类型，保证返回给前端的数据格式统一。


**总结**
- LoginRequest：登录**入参模型**，约束前端 → 后端的JSON（接收请求，校验提交的数据）
- UserResponse：登录**返回模型**，约束后端 → 前端的JSON（封装返回，控制向外输出哪些字段）

### Pydantic 库

Pydantic 是 Python 的**数据校验 + 数据格式化库**，FastAPI 默认配套使用，是 FastAPI 实现参数校验的核心依赖。

✅ 核心作用两点：
1. **校验数据**：检查数据类型、是否缺失。比如 LoginRequest 要求 username 是字符串、必填；前端传数字、漏传字段，直接自动报错，不用自己写一堆 if 判断。
2. **转换包装数据**：像user.py里面的UserResponse，把数据库查出来对象，自动转换成标准 JSON，交给前端 Vue；同时控制哪些字段对外暴露，并隐藏敏感信息（比如密码）。

# 7、创建 API 接口
api/auth.py
```python
from fastapi import APIRouter, Depends
from app.schemas.auth import LoginRequest
from sqlalchemy.orm import Session
from app.database import get_db
from app.models.user import User
from app.schemas.user import UserResponse

router = APIRouter(prefix="/api/auth", tags=["权限验证"])

@router.post("/login")
def login(data: LoginRequest, db: Session = Depends(get_db)):
    user = db.query(User).filter(User.username == data.username).first()

    # 判断账号和密码是否正确
    if not user or user.password != data.password:
        return {"code": 400, "message": "账号或密码错误"}
    return {
        "code": 200,
        "message": "操作成功",
        "data": UserResponse.model_validate(user),
    }
```

**1、导入部分逐行拆解**

1. `from fastapi import APIRouter, Depends` 导入路由对象、依赖注入工具。`APIRouter`用来拆分接口路由；`Depends`用来注入数据库会话。
2. `from app.schemas.auth import LoginRequest` 导入**入参模型**，校验前端传过来的账号密码JSON。
3. `from sqlalchemy.orm import Session` SQLAlchemy的数据库会话类型，用来操作数据库。
4. `from app.database import get_db` 导入获取数据库连接的依赖函数。
5. `from app.models.user import User` 导入数据库ORM模型（数据库user表映射对象）。
6. `from app.schemas.user import UserResponse` 导入**出参模型**，包装要返回给Vue的用户数据。
#### 依赖注入Depends

依赖注入（Depends），很多人说它是 FastAPI 的灵魂：
> 简单说：**把接口需要用到的资源（数据库会话、权限校验、配置）单独抽出去，需要的时候自动给你送进来，不用自己手动写重复代码**。

拿你现在代码看：

```python
def login(data: LoginRequest, db: Session = Depends(get_db)):
```
- `db` 就是注入进来的数据库会话。
- `get_db` 是一个函数，作用是创建、提供数据库连接

**通俗比喻**
你写登录接口、后面还要写用户查询接口、修改接口，**全都需要数据库连接**。
- 如果不使用依赖注入：每个接口里面都要重复写：打开数据库、用完关闭数据库，大量重复代码。 
- 依赖注入：单独写好 `get_db` 这个 “供应工具”。哪个接口需要数据库，写上 `Depends(get_db)`，它就自动把数据库会话送过来给这个接口用，接口用完自动回收

# 9、开发后端 JWT 用户认证

 来自 06开发后端 JWT 用户认证
## 为什么要做用户认证/接口保护

>**保护私有接口，做身份校验，防止陌生人随意操作他人数据**
>**减少密码传输、减少数据库查询**

**情景分析**：
- 我们正在开发智能实验室预约系统。系统里有获取个人信息、预约实验室、查看我的预约记录这类接口，这些接口操作的是用户的私有数据。**如果接口不加任何校验（裸奔），任何人打开 Apipost 直接发请求，就可以随意查看、修改别人的预约和个人信息，数据完全不安全。**
- 同时 HTTP 协议是无状态的，每一次请求都是独立的，**服务器不会自动记住用户已经登录过**。 如果想要限制陌生人访问，笨办法就是每次访问私有接口都带上账号密码，后端反复查询数据库比对密码；
- 但是这个方案**密码多次在网络传输，风险高**，还会**频繁查询数据库，性能差**

所以，我们需要**保护私有接口，做身份校验，防止陌生人随意操作他人数据**，这么做同时还能顺带**减少密码传输、减少数据库查询**

**解决方法：** 
>使用 **JWT + bcrypt** 改造登录流程，实现登录**鉴权**
1. 用户提交账号密码登录，后端从数据库查询用户，用 bcrypt 校验加密密码；
2. 校验通过，生成 JWT 令牌（Token 通行证）返回给前端；
3. 前端保存 Token，之后访问需要保护的私有接口时，在请求头带上这个 Token；
4. 后端通过依赖函数解析、校验 Token，确认是合法登录用户才放行接口；
5. 登录接口、注册接口保持公开，不需要 Token。

**知识点补充**
### 认证/鉴权/Token/JWT/bcrypt
1. **用户认证** 就是校验访问接口的人是谁，确认对方是系统里已经注册登录的合法用户。在本项目里，用来区分：是登录的本人，还是匿名陌生人。

2. **鉴权（新增）** 简单说：**检查通行证是否有效，判断能不能放行本次请求的这个动作，就叫鉴权**。 在我们代码里，`get_current_user` 这个依赖函数，干的就是鉴权：取出 Token、解码校验、查用户、判断是否有效。

> 	区分
> 	认证：登录的时候，核对账号密码，证明 “你是谁”；
> 	鉴权：后续访问接口的时候，核对 Token 通行证，检查 “你有没有资格访问这个接口”

3. **Token（令牌 / 通行证）** 登录成功之后后端下发的一串字符串，相当于临时通行证
>账号密码只在登录的时候提交一次；后续访问私有接口，只传递 Token，不再传递账号密码。Token 带有过期时间，到期失效，需要重新登录获取新 Token

4. **JWT（JSON Web Token）** 是一种标准化的 Token 格式，用来在网络请求里传递身份信息
>分为头部、载荷、签名三部分：
- 头部：记录加密算法（本项目使用 HS256）
- 载荷：存放用户标识 user_id、过期时间`exp`（exp 是固定关键字段，用来控制有效期）
- 签名：用密钥加密生成，防止别人篡改 Token 里面的信息
> ⚠️ 注意：载荷里不要存放密码这类敏感隐私数据

5. **bcrypt** 密码加密工具。数据库不再保存明文密码，只保存加密后的密文；
>校验密码时，对比输入密码和数据库里的密文。就算数据库泄露，别人也无法直接拿到用户原始密码。

6. **HTTP 无状态** HTTP 每一次请求互相独立，请求结束之后服务器不会记住上一次是谁登录的。
>Token 就是用来弥补这个特点

7. 两种接口区分
- 公开接口：登录、注册接口，所有人都可以访问，不需要 Token
- 受保护接口：获取个人信息、预约实验室、查看预约记录，必须携带合法 Token 才能访问

## 配置 JWT 环境变量

```
JWT_SECRET_KEY=F2DtkACCejMl6FMnJWEbBBX2uldFIB4r0fPILvAltaf
JWT_EXPIRE_HOURS=24
JWT_ALGORITHM=HS256
```

1. **JWT_SECRET_KEY（密钥）
- 生成Token的时候，后端用这个密钥给Token打上“防伪印章”
- 校验Token的时候，后端拿同一个密钥检查印章是否真实

2. **JWT_EXPIRE_HOURS=24** 
- 代表Token有效期：**24小时**。 
- Token里面自带过期时间，到时间之后，就算Token本身没有被篡改，后端也会判定它失效，需要用户重新登录。 
- 目的：防止一张通行证永久有效，降低被盗用之后的风险。

3. **JWT_ALGORITHM=HS256** 
- 指定加密签名算法：HS256，是JWT最常用的对称加密算法。

```python
from datetime import datetime, timedelta
import jwt
from app.config import settings

def create_access_token(user_id: int) -> str:
    """创建JWT token"""
    expire = datetime.now() + timedelta(hours=settings.JWT_EXPIRE_HOURS)

    payload = {"user_id": user_id, "exp": expire}  # exp是固定key，不能写成别的

    return jwt.encode(
        payload, settings.JWT_SECRET_KEY, algorithm=settings.JWT_ALGORITHM
    )

def decode_access_token(token: str) -> dict:
    """解析jwt token"""
    return jwt.decode(
        token, settings.JWT_SECRET_KEY, algorithms=[settings.JWT_ALGORITHM]
    )
```

逐行拆解：
1. 导入部分
- `from datetime import datetime, timedelta`：时间工具，用来计算 Token 过期时间
- `import jwt`：pyjwt 库，提供编码、解码 JWT 的能力
- `from app.config import settings`：导入我们在 config.py 实例化好的 settings 对象，用来读取 JWT 的全套配置（密钥、算法、过期小时数）

2. `create_access_token(user_id: int)`：登录成功时调用，生成通行证 Token

- `timedelta(hours=settings.JWT_EXPIRE_HOURS)` timedelta 用来表示一段时间；时长取自 `settings.JWT_EXPIRE_HOURS`，这个值经过 config 读取自.env 文件，方便统一修改有效期
- `payload`：**载荷，存放Token需要携带的信息**
    - `user_id`：自定义内容，标记这个 token 归属哪个用户
    - `exp`：JWT 库识别的固定字段，pyjwt 自动校验这个时间，时间到就判定 token 失效
- `jwt.encode()`：传入载荷、密钥、加密算法，**生成 JWT 字符串**

1. `decode_access_token(token: str)`：
这个函数的作用就是**解析**：前端传过来一个token，后端怎么解析呢

- `jwt.decode` 做两件校验： 
>① 使用 `settings.JWT_SECRET_KEY` 校验签名，判断 Token 有没有被人篡改 
>② 自动校验 payload 里的`exp`过期时间，过期直接抛出异常
- 校验全部通过，返回 payload 字典，我们从中取出 user_id

> 注意坑：decode 的 algorithms 是列表格式 `[settings.JWT_ALGORITHM]`，是 pyjwt 库的固定要求，和 encode 写法不一样

**password.py**
```python
import bcrypt

def hash_password(password: str) -> str:
    """对密码加密"""
    return bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt()).decode("utf-8")

def verify_password(password: str, hashed_password: str) -> bool:
    """验证密码的有效性"""
    """  "123" -> "xxsdasdasdasfa"  """
    return bcrypt.checkpw(password.encode("utf-8"), hashed_password.encode("utf-8"))
```

- `import bcrypt`：bcrypt 加密库，专门做密码哈希加密

1. `hash_password(明文密码)`
    
    - `password.encode("utf-8")`：bcrypt 只接受 bytes 字节类型，所以需要将字符串转字节
    - `bcrypt.gensalt()`：自动生成盐值（salt）。盐是一串**随机**字符串，作用：相同密码每次加密出来的密文都不一样，防止彩虹表破解
    - `bcrypt.hashpw()`：把明文 + 盐，算出加密后的字节密文
    - `.decode("utf-8")`：把字节密文转回字符串，方便存入 MySQL 数据库
    
    > 返回值：加密后的密文，存到 user 表的 password 字段，**数据库绝不保存明文密码**
    
2. `verify_password(用户输入的明文密码, 数据库取出的密文密码)`
    - `bcrypt.checkpw()`：bcrypt 自带的比对函数
    - 内部逻辑：不用把密文解密回明文！bcrypt 是单向哈希，**不能解密**
    - 它会使用密文中自带的 salt，对输入的密码重新做一次加密运算，然后对比两次结果是否一致
    - 返回布尔值：匹配成功返回 True，失败返回 False


# 10、jwt 鉴权

```python
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer
from sqlalchemy.orm import Session

from app.database import get_db
from app.models.user import User
from app.utils.jwt import decode_access_token

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/auth/login")

def get_current_user(
    token: str = Depends(oauth2_scheme), db: Session = Depends(get_db)
) -> User:
    """JWT token 鉴权验证合法性"""
    try:
        payload = decode_access_token(token)
    except Exception:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED, detail="登录已失效，请重新登录"
        )
    # 获取到用户ID
    user_id = payload.get("user_id")
    if not user_id:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED, detail="无效的登录凭证"
        )
    # 从数据库根据用户ID查询用户信息
    user = db.query(User).filter(User.id == user_id).first()
    if user.status != 1:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED, detail="用户被禁用"
        )
    return user
```

### 消息的组成（请求头+请求体）
HTTP 请求 = 发给后端的一条消息。 
这条消息分成两块：**请求头（header）** + 请求体（body）
- 请求体：放业务数据，比如登录时的用户名、密码（就是 LoginRequest 接收的内容）
- **请求头：附加的、描述这条请求的附属信息**，比如身份凭证、请求类型、编码等，放在消息最前面。

`Authorization` 就是**请求头（header）**的一种

### OAuth2PasswordBearer

**情景：**
前端发出请求，需要进行认证，那这个时候我该如何获取token呢？

> OAuth2PasswordBearer 是 FastAPI 提供的安全工具

1. **核心作用** 配合 `Depends()`，自动从 `Authorization` 请求头提取 token。
2. **强制约定格式** 只识别：`Authorization: Bearer 空格 token`这一种格式
>（就像写作文，格式要求必须是标题，开头，正文，结尾，缺一不可）

- `Bearer`：固定标识，后面跟一个空格，再放 JWT 字符串
- 格式不对、缺少该请求头，直接抛出 401

3. **参数 tokenUrl**`tokenUrl="/api/auth/login"` 仅为提示地址，告诉前端去哪里获取 token；**不会自动请求、跳转登录接口**。
4. **边界** 它**只负责提取 token，不校验 token**


### 传token的方式
1. token 本身（那一串 JWT 字符串）**内容不变**，变的只是「怎么发给后端」，也就是传输方式。
2. 传 token 有很多种办法：
    - 方式 A：放请求头（当前方案， `OAuth2PasswordBearer` 只支持这个方式）
    - 方式 B：放 URL 参数 `/api/xxx?token=xxxx`
    - 方式 C：放到请求 body（json 里面带 token）
>你现在选了 `OAuth2PasswordBearer`，这个工具**只认方式 A**传输token：
>即
>		**请求头必须命名为 `Authorization`**
>		该请求头内部内容格式： `Authorization: Bearer 空格 token串`

流程如下：
```
GET /api/user/info

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

token: str=Depends(oauth2_scheme) 就会提取

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
↓ 
oauth2_scheme
↓ 
token = "eyJhbGciOiJIUzI1NiIs..."
```

**为什么要弄清楚这些问题**
1.  提前明确接口的调用规则：虽然暂时还没有写前端代码，但后端接口已经定下了传token的规则。后续写前端、或者测试接口（比如用Swagger、Apipost）的时候，我就知道：访问受保护接口必须带上 `Authorization: Bearer {token}` 请求头；格式不对就会返回401，避免到时候盲目排查

# 12、封装统一返回格式 Response
来自   07. 后端封装统一响应格式+全局异常处理
`common/response.py`

✅ **需求场景**

你现在登录接口里，是**手动手写字典返回**：`return {"code":200, "message":"xxx", "data":xxx}` 问题：(这些代码在api/auth.py)

1. 每个接口都要自己写一遍这个字典结构，容易写错 key（比如有时候写 msg，有时候写 message）
2. 有的接口返回格式不一样，前端对接要写多套解析逻辑
3. 错误返回、成功返回写法不统一，不方便全局管理

所以新增 `common/response.py`：**封装一套全项目统一的返回体工具类** 
以后所有接口（登录、获取用户信息、其他业务接口）统一用 `Response.success()` / `Response.error()`，保证成功、失败的 json 结构一模一样。

```python
from typing import Any
from pydantic import BaseModel

class Response(BaseModel):
    """统一封装的返回格式"""

    code: int
    message: str
    data: Any = None

    @classmethod
    def success(cls, message: str = "请求成功", data: Any = None):
        return cls(code=200, message=message, data=data)

    @classmethod
    def error(cls, code: int = 500, message: str = "请求失败"):
        return cls(code=code, message=message)
```

1. `from typing import Any`
	`Any` 代表任意类型。因为返回的 data 内容不固定：登录时返回 token + 用户信息、查列表返回数组，所以用 Any，表示 data 可以放任何数据。

2. `class Response(BaseModel)` 继承 Pydantic 的 BaseModel。 好处：
- 强制约束返回结构，不会不小心少写 code、message
- FastAPI return 这个对象时，自动变成前端能看懂的 JSON

3. success，请求成功，要返回data
4. error，请求失败，则不用返回data，但要返回错误代码

## 类方法再理解

**1、需求场景（我们为什么这里要用类方法）**

我们有一个模板类 `Response`（Pydantic模型），用来统一返回JSON结构，字段固定：`code、message、data`。 
每次返回成功响应，大部分情况 `code` 永远是 200，只有 `message` 和 `data` 在变。

如果不用快捷方法，每次都要手写：

```python
return Response(code=200, message="登录成功", data=xxx)
```

问题：

1. 重复写固定的 `code=200`，代码啰嗦
2. 有人写错code（写成201、202），返回格式乱掉

👉 我们想要：写一个快捷函数 `success()`，**直接帮我们带上固定的 code=200**，调用只需要传 message、data。 而且希望调用方式简单：`Response.success()`，**不用先新建一个 Response 对象**。 要实现这个能力，就需要 `@classmethod`。

**2、怎么做（代码）**

```python
@classmethod
def success(cls, message: str = "请求成功", data: Any = None):
    return cls(code=200, message=message, data=data)
```

调用：

```python
Response.success(message="登录成功", data=token_data)
```

**3、核心概念 & 细节原理**

（1）**什么是 `@classmethod`**

`@classmethod` 是Python的装饰器
我们已经知道装饰器作用：**不改原函数里面的代码，给函数增加额外能力**

所以`@classmethod`附加的能力是什么：
让这个函数绑定到**类本身**，在不修改函数内部代码的情况下，**给函数增加「作为类方法运行」的能力**`
同时自动帮我们做一件事：调用这个方法的时候，自动把「这个类」传入第一个参数 `cls`


加上 `@classmethod` 装饰器之后（没有改动 success 里面的代码）：
✅ 新增能力 1：调用方式变成 `类名.方法()`
✅ 新增能力 2：Python 自动把当前类传给第一个参数 `cls`
```python
# 1. 实例普通方法（self）：必须先造对象，才能调用
def normal_func(self):
    pass
# 使用
resp = Response(code=200, message="ok")
resp.normal_func()

# 2. 类方法（@classmethod, cls）：类直接调用，用来创建对象/处理类相关逻辑
@classmethod
def success(cls):
    return cls(code=200, message="ok")
# 使用
Response.success()
```
**这里可以在app/api/auth.py的改动体现明显**

（2）**第一个参数 `cls`**（固定约定，必须放第一个）

- `cls` = class 的缩写，代表**这个类本身**，本例里 `cls` 等价于 `Response`
- `cls(xxx)` 等价于 `Response(xxx)`，作用：按照这个类的模板，新建一个实例（对象）

> 注意区分两个容易混淆的参数：
> 
> - 实例普通方法第一个参数是 `self`：`self` 代表**已经造好的那个对象**
> - 类方法第一个参数是 `cls`：`cls` 代表**图纸/类本身**

（3）**执行流程，当你写 `Response.success(...)`**

1. Python找到类 `Response`，找到它身上绑定的类方法 `success`
2. 自动把 `Response` 传给参数 `cls`
3. 方法内部执行 `cls(code=200, ...)` → 创建一个 Response 实例
4. 把这个新建好的实例返回出去，交给FastAPI，最后转成JSON

## 自定义异常+全局异常处理

✅ **需求场景**
在我们项目之前的写法里，报错是手动写的：

```python
if not user or not verify_password(...):
    return Response.error(code=400, message="账号或密码错误")
```

这种写法有局限：

1. **return 只能返回给直接调用它的上层，深层函数传递错误非常麻烦** 
	如果在底层工具函数里面发现业务错误，return 只能传给上一层函数；每一层都要额外写 if 判断，一层一层把错误往上传递。层级一多代码冗余、很容易漏掉判断。

2. **原生各类异常的返回格式不统一** 
	FastAPI 原生 `HTTPException`、Pydantic 参数校验失败（RequestValidationError）、程序意外报错，它们默认返回的 JSON 结构、字段名称都不一样。前端要写多套解析逻辑，非常麻烦。

👉 我们想要做到：

1. 自己定义一种**业务报错（BusinessException）**，在代码任意地方，直接 `raise BusinessException(message="账号已禁用", code=403)` 抛出异常，不用一层层 return 传递错误信息
2. 不管是：我们自己抛的业务异常 / FastAPI 自带的 HTTPException / 参数校验异常 / 程序未知报错 全部拦截下来，**统一转换成我们这套 `{code, message, data}` 的返回格式**，给到前端
3. 前端永远只需要解析同一套 JSON 结构，不用区分是正常返回、手动 return 的错误、抛出异常带来的错误

> 一句话总结场景： 统一捕获各类异常，把所有报错的返回格式对齐我们的 Response 模板；并且支持在代码任意位置抛出业务错误。
> 
   这样还可以达到区分 “报错类型”，知道错哪了

- `return`：是正常返回结果，只传给紧挨着它的上一层，错误要手动层层传递、层层判断。层级深了非常麻烦。
- `raise 异常`：是中断当前流程的报错信号，自动向上冒泡，直达全局异常捕获器，中间代码不用管错误传递。

## `__init__`和`super()`再理解

```python
class BusinessException(Exception):
    """自定义的业务异常"""

    def __init__(self, message: str, code: int = 500):
        self.message = message
        self.code = code
        super().__init__(message)
```


**1. `__init__` 是什么**

`__init__` 叫**构造方法**。 当你 `类名(参数)` 创建对象的时候，Python 会自动调用 `__init__`。
作用：**给刚新建出来的这个实例，初始化、绑定属性**。

```python
# 执行这一句的时候，自动运行 __init__
exc = BusinessException(message="账号禁用", code=403)
```

**2. `super()` 是什么**

`super()`：拿到**父类**

`super().__init__(message)`
1. `super()` 得到【当前这个类 `BusinessException`】的父类，也就是 `Exception`
2. `().__init__(message)` 调用父类 `Exception` 的构造方法 `__init__`，把 `message` 传给它


✅ **需求场景：**
**3、我们为什么要改写父类 Exception 的 `__init__`**？

Python 原生自带的 `Exception`，里面只存错误提示文字（message），**没有 code 这个字段**。

我们现在项目需求： 抛出业务错误的时候，除了文字提示，还需要附带一个**自定义业务码 code**（400、403、500），后面异常处理器要读取 `exc.code` 组装返回体。

👉 原生 Exception 满足不了：它没有 code 属性。 所以我们继承 Exception，重写它的 `__init__`：
1. 保留原生异常原本需要的 message（交给父类处理）
2. **额外新增一个 self.code 属性**，存我们自己的业务码


```python
async def 处理器函数名(request: Request, exc: 要捕获的异常类型):

        status_code=HTTP状态码,
        content=Response.error(code=业务码, message="提示文字").model_dump(),
    )
```

统一规律：

1. 全部是 `async` 异步函数（FastAPI/Starlette 处理器要求）
2. 固定两个入参：
    - `request: Request`：本次 HTTP 请求对象（框架自动传进来，大部分时候我们不用主动使用它，但参数必须写上）
    - `exc: XxxException`：捕获到的异常实例，名字 exc 就是 exception 缩写，我们从这里读取错误信息
3. 返回 `JSONResponse`：专门用来返回 JSON 格式响应
4. `Response.error(...)`：调用我们之前写的统一返回模板，生成 Pydantic 对象
5. `.model_dump()`：把 Pydantic 模型转成 Python 字典，给到 JSONResponse

---


✅ 通用模板
```python

```

统一规律：

1. `async` 标记这是一个**异步函数**
>核心一句话：
不是因为我们现在代码里面有异步任务要跑，而是我们要用异常处理器，而它本身设计就是给 async 函数用的

2. 固定两个入参：
    - `request: Request`：本次 HTTP 请求对象，框架自动传入。多数场景我们不会主动使用它，但是参数必须写上，框架会自动填充。
    - `exc: XxxException`：捕获到的异常实例，我们从这个对象里读取错误信息

3. 返回 `JSONResponse`：专门用来向前端返回 JSON 格式响应。
4. `Response.error(...)`：调用我们写好的统一返回模板，生成 Pydantic 模型对象。
5. `.model_dump()`：把 Pydantic 模型转换成 Python 字典，JSONResponse 接收字典后转为 JSON 字符串发给前端。

# 14、后端配置跨域

来自 08. Vue封装axios并实现前后端接口联调
这里是这个章节的后端部分

```python
from starlette.middleware.cors import CORSMiddleware

origins = [
	"http://localhost:5173",
	"http://127.0.0.1:5173",
]

app.add_middleware(
	CORSMiddleware,
	allow_origins=origins,        # 允许的前端源，不要直接写 ["*"]
	allow_credentials=True,       # ✅ 关键：允许前端携带 Authorization token
	allow_methods=["*"],          # 允许所有请求方法 GET POST PUT DELETE OPTIONS
	allow_headers=["*"],          # 允许所有请求头（包含Authorization）
)
```

✅ **需求场景**

浏览器有**同源策略**这个安全规则： 如果前端页面地址、后端接口地址，**协议、域名、端口有任意一个不一样，就属于跨域**，浏览器会拦住前端发给后端的请求。

我们现在：
- Vue 前端：`http://127.0.0.1:5173`
- FastAPI 后端：`http://127.0.0.1:8000` 端口不一样 → 属于跨域。 
- 如果不做跨域配置，浏览器直接拦截请求，前端连登录接口都发不出去，后面的 token 鉴权、所有接口调用全部无法进行


📝**代码解析**

我们在后端添加 `CORSMiddleware`（跨域中间件），作用就是
后端告诉浏览器：**我信任这两个前端地址，允许它跨域访问我**。

1. `origins`：写清楚允许哪几个前端地址访问后端，这里是只放行我们本地的 5173
>不推荐直接写`["*"]`（`*`代表允许所有来源，而且`*`和`allow_credentials=True`不能同时生效，带 token 的请求会直接失败，这就是注释说不要写`*`的原因）

2. `allow_credentials=True`：重中之重！开启**允许前端携带凭证**，我们的 `Authorization: Bearer token` 身份凭证就是在这里放行，**不开这个，前端带的 token 会被浏览器丢掉，鉴权直接失效**

3. `allow_methods=["*"]`：允许前端使用 GET、POST、PUT、DELETE 等所有请求方式（  *  表示都可以）

4. `allow_headers=["*"]`：允许前端传递所有请求头，包含我们放 token 的`Authorization`请求头


# 15、上传文件

来自 10. 开发后端文件上传API接口

## 上传文件怎么操作

前面我们已经完成登录、注册、用户相关接口，现在系统需要支持**上传文件**（比如头像、预约附件、证明材料等）。

原生FastAPI如果不做封装，直接写上传逻辑会很零散：

- 没有统一限制文件大小，容易上传超大文件占满服务器磁盘
- 没有白名单校验后缀，用户可以上传exe、恶意脚本等危险文件
- 文件名直接用用户原始名称，会出现中文乱码、重名覆盖文件的问题
- 文件保存之后没办法直接通过浏览器地址访问图片/文档

本章目标： **封装一套统一的后端文件上传接口，实现完整安全校验 + 文件落盘存储 + 返回可直接访问的文件url**，配套挂载静态资源，前端拿到url就可以展示、提交给业务表单。

整条流程： 
```
前端选文件 → POST上传到 `/api/files/upload` 
↓ 
后端接口依次校验：文件名非空 → 后缀在允许列表 → 文件大小不超限 
↓ 
生成唯一不重复的磁盘文件名，防止重名覆盖 
↓ 
把文件写入uploads目录 
↓ 
返回成功，带上原始文件名、磁盘文件名、文件大小、访问地址`/uploads/xxx` 
↓ 
静态资源挂载，浏览器直接访问这个url就能打开文件
```


关键点：

1. 配置项统一管理：最大大小、允许后缀、上传目录，方便后期修改；
2. 安全优先：后缀白名单+大小限制，做基础防护；
3. 重命名策略：时间戳+uuid，解决重名冲突；
4. 挂载静态目录，让上传后的文件可以通过http地址访问，给前端使用

### pathlib的写法

```python
UPLOAD_DIR = BASE_DIR / "uploads"
UPLOAD_DIR.mkdir(parents=True, exist_ok=True)
```
这是 **pathlib（Python3.4+ 内置）** 的写法，是新版推荐的路径方案，和旧的 `os.path` 是两套东西

**1. `BASE_DIR / "uploads"` 斜杠拼接路径**

`pathlib.Path` 对象重载了 `/` 运算符，专门用来拼路径，替代旧写法：

- ✅ pathlib（现在这个）：`BASE_DIR / "uploads"`
- ❌ 旧 os.path 写法：`os.path.join(BASE_DIR, "uploads")`

优势： 跨平台自动适配 Windows `\` 和 Linux `/`，不用自己关心斜杠正反，可读性更强

> 注意：只有 `Path` 对象才能用 `/`，普通字符串不行

**2. `mkdir(parents=True, exist_ok=True)` 自动建文件夹**

等价的 os 老式写法：

```
import os
if not os.path.exists(upload_path):
    os.makedirs(upload_path)
```

参数拆开讲：

- `parents=True`：如果上级文件夹不存在，一并创建（比如 `a/b/uploads`，a、b 都没有，也会一次性建好）
- `exist_ok=True`：目录已经存在的时候，**不抛报错**；不加这个，第二次启动项目就会报「文件夹已存在」异常


**为什么这些代码要放到 config.py（配置文件）**
项目分层约定：
config 专门存放常量、路径、开关、限制这类配置； 
service 放业务逻辑、api 放路由接口，各司其职，代码清晰好维护。



## files.py

新建文件上传的 api 接口

```python
import os
import time
from pathlib import Path
import uuid
import shutil
from fastapi import APIRouter, File, UploadFile

from app.common.exceptions import BusinessException
from app.common.response import Response
from app.config import ALLOWED_EXTENSIONS, BASE_DIR, MAX_FILE_SIZE, UPLOAD_DIR

router = APIRouter(prefix="/files", tags=["文件管理"])

@router.post("/upload")
def upload(file: UploadFile = File(...)):
    """文件上传的接口"""
    if not file.filename:
        raise BusinessException(message="文件名不能为空")

    # 原始的文件名  用户头像.jpg
    orignal_name = os.path.basename(file.filename)
    # 文件后缀 .jpg
    ext = Path(orignal_name).suffix.lower()
    if ext not in ALLOWED_EXTENSIONS:
        raise BusinessException(message=f"不自持的文件后缀：{ext}")
    # 文件大小校验
    if file.size and file.size > MAX_FILE_SIZE:
        raise BusinessException(
            message=f"文件不能超过 {MAX_FILE_SIZE // 1024 // 1024}MB"
        )
    # 设置唯一的文件名称   199323213213_ddadaqwerq.jpg
    disk_name = f"{int(time.time() * 1000)}_{uuid.uuid4().hex[:8]}{ext}"
    # 文件存储的实际路径
    save_path = UPLOAD_DIR / disk_name

    # 流式写文件
    with open(save_path, "wb") as f:
        shutil.copyfileobj(file.file, f)

    return Response.success(
        data={
            "original_name": orignal_name,
            "disk_name": disk_name,
            "size": file.size,
            "url": f"/uploads/{disk_name}",
        }
    )
```

✅ **需求分析**

前面已经在 config 配置好了上传目录、文件大小上限、允许后缀白名单。
现在需要开发**上传接口**，接收前端提交的文件，做安全校验之后保存到服务器，并且返回文件访问地址给前端。 要解决这些问题：

1. 防止上传危险类型文件、超大文件，保护服务器；
2. 同名文件上传互相覆盖；
3. 大文件一次性读入内存导致服务器内存溢出；
4. 上传完成后，前端能拿到 url 直接预览图片或者下载文档。

接口完整地址：`POST /api/files/upload`


### 后端API需求场景/API作用
这里来自 9. 开发用户注册功能 第3点

原来的后端代码把登录的业务判断逻辑（查用户、校验密码、生成 token 等）直接写在了 API 路由接口层里面。
这种写法不规范：接口层只应该负责接收参数、调用业务、返回统一响应，不该堆大量业务判断；

两件事：

1. **解耦分层，规范代码结构**：把登录的业务逻辑抽离出来，放到 `services/auth_service.py`（服务层）；API 层只保留很薄的代码：接收前端参数、拿到数据库会话、调用 service 里面的方法、返回统一格式响应。做到路由层和业务逻辑分离。
2. **新增注册能力**：增加注册的业务逻辑与注册接口。注册逻辑写在 service 里：先判断用户名是否已经存在，存在就抛出业务异常；不存在则对密码哈希加密，新建用户入库。API 层新增 `/auth/register` 路由，对外提供注册接口，配合前端注册页面完成注册功能。


📝重要知识点

1、**后端分层思想**：路由层（API） 和 Service 服务层分离（最核心）
原来：查询数据库、判断账号密码、校验状态、生成token全部写在接口函数
`@router.post`
改动后：
- **API层（路由）：只做“搬运”** 职责：接收请求参数、拿到db会话、调用service函数、包装返回统一响应。**不写业务判断、不写数据库查询**。 它就相当于快递前台，只负责收包裹、转交后台处理、最后把结果打包返回，不处理里面的业务审核。
- **Service层：存放业务逻辑** 所有业务规则：查重、密码校验、账号禁用判断、密码加密、新增用户入库，全部放这里

> 一句话：路由层负责http交互，service层封装业务逻辑

### 后端API模板

```python

from sqlalchemy.orm import Session

# 导入项目内部公共组件
from app.common.response import Response

# 导入 schema、service、依赖、模型

# 2. 创建路由实例，统一前缀 + 文档分组标签

# 3. 接口函数
@router.请求方式("/路径", summary="接口名称")

    # 入参1：请求体（Pydantic schema）
    data: XxxRequest,
    # 入参2：数据库会话依赖（绝大多数接口都要查库）
```

## app 挂载静态资源目录
### 静态资源挂载mount

✅ **需求场景**

我们把文件存到了服务器本地 `uploads` 文件夹里。 
浏览器默认**不能直接访问服务器本地磁盘文件**（安全限制，不然浏览器随便读电脑文件就危险了）。 
静态资源挂载，就是告诉 FastAPI：

> 有一个文件夹 `uploads`，里面的图片、文件，是可以直接用网址访问的，交给框架帮我托管。

<br>

📝 **通俗类比（快递驿站延续）**

之前： 后端驿站收到快递（文件），放到仓库 `uploads` 柜子里，**但是没有对外取件窗口**，前端拿不到。

- 挂载静态资源 = 给这个仓库开一个对外窗口 `/uploads/` 
- 规则： 网址 `http://127.0.0.1:8000/uploads/xxx.jpg` → 框架自动去后端项目里的 `uploads/xxx.jpg` 文件拿内容，返回给浏览器。

<br>

**对比接口和静态挂载**
- router 接口 = **人工窗口**，来人了才接待，还要判断业务、查数据库 
- mount 静态挂载 = **自助取件柜**，提前装好，只要输入正确编号（url），系统自动拿文件返回，不需要业务员（函数）

<br>

**对应关系**(重点)
- 磁盘真实位置：`uploads/1769991234_abc12345.jpg`
- 浏览器访问地址：`http://127.0.0.1:8000/uploads/1769991234_abc12345.jpg`

<br>

```python
from fastapi.staticfiles import StaticFiles

from app.config import UPLOAD_DIR

# 挂载静态资源：/uploads/xxx.jpg → uploads/xxx.jpg
app.mount("/uploads", StaticFiles(directory=UPLOAD_DIR), name="uploads")
```

作用
提前告诉 FastAPI：以后只要看到 url 前缀 `/uploads/`，就去这个文件夹找文件
>相当于拿到了取件码，自动取件


## `api/__init__.py`

### 配置路由
Python 包（package） + FastAPI 路由模块化拆分、路由嵌套（路由挂载 include_router）

✅ **需求场景**

我们现在拆分了很多接口文件：auth.py、files.py、user.py。 如果每个路由文件里都自己写 `prefix="/api"`：

1. 重复代码很多，每新增一个接口都要重复写一遍前缀
2. 以后如果要改统一前缀（比如改成 `//v1/api`），要一个个改所有文件，维护麻烦
3. main.py 里面会堆一大堆 `include_router`，代码杂乱

**需求目标：** 把所有子路由统一收拢，**只写一次公共前缀 `/api`**，统一注册管理；让 main.py 清爽，新增接口只需要在汇总处登记一行即可。

> 实现方案：利用 `app/api/__init__.py` 作为路由汇总中心

<br>

- `api = APIRouter(prefix="/api")`：创建汇总路由，在这里一次性定义统一前缀
- `include_router`：把各个独立模块的路由挂载进来

<br>

main.py 只需要一行导入挂载：

```python
from app.api import api
app.include_router(api)
```

 **什么时候用这个方案？**

项目接口按模块拆分（登录、文件、用户等，分多个 py 文件），想要统一管理公共路由前缀的时候。

 **为什么放在 `api/__init__.py`？**
- 文件夹放 `__init__.py` → 这个文件夹变成 Python 包
- `from app.api import api`：导入包，本质就是执行 `__init__.py`，导出里面定义的变量（这里就是汇总路由对象）

### FastAPI 路由嵌套：`include_router()`

```python

from app.api.auth import router as auth_router
from app.api.user import router as user_router
from app.api.files import router as files_router
```

- 在父 router 统一设置 `prefix="/api"`，**一次性给所有子接口加上前缀**
- 好处：统一管理前缀、统一加标签、统一中间件

记住这个判断标准：

> 只要接口**需要约定入参格式 / 约定返回给前端的出参格式**，就来 schemas 新建对应的 Pydantic 模型。

细分 3 种触发场景：

1. **接收前端提交的数据（请求体）** 比如登录、注册、修改个人信息：前端 POST/PUT 发 JSON，你需要规定有哪些字段、字段是什么类型、哪些必填。对应 `LoginRequest`、`RegisterRequest`、`UserUpdateRequest` 这类 `xxxRequest`。
2. **返回数据给前端（响应体格式化）** 接口查库之后，不能直接把数据库的 model 对象丢出去：
    - 数据库模型字段很多，有时候不想全部返回（比如密码绝对不能返回）
    - 想固定返回字段、固定类型，前后端对齐
    - 自动在 Swagger 文档展示返回结构 对应 `UserResponse`、`LoginResponse`、`FileResponse` 这类 `xxxResponse`。
3. **嵌套返回结构** 像登录返回：`{token:xxx, user:{用户对象}}`，里面 user 复用已经写好的 `UserResponse`，就需要在 `LoginResponse` 里直接引入别的 Schema，就是你 auth.py 里的写法。

> 一句话记忆： 
> Request = 前端传给后端 ✅ 
> Response = 后端返回给前端 ✅

**（2）区分容易混淆的点**

- SQLAlchemy `models`：**映射数据库表**，代表数据库里有哪些列（包含密码、各种数据库字段）
- Pydantic `schemas`：**接口传输契约**，控制前后端之间收发哪些字段、校验规则（过滤敏感字段，比如密码不会放到 UserResponse）

### model_validate 与 model_dump 转换方法/model_config
（1）是什么：Pydantic v2 提供的两个**实例转换方法**
（2）需求情景：
我们有两种对象：
ORM 模型（models 里面的 User）：映射数据库表，里面包含数据库全部字段（例如 password 敏感字段）
Pydantic Schema（UserResponse）：接口对外输出的契约，规定前端能拿到哪些字段

需要把查出来的ORM对象安全转成接口返回结构：
model_validate 就是这座桥梁，实现 ORM → Schema 的转换。
> 注意：使用 model_validate 读取ORM属性，Schema必须配置 `model_config = ConfigDict(from_attributes=True)`

（3）二者区分
- `model_validate(外部对象)`：外部对象（ORM） → Schema 实例
  作用：读外部对象的数据，创建Schema
- `model_dump()`：Schema 实例 → Python 字典
  作用：把Schema拆开，转为普通字典
>因为Schema 对象不方便循环遍历；转成字典后，可以拿到键值对，批量动态给 ORM 对象赋值，实现局部更新


### 局部更新
（4）**为什么要局部更新（这才是用`model_dump()`的根本原因）**
 
 方案 1：
 **全量提交（不做局部更新）** 修改个人资料时，前端必须把用户**所有信息全部传上来**：name、email、phone、avatar 一个都不能少。 哪怕用户只改头像，也要把姓名、邮箱、手机号原样再发一遍。 后端收到之后，直接覆盖整条记录。
缺点非常明显：
1. 麻烦：前端表单每次提交，都要先去拉取一遍用户全部信息回填，少一个字段就会把数据库里原来的值清空（变成 null）。
2. 容易出 bug：如果拉取数据失败、漏传某个字段，数据库里原本存在的数据直接丢了。
3. 用户体验不好，逻辑笨重。

方案 2：
**局部更新（`model_dump()` + `exclude_none=True`）** 用户改哪个，前端就只传哪个字段。 比如只换头像 → 请求里只带 `avatar` 这一个字段。 后端拿到 `UserUpdateRequest`，用 `model_dump(exclude_none=True)`，**自动过滤掉所有没传、值为 None 的字段**。 循环只更新传过来的字段，没传的字段，数据库保持原样不动。

✅ 一句话总结局部更新的目的： **用户只提交需要修改的字段，未提交的字段保留数据库原有数据，不会被清空**


### Pydantic 数据转换两条链路
**前情提要**
 - 数据库**不接收字典**。
 - SQLAlchemy ORM 是靠 ORM 对象（`user = User(...)`）和数据库打交道，不是字典。
 - 存入数据库不需要把 schema 转字典


 **链路 A（查询，后端返回给前端，用 model_validate）**
数据库 → SQLAlchemy ORM 对象 → `model_validate()` → Response Schema 实例

> 这里很多时候**甚至不需要 model_dump**！ 因为你的统一响应工具 `Response.success()` 内部会自动处理，把 Schema 转成 json 返回前端。 
> 
> 👉 对应：查用户信息 `get_user_info`

**链路 B（前端提交，后端更新数据库，用 model_dump）**

前端 json → Request Schema 实例（UserUpdateRequest） → `model_dump()` → 字典 → 循环给 ORM 对象赋值 → commit 入库 

>👉 对应：修改个人信息 `update_user_info`

**一句话区分记忆**
`model_validate`：ORM → Schema（查完数据，包装对外输出）
`model_dump`：Schema → 字典（拿到前端提交的数据，拆出来方便批量处理）

1. 简单函数、临时辅助函数，逻辑很短，一眼就能看懂返回值

## （1）后端：写 service 业务逻辑
`services/user_service.py` 追加：

```python
from operator import or_
from sqlalchemy.orm import Session
from app.common.response import PageResponse
from app.schemas.user import UserResponse,

def get_user_page_list(
    db: Session, page: int, page_size: int, keywords: str | None = None
):
    # select * from user where username like '%张%' or name like '%张%';
    query = db.query(User)
    if keywords:
        query = query.filter(
            or_(User.username.ilike(f"%{keywords}%"), User.name.ilike(f"%{keywords}%"))
        )
    total = query.count()
    items = (
        query.order_by(User.id.desc())
        .offset((page - 1) * page_size)
        .limit(page_size)
        .all()
    )
    return PageResponse(
        list=[UserResponse.model_validate(item) for item in items], total=total
    )
```

**1、函数入参部分**

```python
def get_user_page_list(
    db: Session, 
    page: int, 
    page_size: int, 
    keywords: str | None = None
):
```

- `db: Session`：数据库会话，相当于拿到数据库的连接，所有查询都靠它
- `page`：**当前第几页**，比如 page=1 是第一页
- `page_size`：**一页展示多少条数据**，比如 page_size=10，一页10个用户
- `keywords: str | None = None`：搜索关键词，不传就是 `None`，代表不搜索、查全部用户
<br>

**2、构建基础查询对象**

```python
query = db.query(User)
```

- 等价 SQL：`SELECT * FROM user`
- ⚠️ 注意：**现在还没有去数据库查！只是把查询条件组装起来**，SQLAlchemy 是惰性查询，调用 `.all()` / `.count()` 才真正发SQL给数据库。
<br>

**3、关键词搜索逻辑**

```python
if keywords:
    query = query.filter(
        or_(User.username.ilike(f"%{keywords}%"), User.name.ilike(f"%{keywords}%"))
    )
```

- `if keywords`：有传搜索词才走过滤；关键词为空，这一段直接跳过，查全部用户
- `or_()`：或者，二选一满足就行（要先 `from operator import or_` 导入）
- `ilike`：模糊匹配，**不区分大小写**（like区分大小写）
- `f"%{keywords}%"`：SQL模糊查询语法，`%` 代表任意字符
    - 举例：keywords = "张" → `%张%`，只要用户名或者姓名里面包含“张”就匹配上
- 翻译SQL：`where username like '%张%' OR name like '%张%'`

> 重点：`query = query.filter(...)` 是**给原来的query追加条件**，不是覆盖

<br>

**4、统计总条数**

```python
total = query.count()
```

- 执行SQL：`select count(*) from user where ...`
- 拿到满足条件的**全部用户总数**，前端分页组件需要这个数字（一共有多少条、一共多少页）
<br>

**5、分页 + 排序，拿到当前页数据**

```python
items = (
    query.order_by(User.id.desc())
    .offset((page - 1) * page_size)
    .limit(page_size)
    .all()
)
```

一行一行拆开：

1. `order_by(User.id.desc())`：按id**倒序**，新注册的用户排在最前面（id越大越新）
2. `offset((page - 1) * page_size)`：跳过前面多少条
    - 例子：page=2，page_size=10 → (2-1)*10 = 10 → 跳过前10条
3. `limit(page_size)`：最多取几条，这里取10条
4. `.all()`：**真正访问数据库**，把查到的多条用户记录，放到列表 items 里面
<br>

**6、包装分页返回结果**

```python
return PageResponse(
    list=[UserResponse.model_validate(item) for item in items], 
    total=total
)
```

- `[UserResponse.model_validate(item) for item in items]` 列表推导式
    - 循环每一条数据库查出来的 user 对象
    - `model_validate`：把数据库模型 `User` → 转为我们定义的响应Schema `UserResponse`
    - 作用：过滤掉敏感字段！比如密码password，不会返回给前端
- `PageResponse`：我们项目统一的分页返回结构体，固定返回：
    - list：当前页的数据列表
    - total：总数据条数

---

7、**完整执行顺序**

1. 拿到数据库连接 db
2. 先搭基础查询：查User表
3. 如果有搜索关键词，加上 OR 模糊查询条件
4. count 算出符合条件一共有多少条（total）
5. 加上排序、分页偏移、条数限制
6. 去数据库查出当前页的数据 items
7. 循环转换模型，剔除敏感字段，封装成统一分页对象返回

<br>

8、**两个高频坑点**

1. `query` 只是查询构造器，**没调用 .count() / .all() 之前不会查库**
2. `or_` 必须导入，不能直接写 or；SQLAlchemy里面 `or` 和 `or_` 不是一回事


## （2）后端：定义入参 Schema

`common/response.py` 追加：

```python
class PageResponse(BaseModel):
    """分页的返回结果"""

    list: Any = []
    total: int = 0
```

1. `list: Any = []`
- `list`：字段名，存放当前页的数据列表
- `Any`：任意类型，里面可以放用户、实验室、文件等任意实体对象
- `= []`：默认空列表，查不到数据的时候不会报错

<br>

2. `total: int = 0`
- `total`：符合筛选条件的数据总条数（前端分页控件需要，用来算总页数：总条数 / 每页大小）
- `int`：整数类型
- `= 0`：默认 0 条

### 为什么放在 common？

**📌重点：为什么不放 schemas 文件夹，放在 common**

先区分两个文件夹的定位（这个是面试可以直接说的）

`schemas/`：**业务专属模型**，和某个业务强绑定 
举例：`schemas/user.py`、`schemas/lab.py` 里面放：`UserCreate`、`UserResponse`
特点：只给这一个业务模块用，字段是这个业务独有的（用户名、邮箱、设备编号等）


`common/`：**全局通用、跨业务复用的公共组件**
不属于某一个业务 里面放：统一返回体、异常类、常量、工具函数、分页外壳

所以：**放在 common 的理由：**

1、**PageResponse 不绑定任何业务** 
它里面只有 `list` 和 `total` 两个字段，查用户能用、查实验室能用、查预约记录也能用。 不属于用户模块，也不属于实验室模块，不属于任何单一业务，所以不属于 schemas

2、schemas 存放的是**实体内容模型**，而`PageResponse`是外层包装壳
举个例子：
- `UserResponse`（schemas/user.py）：规定**一条用户长什么样**（id、username、avatar…）
- `PageResponse`（common/response.py）：规定**一堆数据分页后外层怎么打包**，里面装什么东西它不关心

你这个项目里 `common/response.py` 一般还会放基础的 `Response`（code、message、data）全局返回模板
`Response`和`PageResponse`才是一类的，都是一种通用返回结构，所以都应该放在`common`里面，统一维护，风格一致

<br>

**一句话总结：**
`schemas` 放各个业务自己的入参、响应模型，和业务强耦合； 
PageResponse 只是通用分页外壳，只有 list 和 total，所有业务列表接口都可以复用，不属于某一个业务，属于项目公共基础设施，所以放在 common，和统一返回响应放在一起

```python
from app.dependencies.auth import get_current_admin

@router.get("/list")
def get_user_list(

```

### 后端的路由接口再理解

路由接口（api 层，也叫 控制器 / 接口层）定位：**只做「接收、校验、鉴权、转发、包装返回」，不写复杂业务逻辑**

1. 接收前端 GET 请求 `/api/user/list`
2. FastAPI 自动接收 url 查询参数：`page`、`page_size`、`keywords`，并且自动做**基础类型校验**（比如：page 必须是数字）

3. 执行 `Depends` 依赖：
    - `Depends(get_current_admin)`：鉴权 + 角色权限校验（必须是管理员）**
    - `Depends(get_db)`：拿到数据库会话 db
4. **把参数交给 service**：调用 `user_service.get_user_page_list`，真正的查询、分页、搜索逻辑都在 service 里面

> 路由本身不写查询 SQL、不写判断逻辑，只调用 service ✔

5. 拿到 service 返回的 `PageResponse` 对象，套上项目统一的成功返回体 `Response.success()` 返回给前端

## （2）后端：写 service 业务逻辑
```python
def update_user(db: Session, user_id: int, data: UserUpdateRequest):
    """更新用户"""
    user = db.query(User).filter(User.id == user_id).first()
    if not user:
        raise BusinessException(message="用户不存在")
    payload = data.model_dump(exclude_none=True)
    for filed, value in payload.items():
        setattr(user, filed, value)
    db.commit()
    db.refresh(user)
    return UserResponse.model_validate(user)
```

1、
```python
user = db.query(User).filter(User.id == user_id).first()
if not user:
    raise BusinessException(message="用户不存在")
```
`db.query(模型).filter(条件).first()`：查询第一条，找不到返回 `None`


2、
```python
payload = data.model_dump(exclude_none=True)
for filed, value in payload.items():
    setattr(user, filed, value)
```

### payload载荷
payload = 有效载荷，在这里代表：**前端本次真正提交、想要修改的字段字典**
怎么实现的：`model_dump(exclude_none=True)`实现的**局部更新**
（这里详见 `11. 开发用户修改个人信息功能--2、用户 Service--局部更新`）

### setattr
**setattr 原生 Python 语法**
```python
setattr(对象, 属性名字符串, 值)
```

举个简单小 demo 理解：

```python
class Demo:
    name = "原始名字"

d = Demo()
setattr(d, "name", "张三")
print(d.name) # 张三
```

<br>

这里我们的**需求是赋值**
写法 1：硬编码**直接赋值**（`user.xxx = 值`）
```python
if data.name is not None:
    user.name = data.name
if data.email is not None:
    user.email = data.email
if data.role is not None:
    user.role = data.role
# 每新增一个可更新字段，就必须新增一段if判断
```

特点： 属性名是写死在代码里的（`name` / `email` / `role`）。 
在写代码的时候，就已经固定了要更新哪些字段；
字段越多，if 判断就越多，维护麻烦

<br>

写法 2：`setattr` + 循环（`for xx , xx in payload.item()`)实现**动态赋值**
1. `payload` 是字典，key 是**本次要更新的字段名字符串**，value 是新值；
2. `field` 是循环拿到的变量，里面存着字段名（可能是`"name"`，也可能是`"status"`，由前端传参决定）；
3. `setattr(user, field, value)`：把变量 `field` 里面存的字符串，当做属性名去赋值

总之
>setattr 是无脑按字典 key 赋值！ 
>只要 payload 里面有的 key，都会赋值给 user 对象

### Post不加路径参数
**新增用户为什么用 POST，并且 @router.post ("") 不加路径参数**

（1）`/api/user` 代表【用户这个资源集合】（全部用户的列表）
- POST 的语义：**往这个集合里面新增一条数据** 
- 新建用户的时候，这条用户记录还没存入数据库，数据库还没有给它分配自增 id，它本身不存在 id， 所以没法在 url 里写 id
>这个是后端路由接口，作用就是接收前端传过来的数据（账号、密码、姓名等新增信息放在请求体 JSON 里），依次做接收、参数校验、权限鉴权、调用业务逻辑，最后包装结果返回给前端
>
>api + prefix="/user" +"/me"会组成一个**完整 URL 地址**，是前端访问后端的时候，参考的地址
>这里不写第三部分，即`post("")`,意思是就在/api/user这里新增用户

<br>

（2）举个生活化类比：
`/api/user` 相当于一个文件夹，文件夹名字叫【所有用户】 
POST 就是往这个文件夹里**新建一个文件**，新建之前这个文件没有编号，编号是保存成功之后系统才分配的

而修改、删除（PUT、DELETE），是去修改 / 删掉**已经存在的某一条用户**。
这条记录早就入库，有唯一 id 了，所以要在 url 带上 `/{user_id}`，告诉后端：你要操作的是哪一个用户

>**一句话总结**
>	POST 新增：目标是【用户集合】，资源还没有 id，不带路径 id； 
>	PUT/DELETE 修改删除：目标是【某一个已存在用户】，用 url 里的 id 定位它。

### `/list`和`/{user_id}`的核心区别

**① `/list` 👉 固定字符串路径**

```python
@router.get("/list")
```

拼接完整路径：`/api/user/list`

- `/list` 是**固定字面常量**，写死的文本
- 作用：查询用户列表，批量查询，不是操作某一个特定用户

 **② `/{user_id}` 👉 路径参数（动态占位符）**

```python
@router.put("/{user_id}")
```

`{user_id}` 是 FastAPI 的**动态路径变量**，可以匹配任意数字，例如： `/api/user/1`、`/api/user/2`、`/api/user/100`

- 用来定位**单独某一条用户记录**
- `user_id` 会自动解析，传给函数里的 `user_id: int` 参数

<br>

**重点：为什么 `/{user_id}` 要写在 `/list`、`/info`、`/password` 的后面？**（高频考点）

>FastAPI 匹配路由的规则：**从上往下一行一行比对，碰到第一个匹配成功的路由，就直接执行，不再往下看**

`/{user_id}` 是动态占位符，它可以匹配 `/api/user/后面随便写的内容`，而且你定义了 `user_id: int`，要求匹配到的内容必须是数字。

❌ 如果顺序写反（错误示范）

```python
@router.get("/{user_id}")   # 动态路由放前面
@router.get("/list")        # 固定路由放后面
```

当访问 `/api/user/list`： FastAPI 从上开始匹配，先看到 `/{user_id}` 这条规则，它会把字符串 `list` 当成 user_id 的值，然后尝试把文本 `list` 转成整数，转失败 → 直接报错。

✅ 正确顺序

```python
@router.get("/list")        # 固定文字路由放上面
@router.get("/{user_id}")   # 动态id路由放下面
```

访问 `/api/user/list`： 优先匹配到上面的 `/list`，正常执行列表接口，不会走到下面动态路由。 只有访问 `/api/user/2`、`/api/user/5` 这种数字的时候，才会匹配到下面的 `/{user_id}`。

> **一句话总结**
> `/list`、`/info` 是写死的固定文字路径，要优先匹配；
>  `/{user_id}` 属于 “兜底匹配”，放后面，只有前面固定路径全都不匹配的时候，才轮到它。

## （2）Schema

### DTO
全称：**Data Transfer Object，数据传输对象**
一句话：**专门用来在层与层之间搬运数据的盒子(就是schema)，只装字段，不写业务逻辑**

 在你 FastAPI + SQLAlchemy 代码里： 
> `EquipmentResponse`、`LabResponse` 就是 DTO（返回给前端的响应 DTO）
>  还有 `EquipmentCreate`、`EquipmentUpdate` 这种接收前端提交参数的，也是 DTO

DTO 分两类（后端常规叫法）
1. **入参 DTO（请求 DTO）**：前端传给后端 例：`EquipmentCreate`，接收新增设备的 name、lab_id，做参数校验
2. **出参 DTO（响应 DTO）**：后端返回给前端 例：`EquipmentResponse`，给前端展示列表，**可以额外拼接关联字段（lab_name）**


### Response和Request

**需求情景 / 使用动机**
 Schema 有两大职责：
1. **Request 类（XXCreateRequest / XXUpdateRequest）**：约定前端传给后端的字段、定义入参的基础校验规则，**校验前端发过来的数据**。
2. **Response 类（XXResponse）**：约定后端返回给前端有哪些字段、返回数据的类型；即**规范、过滤后端给前端的数据**
 
**所以拆分三类Schema**：
  - XXXCreateRequest：新增【请求入参】，校验前端新增提交的数据 
  - XXXUpdateRequest：修改【请求入参】，校验前端修改提交的数据
  - XXXResponse：【响应出参】，把数据库查询出来的ORM对象，过滤、整理之后返回给前端 
  
  目的：**入参校验 和 返回输出分开管控**，一套模型不混用，权限、字段可控
   > 这是 FastAPI + Pydantic 项目标准分层写法，user、lab、auth、file 全部统一这个规范
   
<br>

**综合对比**
**1. DTO（Data Transfer Object）**
是**抽象概念** 定义：层之间传输数据的对象，只是一个统称，不区分方向。
> 只要是用来传输数据的盒子，都叫 DTO。

<br>

**2. Request / Response（Pydantic Schema）**
是**按传输方向划分的落地产物** 在 FastAPI + Pydantic 项目里，我们用 `BaseModel` 写出来的这些类，就是 DTO 的实现：

- 前端 → 后端：**Request DTO（入参 Schema）**
>`EquipmentCreateRequest / EquipmentUpdateRequest`
- 后端 → 前端：**Response DTO（出参 Schema）** 
>`EquipmentResponse / LabResponse`

### 分页逻辑/分页模板
对应代码：`get_lab_page_list` 里面分页查询
```python
total = query.count()
items = (
    query.order_by(Lab.id.desc())
    .offset((page - 1) * page_size)
    .limit(page_size)
    .all()
)
```

这里是数据库层面 offset + limit 分页，是正确写法
反面写法（源码里没有，是错误示范）：先 all () 查出全部，再列表切片


 **offset + limit 分页执行流程**
1. 先在数据库里执行 `ORDER BY id DESC` 排序
2. `offset`：跳过前面多少条数据 比如 `page=2，page_size=10` → `offset = (2-1)*10 = 10`，跳过前 10 条
3. `limit`：只取后面 10 条
4. 数据库只返回这 10 条给 Python 后端，不是把整张表数据全部发过来

✅ 优点：
- 数据量大的时候，内存占用很小
- 数据库本身做筛选截取，是标准方案 
> 适用：绝大多数后台列表（用户列表、实验室列表、订单列表）

**total的解读**
经过关键词搜索后，会出现一些数据，这些数据有多少呢，我们使用`total`来统计

`items` 只是拿到**当前这一页**的几条数据
>假如符合搜索条件的有26条数据，total = 26
>则第一页 10 条，第二页10条，第三页6条

>`total` 是给前端分页组件 `el-pagination` 使用：
>前端拿到 `total`、`page_size`，自动算出总页数，渲染页码、“共 xx 条” 文字。
>后端只负责把这个数字返回，**后端不渲染页码 UI**
<br>

**组装返回数据给前端**
```python
return PageResponse(
    list=[LabResponse.model_validate(item) for item in items],
    total=total,
)
```

```python
    db: Session,
    page: int = 1,
    page_size: int = 10,
    # 这里放你的筛选参数：keywords、status、lab_id 等
):
    # 1. 【兜底参数校验】防止前端传负数、0、超大page_size
    page = max(1, page)
    page_size = min(100, max(1, page_size))

    # 2. 基础查询（根据业务拼接 where 条件，关键词、状态、权限过滤都写在这里）
    query = db.query(ModelName)
    # 示例过滤：
    # if keywords:

    #     query = query.filter(...)
    # 权限过滤（预约/用户常用）
    # if current_user.role != "admin":
    #     query = query.filter(...)

    # 3. 统计满足条件的总条数（自动带上上面全部filter）
    total = query.count()

    # 4. 排序 + 分页截取（order_by 必须写在 offset、limit 前面！）
    items = (
        query.order_by(ModelName.id.desc())
        .offset((page - 1) * page_size)
        .limit(page_size)
        .all()

    data_list = [ModelResponse.model_validate(item) for item in items]

    return PageResponse(list=data_list, total=total)
```

**1. 需求情景 / 使用动机**

我们要让每个设备都关联一个实验室。
我们要做到两件事：

1. 不能给不存在的实验室添加设备；
2. 查设备的时候，可以直接拿到它所属实验室的名字，不用自己再写复杂 SQL语句来把两张表连起来

**2. 代码逐段解释**

> 关联相关代码提取：
```python
# 外键
lab_id: Mapped[int] = mapped_column(
    ForeignKey("labs.id"), comment="所属实验室", nullable=False
)
# ORM关联导航
lab: Mapped[Lab] = relationship()
```

✅ `ForeignKey("labs.id")` 
向数据库声明外键约束，底层由数据库做数据校验
大白话：告诉数据库，`lab_id` 必须去 `labs` 这张表里找对应的 id

- 数据库这边生效，表里真的有 `lab_id` 这一列，并设置为外键
- 数据库校验效果：
    - 如果你填一个不存在的实验室 id 去新增设备 → 数据库直接拒绝保存
    - 如果你想删掉一个还有设备挂着的实验室 → 默认删不掉，数据库阻止你
- SQLAlchemy 只是帮你把这条规则告诉数据库
- 我们写它的目的：避免出现 “设备归属一个根本不存在的实验室” 这种错误数据

<br>

✅ `lab: Mapped[Lab] = relationship()` 
作用：拿到设备对象后，可以直接通过 `.lab` 拿到对应的实验室整条数据

- 数据库表里看不到这个 `lab`，是ORM 提供的导航属性
- 效果：当你拿到一条设备数据后，可以直接写 `equipment.lab.name`，拿到这个设备所属实验室的名字
- 我们写它的目的：
	- SQLAlchemy 帮你自动去关联查表拿实验室信息
	- 简化代码查询，不用手写 JOIN进行连表查询
- 加载特性：默认懒加载，不访问 `.lab` 就不会额外发起查询

**3. 必要知识点**

1. `ForeignKey`：数据库层面的规则，实实在在存在于数据表
2. `relationship`：只在 Python 代码里生效，数据库没有这一列
3. 关系：多个设备属于同一个实验室（多对一）
4. 外键 设置属性`nullable=False`：新增设备必须选择实验室，不允许设备没有归属
5. 默认懒加载：你不写 `.lab`，它就不去查实验室；你访问 `.lab`，它才额外查一次数据库
6. 外键只是兜底保护，业务上我们还是要先在 service 里判断实验室是否存在，给前端友好提示

### nullable属性
核心一句话：**nullable 控制该字段是否允许为 NULL（空值）**
```python
nullable=False  → 不允许为空（NOT NULL），必填
nullable=True   → 允许为空（DEFAULT，默认值就是 True）
```

### 字段/主键和外键约束

❌ 我的理解：

> A 表的 id；B 表有一模一样的 id 字段，能靠它连 A 表，那 B 里这个字段就叫外键，在A哪里就叫主键

思维误区： 
- 字段 `lab_id` 本身，就只是一个存数字的普通列，它**天然不是外键**
- 是你给这个字段**挂上了外键约束**之后，它才变成 “外键字段”
- 字段是载体，约束是附加在它身上的规则，二者不能混为一谈

<br>

✅ 对照主键帮你对比，一下子就通：
- `labs.id`：只是一个存数字的列；给它加上**主键约束（PRIMARY KEY）** → 它成为主键字段，规则：不能重复、不能为空、唯一标识一行。
>那么，加上主键约束这个操作在哪呢？
>在`utils/database.py`
- `equipments.lab_id`：只是一个存数字的列；给它加上**外键约束（FOREIGN KEY）** → 它成为外键字段，规则：它的值必须在 labs 的主键里面存在。

👉 一句话： **字段是容器，主键 / 外键是贴在容器上的规则标签。** 
>我们口语经常偷懒，说 “这个字段是外键”，是简化说法
严格来说：这个字段**带有外键约束**

    - 更新：只限制同一个实验室内部不能重名 ✅ 两种修正方向（二选一，业务对齐）
    - 方案1（统一为：全局name唯一）：update改成和create一样，只判断name，去掉lab_id条件

❌ 误区2：update里的lab_id是原来的实验室id 
不是，代码里lab_id是取payload里面更新后的lab_id，支持“设备挪到别的实验室”场景下的校验。 
❌ 误区3：新增也需要加 `id != xxx`

1. 指定 equipment_id：预约这个实验室下面某一台设备
2. 不传 equipment_id：直接预约整个实验室（不绑定设备） 如果查到重叠预约，直接抛出异常，禁止重复预约


📝**代码解析**

```python
    # 实验室或者设备是否可预约的状态
    query = db.query(Reservation).filter(
        Reservation.lab_id == data.lab_id,
        Reservation.date == data.date,
        Reservation.status.in_([0, 1]),  # 0表示待审核  1已通过
        Reservation.start_time < data.end_time,
        Reservation.end_time > data.start_time,
    )
```

**前三条在进行匹配，后面两条在进行校验**
1. `Reservation.lab_id == data.lab_id`：锁定同一个实验室
2. `Reservation.date == data.date`：只看同一天的预约（日期是单独字段，时分是 start_time、end_time）
3. `Reservation.status.in_([0, 1])`：只拿【待审核、已通过】的预约，已拒绝、已取消（2、3）不用校验冲突
4. `Reservation.start_time < data.end_time` 和 `Reservation.end_time > data.start_time`：**时间段重叠判断核心条件** 
>现有预约的开始时间 ＜ 用户预约的结束时间 
>现有预约的结束时间 ＞ 用户预约的开始时间 
>满足这两条 = 两个时间段发生重叠
>
>	可以画时间轴，小的在左边，大的在右边


```python
    if data.equipment_id:
        query = query.filter(
            Reservation.equipment_id == data.equipment_id
        )  # 预约实验室设备
    else:
        query = query.filter(Reservation.equipment_id.is_(None))  # 只预约实验室
    res = query.first()
    if res:
        raise BusinessException(message="该时段已被别人预约")
```

1. if 分支：用户传了 equipment_id → 校验【该实验室下这台设备】的时段冲突
2. else 分支：equipment_id 为空 → 校验【整个实验室】的预约，只匹配预约实验室（equipment_id is null）的记录
3. `query.first()`：找到任意一条冲突记录就够了
4. if res：查到冲突，抛出业务异常，提示该时段已预约

### db.refresh()再理解

**问题情景**
这里预约新增 service结尾部分，add+commit 之后没有写 db.refresh ()
对比之前设备新增接口带 refresh
>什么时候需要 db.refresh ()

<br>

**原理**
db.refresh (对象)：执行一次 SELECT，把数据库最新数据（自增主键 id 等）同步到 Python 的 ORM 实例。 
commit 本身不会自动把数据库生成的 id 回填到本地对象。

<br>

**使用规则**

1. 需要 refresh：commit 之后，还要使用这个 ORM 实例（序列化 Response、拿 id 继续业务操作）
2. 不需要 refresh：commit 之后，函数流程结束，不再读取、使用这个实例，不需要拿到自增 id

<br>

**本案例原因**
预约提交完成后没有后续代码读取 resvervation_model，不需要序列化返回，因此可以省略 refresh。

<br>

**一句话浓缩**
refresh 按需使用，目的是回填数据库生成字段；
提交后不再使用该对象，就不用写 refresh。


### 关键字后面加下划线
SQLAlchemy 常用查询运算符速查表

> 核心前提：`== > < >= <= !=` 可以直接写，已经被ORM重载；
>  `is / in / and / or / not` 是Python原生关键字，**不能直接用**，要用ORM提供的带下划线后缀版本

|写法|翻译成SQL|说明|错误写法|
|---|---|---|---|
|col.is_(None)|`IS NULL`|判断为空|`col == None`|
|col.is_not(None)|`IS NOT NULL`|判断非空|`col != None`|
|col.in_([1,2,3])|`IN (1,2,3)`|在集合内|`col in [1,2,3]`|
|col.not_in([1,2,3])|`NOT IN (1,2,3)`|不在集合内|`col not in [1,2,3]`|
|and_(条件1,条件2)|`条件1 AND 条件2`|多个条件同时满足|`条件1 and 条件2`|
|or_(条件1,条件2)|`条件1 OR 条件2`|满足任意一个|`条件1 or 条件2`|
|not_(条件)|`NOT 条件`|取反|`not 条件`|

**代码示例**
```python
# and_ 多条件同时满足
db.query(User).filter(
    and_(
        User.role == "admin",
        User.status == 1
    )
)

# or_ 满足其一
db.query(User).filter(
    or_(
        User.role == "admin",
        User.role == "teacher"
    )
)

# not_ 取反：不是管理员
db.query(User).filter(
    not_(User.role == "admin")
)

# 组合混用
db.query(User).filter(
    and_(
        User.status == 1,
        or_(
            User.role.in_(["admin", "teacher"]),
            User.phone.is_(None)
        )
    )
)
```

<br>

**总结**
就是相当于用python完成SQL语句的功能，有些关键字要加下划线


✅ 什么时候要带下划线（核心原因：和 Python 原生关键字冲突，没法直接重载）
`is_`、`in_`、`and_`、`or_`、`not_`
- `is、in、and、or、not` 是 Python 保留关键字，你直接写，Python 会当场执行布尔判断，不会交给 SQLAlchemy 生成 SQL。
- 所以库里面改名，末尾加下划线区分。

<br>

✅ 不用下划线，可以直接写的（运算符被 ORM 重载了）
`==`、`>`、`<`、`>=`、`<=`、`!=`

<br>

📌 补充
还有一些是方法，不是因为关键字冲突：
- `like()`、`between()` 这类，本身就不是 Python 关键字，**不加下划线**

## 1、后台定时任务
**自动过期【待审核】预约（status=0）**


✅ 需求情景 
1. 就是要去处理**时间已经过期、但状态仍然是待审核 status=0的预约**
2. 已经通过（status=1）的预约：到时间正常使用，过期后不需要自动取消，不需要释放时段，到期自动失效、不拦截新预约。
3. 选择方案：后端独立后台定时扫描任务，项目启动就自动跑，每 60 秒检查一次，把**已经超时、还没审核的预约自动改成【已取消 status=3】，释放时段**

```python
import asyncio
from datetime import datetime
from app.database import SessionLocal

# 同步函数：执行过期判断、更新数据库
def expire_pending_reservations():
    db = SessionLocal()  # 新建一个独立数据库会话，和接口请求的db分开
    try:
        now = datetime.now()
        today = now.strftime("%Y-%m-%d")
        now_time = now.strftime("%H:%M")
        # 只查询：状态=0 待审核的预约
        items = db.query(Reservation).filter(Reservation.status == 0).all()
        changed = False
        for item in items:
            # 两种过期条件满足其一：
            # 1. 预约日期 早于今天 → 已经是昨天或者更早的预约，还没审核
            # 2. 预约就是今天，并且预约结束时间 <= 当前时间 → 预约时段已经过完了
            if item.date < today or (item.date == today and item.end_time <= now_time):
                item.status = 3  # 修改为 已取消
                changed = True
        # 只要有数据被修改，才提交事务，避免空提交
        if changed:
            db.commit()
    finally:
        db.close() # 不管报错与否，会话一定关闭，防止数据库连接泄露

# 异步循环任务：持续定时调度
async def run_expire_scan():
    while True:
        expire_pending_reservations()
        await asyncio.sleep(60) # 休眠60秒，每隔1分钟扫描一次
```


过期扫描函数

### （1）形参和无参的再理解
#### 这个东西要不要做成参数？

✅ 1、这个东西，是不是每次调用都不一样？
- 是 → 做成参数（文件路径、db、id、page、status）
- 固定不变、全局统一 → 放函数内部

✅ 2、我希望这个函数能不能复用在不同环境？
- 想复用：不同调用方可以传入不同 db / 不同路径 → 做成参数
- 这个功能就是专属当前场景、只在这里跑（过期扫描）→ 内部自建

✅ 3、资源谁方便造、谁负责管控生命周期，就交给谁
- 交给调用方管控 → 做成参数； 
- 交给函数自己管控 → 内部自建

✅ 4、读代码的时候，看有参数参数在哪，可以作为判断的一个标准
- `def xxx(db,data):`有形参传入，就说明是为了调用方准备
- `def xxx(): db = SessionLocal()`无形参传入，参数在内部定义，就是为自己准备使用
>这个判断方法可以作为一个快速猜想，第一眼看代码的直觉；
>但是不能作为下结论的公式，因为存在反例（函数内部可以从别的地方拿资源，比如读全局变量、读配置单例）

<br>

**问题情景**
回到这里，为什么这个`expire_pending_reservations`函数不传参，同时为什么要新建一个独立数据库会话?

- service 函数(`cancel_reservation`,`expire_pending_reservations`)全部都是普通函数； 
- 带 db 参数只是一种约定：适合给外面调用（比如`cancel_reservation`，路由接口要调用） service； 
- 不带 db、内部自己造 Session，是适合自己使用的（这里过期扫描函数是后台定时任务调用）的 service； 
- 区别不在函数本身，区别在：调用这个函数的环境，有没有 Depends、能不能稳定拿到 db
<br>

**补充**：**不同需求情景下函数作用不同**
场景 A：普通给接口调用的函数（用户点页面、提交预约、审核） 
- 有用户发请求
- FastAPI 通过 `Depends(get_db)` 自动给你生成一个 db（数据库会话），当参数传给 service 函数。
- 请求结束，这个 db 就自动关掉、回收。 
👉 这种 service 函数：`def xxx(db: Session, ...)`，db 是外面传进来的。

场景 B：这个过期扫描函数 `expire_pending_reservations()` 
- 没有用户发请求触发它 
- 它是后台悄悄循环跑的一段代码，没有 HTTP 请求，没有 `Depends`，没人自动给它生成 db 传进来
👉 所以它**不能靠传参拿 db，只能自己在函数里面造一个**

### （2）try-finally再理解

**需求情景**
- 资源释放优先用 `try-finally`；
- 捕获报错用`try-except`
<br>

**一、先拿【打开文件】举例，最经典场景**

**写法 A：try + finally（重点：保证关闭）**

```python
f = open("a.txt", "r")
try:
    data = f.read()
finally:
    # 无论read成功，还是read中途报错，都一定会执行close
    f.close()
```

目的：**文件句柄一定要关闭，防止资源泄露**。 
哪怕读文件的时候代码炸了，`f.close()` 照样跑。

> 补充：Python 里打开文件更推荐 `with open() as f:`
> **with 本质就是语法糖，底层自动帮你实现 try-finally，自动 close**

<br>

**写法 B：try + except（捕获错误）**

```python
try:
    f = open("a.txt", "r")
except FileNotFoundError:
    print("文件不存在")
```

这个是用来**处理 “打不开” 这个错误**，不是保证关闭
<br>

**组合写法（最完整）**
```python
f = open("a.txt", "r")
try:
    data = f.read()
except Exception as e:
    print("读取出错", e)
finally:
    f.close()
```

<br>

**二、回到你预约项目里的这段代码**
```python
def expire_pending_reservations():
    db = SessionLocal()
    try:
        now = datetime.now()
        items = db.query(Reservation).filter(Reservation.status == 0).all()
        # 循环修改状态、commit
        if changed:
            db.commit()
    finally:
        db.close()
```

✅ 这里只用了 `try-finally`，**没有写 except**，这个设计是合理的！ 我们拆开它的诉求：
- 目标：**不管查询、修改、commit 成功还是报错，这个 db 会话必须关闭，不能泄露数据库连接** → 交给 finally
- 为什么不加 except？ 
	- 这个是后台定时任务。如果数据库报错（断连、SQL 异常），我们**不打算吃掉这个错误**
	- 报错抛出去，任务本次执行失败，然后循环 60 秒后下一轮继续扫描
	- 如果加了 except 把错误吞掉，你连任务出问题了都不知道

👉 翻译： **try-finally：保证资源释放；要不要 except，看你要不要【捕获、消化这个异常】。**

<br>

**三、判断规则**

**1、什么时候必须想到 try-finally？**
只要你手动拿到了**需要手动释放的资源**：
- 手动 open 文件、手动 f.close ()
- 手动创建 db Session、手动 db.close ()
- 网络连接、socket、锁 
>特点：资源有 “打开 / 获取” 和 “关闭 / 释放” 配对动作，**哪怕中间报错，也必须释放**

<br>

**2、什么时候才加 except？**

满足下面任意一种，才需要捕获异常：
1. 你想给用户友好提示（接口里抛 BusinessException，返回前端提示）
2. 你想报错之后继续跑后面逻辑，不中断整个程序
3. 你需要单独处理特定错误（文件不存在、主键冲突）

**反面**：**不适合加 except 的场景**（定时任务就是这类）
后台任务、脚本：出错应该暴露出来，日志打印异常，不要悄悄吃掉错误。只需要 finally 保证资源关掉。

**总结**
过期扫描这个函数，在第一行代码创建数据库会话后，接下来就马上写`try-finally`

### （3）并发、并行
- 并发（Concurrency）：**看起来同时在跑**，本质是快速切换，同一时刻 CPU 只处理一件事
- 并行（Parallelism）：**真正同时一起跑**，多个 CPU 核心同一时间各自干活


### （4）进程、线程、协程再理解
#### 进程
是**操作系统**进行**资源分配**的基本单位，每打开一个程序至少就会有一个进程 

例子： 
打开微信 = 一个进程；打开 Chrome = 另一个进程；你的 FastAPI 后端服务跑起来，就是**一个进程**。
特点：
- 进程之间隔离：每个进程有自己独立内存，A 进程崩了，一般不影响 B 进程
- 开销大：创建、销毁进程很耗资源
- 一个进程里面，至少自带 1 个线程（主线程）

#### 线程
属于进程内部，是 CPU **调度**的最小单位，一个进程至少有主线程

一个进程可以开很多线程。 比如 FastAPI 进程（1 个进程），可以开：主线程、额外的工作线程。
- 操作系统负责切换线程：CPU 跑一会儿线程 A，切去跑一会儿线程 B
- 缺点：切换线程有开销；**共享同一个进程内存，容易出现竞争、数据错乱（线程不安全）**

> 重点：**多线程**是操作系统层面的**并发**方案

<br>

**总结**
- 从资源管理角度：进程是资源分配单位
- 从 CPU 干活调度角度：线程是调度单位

#### 协程
✅ 最重要一句话：**协程跑在某一个线程里面，协程不是操作系统管的，是代码自己控制切换**
👉FastAPI 项目是**一个进程**，这个进程默认有主线程，协程跑在这个主线程里面。 你完全可以再开别的线程，别的线程里面又跑别的逻辑
>协程是**线程里面的轻量任务**

<br>

**线程切换 VS 协程切换**
- 线程切换：操作系统强制切，说切就切，不知道什么时候切
- 协程切换：**只有到 await 这个标记点，主动让出控制权才切换**，代码自己控制什么时候切


**类比理解**
食堂
- 进程：独立的一家餐馆（内存独立，互不干扰）
- 线程：餐馆里面的服务员
    - 多线程：餐馆雇 3 个服务员（3 个线程，OS 调度）
    - 协程：**只有 1 个服务员（单线程），但是同时接很多桌客人** 
	    - 客人 A 烧水要等 3 分钟（await），服务员不站着等，转身给客人 B 下单；
	    - 等 A 水好了，再回来处理 A

协程又叫**用户态并发**，切换开销极小，非常适合 IO 等待场景（等数据库、等网络、sleep）

#### async、await、asyncio
`async`、`await` 是**语法标记**；
`asyncio` 是 Python 自带的库，用来管理协程、事件循环。
它们是一套：**单线程里面，遇到IO等待的时候，让出CPU，去干别的事** 的并发方案，不是多线程、不是多进程。
<br>
#### await
**await 是干嘛的？（最核心）**
先代入一个场景：
- 你有唯一一直画笔，和一个画好了的平面直角坐标系
- 你需要从x轴出发，平行于y轴画直线
	- 主线程 = **唯一一支画笔**（单线程，同一时刻只能画一条竖线）
	- X 轴上坐标：一个个独立协程任务，标记为 x1、x2、x3、x4……
	- 沿着 Y 轴向上画竖射线 = 这个任务正在被主线程执行
	- 没有多支画笔，画笔走到 `await` 时，才会停下当前这条射线

**场景 1：`await xxx()`**（await 后面是另一个协程 xxx）
1. 画笔正在画 x1 的竖射线
2. 遇到 `await x2()` → **x1 暂停上锁，暂时不能继续画**
3. 画笔空闲，调度器挑选就绪任务：先去画 x2
4. 如果 x2 内部也有 `await`，x2 也会暂停上锁，画笔再次释放，可以跑去画 x3、x4
5. 不断来回切换，直到 x2 整条射线全部画完（x2 任务结束）
6. x1 的解锁条件达成，x1 变成就绪；画笔有空了，回到 x1，继续向上画
>之前的思维误区是，我认为在第2点这里遇到await，x1 停下，提高xxx优先级，画笔切去专门画 xxx，必须从头到尾把 xxx 画完，才能回来画 x1
>实际上，await真正的作用是**上锁**


**场景 2：`await asyncio.sleep(n)`**
1. 画笔正在画 x1
2. 碰到 `await asyncio.sleep(n)` → x1 暂停上锁，上锁条件：等待 n 秒
3. 画笔释放，去画 x3、x4 等其他就绪任务
4. n 秒计时结束，x1 解锁变为就绪；画笔空闲时回来继续画 x1

> 和 `await xxx()` 的区别： sleep 的解锁条件是【时间到】；`await xxx()` 的解锁条件是【xxx 协程执行完毕】

**场景 3：调用普通同步函数**（函数内部没有 await）

```python
async def x1():
    expire_pending_reservations() # 同步def函数，内部无await
    await asyncio.sleep(60)
```

✅ 射线模型解释

1. 画笔开始画 x1，进入同步函数
2. **同步函数里面没有任何 await**，没有上锁暂停的标记
3. 画笔被粘在这条射线上，**不能离开、不能跑去画别的 x3/x4**
4. 必须一口气把同步函数的射线全部画完
5. 同步函数跑完之后，代码才走到后面的 `await`，才会发生暂停、释放画笔

👉 这就是**阻塞**：没有 await，射线中途不能停下，画笔被独占
<br>

**总结**
`await` 只能写在 `async def` 协程函数里面
语法：`await 可等待对象`（协程、asyncio.sleep、异步 IO、异步数据库查询等）


#### asyncio
**asyncio 是什么？**

它是**协程的调度器（事件循环）** 事件循环就是一个大管家：

- 保存一堆待跑的协程任务
- 哪个协程 await 让出了，就切去跑别的就绪协程
- IO返回了，再切回来继续跑这个协程

常用的3个API，项目里已经用到：
1. `asyncio.run(xxx)`：启动事件循环（一般脚本用）
2. `asyncio.create_task(协程)`：把协程丢进事件循环，后台并发跑（lifespan 里面扫描任务就是这个）
3. `asyncio.sleep()`：异步休眠（await 它，不会阻塞线程）

代入比喻：
`asyncio` = **整套调度管理的工作台 + 调度管家**
管家手里管着：
1. 所有已经生成的射线草稿（协程对象）
2. 所有被上锁暂停的射线，记录它们的解锁条件（等别的协程跑完 / 等时间到）
3. 记录哪些射线现在是【就绪状态】，可以拿画笔去画
4. 负责在画笔空闲的时候，挑选就绪的射线，安排画笔去绘制

👉 对应你见过的 API：
- `asyncio.run()`：启动管家、开启工作台，开始调度
- `asyncio.create_task()`：把射线草稿交给管家，加入调度队列，有空就安排画笔绘制
- `asyncio.sleep()`：管家提供的一种解锁规则：等待指定时间后解锁这条射线

#### async
**async是干嘛的？**
写在 `def` 前面，变成**协程函数**

```python
async def demo():
    pass
```

⚠️ **注意** 
你直接调用 `demo()`，**不会执行里面代码**，只会得到一个「协程对象」，类似一个待启动的任务，不是直接跑
普通函数 `def` 一调用就立刻执行；async 函数调用只打包，不跑

联系上面的比喻
`async` 是标记，用来**定义一条可以被暂停的射线模板**
- 普通 `def` 函数 = 一条**不能中途断开的实线射线**，画笔一旦开始画（一旦被调用），必须一口气画到头，没有暂停点。 
- `async def` 定义的函数 = 一条**允许中途打暂停标记（await）的射线模板**
	- 注意，这个模板和普通函数调用的方式不太一样，想让画笔画出这条线
		- `await demo_async()` 
		- `asyncio.create_task(demo_async())` 把草稿交给管家，管家才会在合适的时候安排画笔绘制这条射线。

<br>

#### time.sleep (60) / asyncio.sleep (60)
**1. time.sleep (60) 【同步休眠】**

```python
import time
time.sleep(60)
```

- 作用：让**当前线程原地卡死 60 秒**
- 底层：它会占用线程，**没有让出的动作，事件循环没法切换任务**
- 放在 async 函数里用它 = 灾难，直接阻塞整个 FastAPI 的事件循环

**2. await asyncio.sleep (60) 【异步休眠】**

```python
import asyncio
await asyncio.sleep(60)
```

- `asyncio.sleep(60)`：它本身是一个**可等待对象**，由 asyncio 库提供
- 碰到 `await`：
    1. 当前这个协程标记：我先暂停，60 秒之后再来唤醒我
    2. 主线程（事件循环）立刻离开这个协程，去处理别的协程（处理前端 http 请求、别的后台任务）
    3. 60 秒计时到了，这个协程变成就绪状态，主线程有空了再回来继续跑它
<br>

**4. 串起来，完整小例子**

```python
import asyncio

async def task1():
    print("任务1开始")
    await asyncio.sleep(2) # 等待，让出线程
    print("任务1结束")

async def task2():
    print("任务2开始")
    await asyncio.sleep(1)
    print("任务2结束")

async def main():
    # 创建两个后台任务，并发跑
    t1 = asyncio.create_task(task1())
    t2 = asyncio.create_task(task2())
    await t1
    await t2

asyncio.run(main())
```

执行顺序： 任务1开始 → 任务2开始 → 1秒后任务2结束 → 再等1秒任务1结束 总耗时≈2秒，不是3秒，这就是并发
<br>

**5. 回到这个预约部分（重点）**

```python
async def run_expire_scan():
    while True:
        expire_pending_reservations() # ❗这是同步函数！没有await
        await asyncio.sleep(60)
```

- 只有 `await asyncio.sleep(60)` 这一行，会让出线程，请求可以正常进来
- 但是 `expire_pending_reservations()` 同步函数执行的那一瞬间，**整个事件循环卡住**，所有HTTP请求全部等待，直到这个函数跑完。
- 修复方案：把数据库查询改成异步驱动，或者用线程池包一层同步函数：`await asyncio.to_thread(expire_pending_reservations)`
<br>

**6. 高频误区（记笔记）**
❌ await 就是等待，和 time.sleep 一样 
✅ 不一样：`time.sleep()` 是同步阻塞，卡死线程；`await asyncio.sleep()` 是让出线程
❌ create_task 开多线程
✅ 不是！任务依旧在同一个线程的事件循环里调度
<br>

**7. 总结**
- async：标记函数为协程函数，调用后生成协程对象，不会直接执行
- await：只能在async函数内使用；遇到IO等待时主动让出线程，允许其他协程运行
- asyncio：Python原生协程库，提供事件循环，负责调度管理多个协程任务

核心规则
- 协程切换只发生在 await 处；
- 同步耗时函数没有await，会阻塞整个事件循环；
- create_task 是把协程交给事件循环后台并发执行，不是新开线程。



### （5）同步、异步再理解
同步、异步是描述**一段代码的执行方式**，不是和进程 / 线程 / 协程并列的东西

**1. 同步**：一行一行顺序执行，遇到等待就原地阻塞，啥也不干，等完才往下走
```python
# 同步
time.sleep(5) # 卡住整个线程，原地等5秒
print("结束")
```

**2. 异步**：遇到 IO 等待的时候，主动让出，先去干别的，等待结束再回来继续执行

```python
# 异步
await asyncio.sleep(5) # 让出线程，在这个5秒内，线程可以跑别的协程
```

> 同步代码可以跑在主线程、子线程里； 
> 异步代码（协程）只能跑在支持 asyncio 事件循环的线程里

<br>

**套回预约项目的场景，落地理解**
**1、项目运行**
1. 启动 uvicorn，启动**一个进程**
2. 这个进程里面，主线程跑 asyncio 事件循环
3. 主线程里面有很多协程任务：
    - 处理前端 HTTP 请求的协程
    - 你写的后台扫描 run_expire_scan 协程（被 create_task 丢进事件循环）
4. 它们在同一个主线程里面，在 await 点来回切换（协程并发）

**2、**
- `async / await / asyncio.create_task()` **不是 FastAPI 专属，是 Python 原生异步 IO（asyncio）的知识** 
- asyncio 异步：**单线程内的并发**，是 Python 代码自己调度，又叫「**协程**」

- 协程 ≠ 多线程：
    - 多线程：操作系统负责调度切换
    - 协程：运行在同一个线程内部，只有遇到 `await` 才主动让出控制权、切换任务
- FastAPI 只是大量使用 asyncio，所以开发时会频繁见到这套语法

**3、总结(重点)**
- `expire_pending_reservations()`是一个业务工具函数，写在协程 `run_expire_scan` 里面
- `main.py` 通过 `create_task` 把 `run_expire_scan` 这个协程扔进事件循环后台跑
- `lifespan` 控制它的启动和关闭

#### lifespan
FastAPI lifespan 挂载后台异步定时任务（预约过期扫描）

✅ **需求情景**
我们有一个独立的功能：每隔 60 秒自动扫描、把超时未审核的预约改成已取消。 这个功能**不是接口，不需要前端调用**，希望满足两点：

1. **项目启动的时候自动启动这个扫描循环**，不用手动去单独运行脚本；
2. **项目正常关闭的时候，优雅地关掉这个后台循环任务**，不要留下僵尸任务、无限死循环。

FastAPI 旧版本用 `@app.on_event("startup")` / `@app.on_event("shutdown")`，新版推荐统一用 `lifespan` 生命周期管理器。

> 简单一句话：lifespan 就是给你提供「服务启动时」和「服务关闭时」两个钩子，用来挂载后台常驻任务

<br>

 **代码逐段解析**

```python
import asyncio
from contextlib import asynccontextmanager
from app.services import reservation_service
```

- `asyncio`：用来创建、管理异步后台任务
- `asynccontextmanager`：用来写异步的上下文管理器，是 `lifespan` 要求的装饰器
- 导入我们写好的扫描函数 `run_expire_scan`（里面是 while True 循环 + await sleep）

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    # ========== 启动阶段：yield 之前的代码 ==========
    task = asyncio.create_task(
        reservation_service.run_expire_scan()
    )
    # create_task：把这个异步循环丢进事件循环，后台跑，不阻塞主服务
    # 主服务继续去接收前端接口请求，扫描在后台悄悄并行执行

    yield   # 【分水岭】
    # yield 执行之后：FastAPI 正式启动，对外提供接口服务，处理HTTP请求

    # ========== 关闭阶段：yield 之后的代码 ==========
    task.cancel()
    # 当服务收到关闭信号（ctrl+c、容器停止），走到这里，给后台任务发送取消信号
```

```python
app = FastAPI(lifespan=lifespan)
# 把这个生命周期函数绑定给 FastAPI 实例，框架自动管理
```

**执行时序（非常关键）**
1. 启动服务 → 进入 `lifespan`
2. `asyncio.create_task()` 创建后台扫描任务，任务开始跑循环
3. 遇到 `yield` → **卡住在这里，FastAPI 正式上线，开始接收前端请求**
4. 服务收到关闭信号（停止）→ 跳出 yield，执行后面 `task.cancel()`
5. 后台任务收到取消信号，结束循环，服务正常退出

> ⚠️ 重点：`yield` 是分界线！ yield前面 = 启动逻辑；yield后面 = 关闭逻辑。

<br>

📌**注意（了解即可）**

1. **`asyncio.create_task()` 的作用** 把异步函数交给事件循环，**并发后台运行**
2. 如果不写 `create_task`，直接调用 `await run_expire_scan()`，代码会卡在这个死循环里，`yield` 永远执行不到，整个web服务直接起不来！
 ```python
 # ❌ 错误写法，阻塞启动
 await reservation_service.run_expire_scan()
 # ✅ 正确写法，丢后台并行
 task = asyncio.create_task(reservation_service.run_expire_scan())
 ```

3. **`task.cancel()` 是优雅关闭，不是立刻杀死**`cancel()` 是发送取消标记，当后台任务运行到 `await asyncio.sleep(60)` 这个await点的时候，才会抛出 `CancelledError`，循环终止。 如果没有 `task.cancel()`：服务主进程关掉了，这个while循环还可能残留，变成僵尸任务
4. 为什么不能直接写在模块顶层？ 如果直接在main.py顶层写 `run_expire_scan()`，导入代码的时候就直接跑，不受服务生命周期控制，不好管理启停。lifespan 绑定到服务，生命周期对齐
5. 适用范围：只适合**异步的后台任务** 我们的扫描是 `async def run_expire_scan()`，所以可以用 asyncio 任务； 如果是同步阻塞死循环，不能直接 create_task，会卡住整个事件循环

### 注解再理解
`-> OpenAI`：**Python 类型注解（返回值标注）**

### 解包再理解
- `**字典`：**字典解包** → 把`key:value`拆成 `key=value` 关键字参数（
- `*列表/元组`：**序列解包（单个星号解包）** → 把列表里面每一项，拆开、挨个拿出来，作为独立的位置元素

**1. 先看场景**（这里chat函数内部的代码）

```python

    ChatMessage(role="assistant", content=SYSTEM_PROMPT).model_dump(),
```

- `history` 是什么：是一个**列表**，里面每一项是一条消息字典

```python
        {"role":"user", "content":"怎么预约？"},
```

我们想要拼成一个新的大列表：**系统提示词 + 全部历史消息**
<br>

 (1)**如果不写 `*`，直接写**


结果会变成**嵌套列表**（错误！OpenAI SDK不认）：

```python

    {"role":"assistant", "content":"系统提示词"},
    [
        {"role":"user", "content":"怎么预约？"},
        {"role":"assistant", "content":"登录后选实验室..."},
    ]
]
```

👉 里面塞了一个子列表，SDK报错，格式不对。
<br>

(2)**加上 `*history`（正确写法）**

✅ 一维平列表，正好符合 OpenAI 要求的 messages 格式！


### 2、全局变量+单例实现缓存（懒加载）
**需求分析**
Chroma 集合对象、中文 BGE 向量模型加载开销很大，不能每次用户提问都新建一遍
所以，我们需要：
- 1、提供一个获取 Chroma 集合的函数，**整个服务运行期间，只创建一次集合对象**；
- 2、后续所有检索请求，都复用这同一个对象。
- 3、外部代码不能直接随便操作这个集合，统一通过 `get_collection()` 获取
- 4、【新增懒加载需求】推迟初始化时机：**后端启动时不加载模型、不初始化向量库，第一次调用检索时才初始化**，避免启动阶段阻塞、HuggingFace网络超时卡死

```python
_collection = None

def get_collcetion() -> Collection:
    """向量库的初始化"""
    global _collection
    if _collection is not None:
        return _collection
        
# 懒加载版本只是在if return之间添加了代码，不满足if则直接最后return，满足if则进行中间的初始化代码
```

#### 私有变量再理解
`_collection`
Python 私有约定（不是强制语法，是代码规范）：
- 变量 / 函数名**单下划线开头 `_xxx`**：代表**内部私有变量** 
- 👉 含义：**这个变量只是给本文件（kb_service.py）自己内部用的，不要在别的文件 import 之后直接去读写它** 
- 别人看到下划线，就知道：不要直接碰 `_collection`，想要集合，老老实实调用 `get_collcetion()` 获取

> 对比： 
> `collection`：普通名字，暗示外部也可以直接使用 
> `_collection`：内部私有，对外隐藏，只供内部使用

**再理解**
看上面需求分析第3点，那么为什么要让外部代码不能直接随便操作这个集合，统一通过 get_collection() 获取？为什么要这样设计呢？

**1. 保护单例逻辑**（最贴合你这段 RAG 代码的理由）

我们整套代码的目标：`_collection` 有且只能有一个，全程复用。 如果外部可以直接操作 `_collection`：

- 别的地方写一句 `kb_service._collection = None`
- 或者外部重新新建一个 collection 赋值给它 👉 缓存直接被破坏，单例失效，后续又会重复初始化、重复导入文档、向量模型重复加载，甚至 Chroma 文件锁报错。

把获取入口收窄成唯一函数 `get_collection()`： **所有地方拿集合，只能走这个函数，单例判断逻辑被封装在函数里面，外部没法绕过。**
<br>

**2. 统一收口，封装**

假设以后你要加功能：
- 拿到集合之前打印日志
- 加异常捕获、自动重连
- 切换不同的向量库实例 

如果外部到处都是直接访问 `_collection` 的代码，你要改所有地方，工作量巨大
统一入口之后：**改逻辑只改一处，比如这里只修改 `get_collection()` 内部，所有调用方自动生效**

内部细节藏起来，对外只暴露简单接口，符合**封装思想（面向对象基础思想）**
使用者只需要 `col = get_collection()`，不用关心底层怎么实现缓存

#### 全局变量再理解
`global _collection`

✅ **需求情景**
我们需要一个**在函数多次调用之间，能保留状态的地方——就是缓存**
- 如果是在函数内部创建的局部变量，函数跑完就销毁了，存不住 “已经创建好的集合”
- 把它放到函数外面，成为模块级全局变量，进程活着，这个变量就一直存在
>`global` 作用：允许函数内部修改这个顶层全局变量的值

#### 单例模式再理解
（整套结构：全局变量 + if 判断 + return）
✅**先说，单例模式是什么？**
- 单例**是一种设计模式（固定的代码思路、结构范式）**；
- 控制目标：**整个程序生命周期内，实例最多只有一个**
- 不是只能给初始化函数用，只是非常适合「**只需要一份的、初始化开销大**」的东西

#### 懒加载
✅ 懒加载是什么？ 
懒加载是**初始化时机策略**：不是程序启动/模块导入时立刻创建实例，而是等到第一次真正需要使用资源的时候，才去初始化。 它解决【什么时候创建实例】的问题。 
对比两种单例写法： 
 - 预加载单例：模块顶层直接实例化（上面原版kb_service），导入就加载模型，启动容易卡死 
 - 懒加载单例：初始值None，第一次调用函数才初始化（我们最终版本），启动不阻塞

**总结**
现在这个写法
- 全局变量 + if 判断 + return，就是说，**如果有，则直接return，如果没有，再往下走初始化代码**，这个就属于**单例的简易实现版本**（适合小项目）
	- 正规写法还有类里面重写 `__new__`、用装饰器等，本质目标不变
- 全局变量 + if判断 + 延迟初始化，就是**懒加载版本的简易单例**
<br>

再看看这里我们需要做什么？
✅**需求情景**：上面需求分析的1、2点

资源（Chroma 集合、向量 Embedding 模型）初始化成本高：
- 重复加载 BGE 向量模型很慢
- 反复新建 Chroma 客户端容易出现文件锁冲突
- 重复读取 md、导入向量会产生大量重复数据 
	- 单例目标：**全局保证只有这一个集合实例**，所有请求共享它 
	- 懒加载目标：推迟加载，不让模型加载阻塞后端启动
	- 第一次调用：`_collection` 是 None → 往下走创建集合； 
	- 之后任意次调用：直接返回已经存在的对象，不再重复初始化

<br>

**总结单例模式**
1. 它是一套**约定好的代码结构**，目标只有一条：

> 保证整个程序运行期间，这个类 / 对象**最多只有一个实例**，所有人拿到的都是同一个

2. 它**很适合初始化开销大的资源**（你现在的场景）： 向量模型、数据库连接、Chroma 集合、redis 连接池、日志实例。 这些东西加载慢、占资源、开多份还容易冲突（文件锁、连接爆满），所以优先上单例。
3. 但！**不是专门只给初始化函数用**，它是通用模式： 只要业务要求「全局唯一一份」，就可以用单例。 举别的例子：
	- 全局配置管理器，整个项目就一份配置
	- 全局消息通知器


#### 对比pickle 序列化缓存
- **pickle 序列化缓存**
	- 把【计算出来的结果 / 对象】存到**磁盘文件**
	- 程序重启之后，读文件把对象恢复出来；解决「重启之后数据丢了」
	- 属于**持久化缓存**
- **`_collection` 全局变量缓存**
	- 只存在**内存里**。服务一旦重启，`_collection` 变回 `None`，缓存直接消失
	- 它只解决**同一次服务运行内，多次请求重复初始化**的问题
	- 是**内存缓存**

#### embedding和TF-IDF
**需求情景**
联想之前的红楼梦图书检索那个项目，**RAG的底层**就是
**文本 →  通过模型 → 向量，再做相似度计算**

而这里的代码，就在做**将集合和模型（embedding）绑定**，还没有输出向量，后续会传入md文件，再调用这里即可进行**文本向量化**
- 图书检索那里，用的是**TF-IDF**完成文本向量化
- 而这里用的是**embedding模型**

TF-IDF
- 本质：**基于词频的统计方法**，不是 AI 模型
- 逻辑：统计每个词在当前文档出现频率、以及在全部文档里的稀有程度
- 特点：只认字面单词，**不懂语义**
- 优点：轻量、快、不需要训练模型、不需要 GPU
- 缺点：同义词、近义词、转述，匹配不到；长文本效果差
>举例子
>`计算机实验室几点开门` 和 `机房开放时间` TF-IDF 看到单词不一样，会判定完全不相似；哪怕意思相同

Embedding
- 本质：**预训练语言模型（神经网络）输出的语义向量**
- 逻辑：模型在海量文本上学过语言，把**语义含义**编码进向量
- 优点：理解语义，同义改写、换说法也能检索出来，RAG 首选
- 缺点：需要加载模型，开销比 TF-IDF 大
>同样上面例子：`计算机实验室几点开门` 和 `机房开放时间` 语义相近，算出来的向量距离很近，可以匹配上。

---

所以，这里的几行代码在做什么？
1. `PersistentClient(...)`：只是打开 / 连接本地的向量库文件夹
2. `get_or_create_collection(..., embedding_function=xxx)`： 
	1. 只是**把这个 embedding 函数（BGE）登记绑定到这个集合上** 
	2. 相当于写一条备注：以后这个集合 add /query 的时候，就用这个函数做向量化 
	3. ✅ 仅仅保存函数引用，**没有传入任何文本，模型不会跑，不会产出向量**
3. 真正产生向量，发生在下面两个地方：
	- `col.add(documents=[...])`：把 md 文档文本喂进去 → 自动调用 BGE → 生成文档向量，存入 Chroma
	- `col.query(query_texts=[...])`：把用户提问文本喂进去 → 自动调用 BGE → 生成 query 向量，再去比对相似度

**逐行拆解**

    - 持久化：向量、文档、索引全部写到 `CHROMA_DIR` 本地文件夹里，服务重启之后向量数据还在。
- `path=str(CHROMA_DIR)`：告诉 Chroma，把数据存在这个目录。

> 注意：Chroma 的接口要求 path 传字符串，Path 对象要转 str。

`get_or_create_collection` 是一个原子操作：

✅ 如果不存在 → 新建这个集合
- `name="lab_kb"`：集合唯一名字，区分别的知识库

	- 以后往这个集合添加文档、查询检索，**全部自动用这个 BGE 中文模型做向量化**

### 6、search 检索函数

**需求情景**

前面 `get_collection + col.add` 是**入库、建向量索引（一次性）**；
`search` 是**用户提问阶段，检索阶段**： 
- 接收用户的问题文本，交给 Chroma，自动把问题转成 query 向量
- 和库里已经存好的文档向量做相似度比对
- 筛选出相关知识库文本，格式化之后返回给上层 AI 接口
- 用来拼进 prompt 给大模型

> 一句话分工：add 是存资料；search 是拿问题找资料


```python
def search(query: str):
    """根据关键字去检索向量库"""
    col = get_collcetion()
    if col.count() == 0:
        return ""
    limit = min(5, col.count())
    res = col.query(query_texts=[query], n_results=limit)
    docs = (res.get("documents") or [[]])[0]
    metas = (res.get("metadatas") or [[]])[0]
    distances = (res.get("distances") or [[]])[0]

    score_parts = []
    for doc, meta, dist in zip(docs, metas, distances):
        # 0-1 越接近1表示越相关
        score = 1 / (1 + dist)
        if score < 0.5:
            continue
        name = meta.get("source") or ""
        score_parts.append({"score": score, "content": f"[{name}]\n{doc}"})
    print(f"检索出来的 score_parts：{score_parts}")
    score_parts.sort(key=lambda x: x["score"], reverse=True)
    final_parts = [item["content"] for item in score_parts[:2]]
    return "\n\n".join(final_parts)
```


`dist`：**dist越小，向量越相似**，距离不能直接当相似度给人看

- score越接近1：越相关

### 1、生成器表达式+next()

```python
question = next(
    (item["content"] for item in reversed(history) if item["role"] == "user"), ""
)
```

✅ 作用：拿到**最新一条用户消息**

- `reversed(history)`：把对话历史倒序遍历（从最后一条往前找）
- 生成器表达式：找第一个 role=user 的内容
- `next(..., "")`：找到就返回文本；如果找不到用户消息，默认返回空字符串，防止报错

> 为什么只取最新一条？
> RAG 检索只拿用户当前这一轮的问题去搜知识库，不需要拿全部历史去检索。


#### 生成器再理解2
- `yield` 写的函数，是**生成器函数**； 
- 而 `(xxx for x in ... if ...)` 这种括号写法，叫 **生成器表达式**
>二者本质都是生成器：**惰性求值、按需产出，不会一次性把所有结果全部放到内存**

#### 生成器表达式
先看这一段代码里的生成器表达式
```python
(item["content"] for item in reversed(history) if item["role"] == "user")
```

这就是生成器表达式。 
- 它**不会立刻循环、不会把所有符合条件的结果全部算出来存成列表**。
- 它只是一个 “待执行的迭代流水线”： 只有外面要它拿一个值的时候，它才往前走一步，判断条件，产出一个结果

对比：

```python
# 列表推导式：一次性全部算完，全部放进内存，用的中括号[]
[item["content"] for item in reversed(history) if item["role"] == "user"]

# 生成器表达式：惰性，要一个，算一个,用的小括号()
(item["content"] for item in reversed(history) if item["role"] == "user")
```


**为什么这里不用列表推导式？**

- 列表推导式会**遍历全部历史，把所有 user 消息全部收集出来**，我们其实只需要第一个。 history 消息很多的时候，那就是做了多余的循环。
- 生成器 + next 找到第一个就直接停，效率更高，也更节省内存

#### next再理解
`next(生成器, 默认值)` 
作用：**向生成器索要下一个值**。

执行流程套进这行代码：
```python
question = next(
    (item["content"] for item in reversed(history) if item["role"] == "user"), 
    ""
)
```

1. `reversed(history)`：从最后一条消息（最新消息）开始往前遍历
2. 生成器开始逐个取 item，判断 `item["role"] == "user"`
3. **找到第一个满足条件的，立刻把这个 content 返回，生成器直接停下，不再继续循环！** 
	1. 👉 重点：找到就停，不会把剩下所有 user 消息全部遍历一遍！
	2. 这是这个写法的优势：我们只想要**最新一条用户消息**，找到就结束，不用遍历全部历史。
4. 如果从头到尾遍历完，一条 user 消息都没有，生成器耗尽了。 这时 next 会返回第二个参数 `""`（空字符串），而不是抛出 `StopIteration` 报错
