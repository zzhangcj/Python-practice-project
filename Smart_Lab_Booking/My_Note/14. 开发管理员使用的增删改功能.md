```python
def create_user(db: Session, data: UserCreateRequest):
    """新增用户"""
    exist = db.query(User).filter(User.username == data.username).first()
    if exist:
        raise BusinessException(message="账号已存在")

    user = User(
        username=data.username,
        password=hash_password(data.password),
        name=data.name,
        role=data.role,
        email=data.email,
        phone=data.phone,
        avatar=data.avatar,
        status=data.status,
    )
    db.add(user)
    db.commit()
    db.refresh(user)
    return UserResponse.model_validate(user)

def update_user(db: Session, user_id: int, data: UserUpdateRequest):
    """更新用户"""
    user = db.query(User).filter(User.id == user_id).first()
    if not user:
        raise BusinessException(message="用户不存在")
    payload = data.model_dump(exclude_none=True)
    for filed, value in payload.items():
        setattr(user, filed, value)
    db.commit()
    db.refresh(user)
    return UserResponse.model_validate(user)

def delete_user(db: Session, user_id: int, currut_user: User):
    """删除用户"""
    if user_id == currut_user.id:
        raise BusinessException(message="不能删除当前登录的账号")
    user = db.query(User).filter(User.id == user_id).first()
    if not user:
        raise BusinessException(message="用户不存在")
    db.delete(user)
    db.commit()
```

密码要加密。修改时没传密码就不动。不能删当前登录账号。

### payload载荷
payload = 有效载荷，在这里代表：**前端本次真正提交、想要修改的字段字典**
怎么实现的：`model_dump(exclude_none=True)`实现的**局部更新**
（这里详见 `11. 开发用户修改个人信息功能--2、用户 Service--局部更新`）

### setattr
**setattr 原生 Python 语法**
```python
setattr(对象, 属性名字符串, 值)
```

举个简单小 demo 理解：

```python
class Demo:
    name = "原始名字"

d = Demo()
setattr(d, "name", "张三")
print(d.name) # 张三
```

<br>

这里我们的**需求是赋值**
写法 1：硬编码**直接赋值**（`user.xxx = 值`）
```python
if data.name is not None:
    user.name = data.name
if data.email is not None:
    user.email = data.email
if data.role is not None:
    user.role = data.role
# 每新增一个可更新字段，就必须新增一段if判断
```

特点： 属性名是写死在代码里的（`name` / `email` / `role`）。 
在写代码的时候，就已经固定了要更新哪些字段；
字段越多，if 判断就越多，维护麻烦

<br>

写法 2：`setattr` + 循环（`for xx , xx in payload.item()`)实现**动态赋值**
1. `payload` 是字典，key 是**本次要更新的字段名字符串**，value 是新值；
2. `field` 是循环拿到的变量，里面存着字段名（可能是`"name"`，也可能是`"status"`，由前端传参决定）；
3. `setattr(user, field, value)`：把变量 `field` 里面存的字符串，当做属性名去赋值

总之
>setattr 是无脑按字典 key 赋值！ 
>只要 payload 里面有的 key，都会赋值给 user 对象

### Post不加路径参数
**新增用户为什么用 POST，并且 @router.post ("") 不加路径参数**

（1）`/api/user` 代表【用户这个资源集合】（全部用户的列表）
- POST 的语义：**往这个集合里面新增一条数据** 
- 新建用户的时候，这条用户记录还没存入数据库，数据库还没有给它分配自增 id，它本身不存在 id， 所以没法在 url 里写 id
>这个是后端路由接口，作用就是接收前端传过来的数据（账号、密码、姓名等新增信息放在请求体 JSON 里），依次做接收、参数校验、权限鉴权、调用业务逻辑，最后包装结果返回给前端
>
>api + prefix="/user" +"/me"会组成一个**完整 URL 地址**，是前端访问后端的时候，参考的地址
>这里不写第三部分，即`post("")`,意思是就在/api/user这里新增用户

<br>

（2）举个生活化类比：
`/api/user` 相当于一个文件夹，文件夹名字叫【所有用户】 
POST 就是往这个文件夹里**新建一个文件**，新建之前这个文件没有编号，编号是保存成功之后系统才分配的

而修改、删除（PUT、DELETE），是去修改 / 删掉**已经存在的某一条用户**。
这条记录早就入库，有唯一 id 了，所以要在 url 带上 `/{user_id}`，告诉后端：你要操作的是哪一个用户

>**一句话总结**
>	POST 新增：目标是【用户集合】，资源还没有 id，不带路径 id； 
>	PUT/DELETE 修改删除：目标是【某一个已存在用户】，用 url 里的 id 定位它。

### `/list`和`/{user_id}`的核心区别

**① `/list` 👉 固定字符串路径**

```python
@router.get("/list")
```

拼接完整路径：`/api/user/list`

- `/list` 是**固定字面常量**，写死的文本
- 作用：查询用户列表，批量查询，不是操作某一个特定用户

 **② `/{user_id}` 👉 路径参数（动态占位符）**

```python
@router.put("/{user_id}")
```

`{user_id}` 是 FastAPI 的**动态路径变量**，可以匹配任意数字，例如： `/api/user/1`、`/api/user/2`、`/api/user/100`

- 用来定位**单独某一条用户记录**
- `user_id` 会自动解析，传给函数里的 `user_id: int` 参数

<br>

**重点：为什么 `/{user_id}` 要写在 `/list`、`/info`、`/password` 的后面？**（高频考点）

>FastAPI 匹配路由的规则：**从上往下一行一行比对，碰到第一个匹配成功的路由，就直接执行，不再往下看**

`/{user_id}` 是动态占位符，它可以匹配 `/api/user/后面随便写的内容`，而且你定义了 `user_id: int`，要求匹配到的内容必须是数字。

❌ 如果顺序写反（错误示范）

```python
@router.get("/{user_id}")   # 动态路由放前面
@router.get("/list")        # 固定路由放后面
```

当访问 `/api/user/list`： FastAPI 从上开始匹配，先看到 `/{user_id}` 这条规则，它会把字符串 `list` 当成 user_id 的值，然后尝试把文本 `list` 转成整数，转失败 → 直接报错。

✅ 正确顺序

```python
@router.get("/list")        # 固定文字路由放上面
@router.get("/{user_id}")   # 动态id路由放下面
```

访问 `/api/user/list`： 优先匹配到上面的 `/list`，正常执行列表接口，不会走到下面动态路由。 只有访问 `/api/user/2`、`/api/user/5` 这种数字的时候，才会匹配到下面的 `/{user_id}`。

> **一句话总结**
> `/list`、`/info` 是写死的固定文字路径，要优先匹配；
>  `/{user_id}` 属于 “兜底匹配”，放后面，只有前面固定路径全都不匹配的时候，才轮到它。

## （6）前端：新建页面 Vue

**一、固定公理**

以下是 Vue3 + Element Plus 后台开发的通用底层规则，不受业务影响，恒定成立：

1. `el-dialog` 通过 `v-model` 绑定布尔值，控制弹窗的显示与隐藏。
2. 表单提交前必须调用 `formRef.value.validate()` 执行校验，校验不通过不得发起接口请求。
3. `el-form-item` 的 `prop` 属性值必须与 `form` 响应式对象中的字段名完全一致，否则校验规则不会生效。
4. 列表页完成新增、修改、删除操作后，必须重新调用列表加载函数刷新表格，保证页面数据与数据库数据一致。
5. 删除属于高危操作，必须增加二次确认交互，这是行业通用的交互规范。
6. REST 接口规范：新增资源用 POST 请求，更新资源用 PUT 请求，删除资源用 DELETE 请求。
7. 编辑场景下，业务唯一标识（如用户账号、ID）通常不允许修改，对应输入框需设置禁用状态。

**二、严谨文字解释**

本次在基础列表页之上新增了「新增用户、编辑用户、删除用户」三项能力，以下区分标准规范与项目自定义写法：

**1. 顶部操作区 + 表格操作列**

- **标准规范**：后台 CRUD 列表页的标准布局：顶部放搜索+新增按钮，表格末尾固定“操作列”放置行级编辑、删除按钮。
- **项目自定义**：按钮搭配 Element Plus 图标组件；操作按钮使用文字按钮样式；点击新增触发 `handleCreate`，点击行内编辑触发 `handleEdit(row)`。

**2. 新增/编辑弹窗复用**

- **标准规范**：新增与编辑业务字段一致时，复用同一个弹窗、同一份表单数据对象，是前端开发的标准最佳实践，可减少重复代码。通过表单中是否存在主键 ID，区分「新增模式」与「编辑模式」。
- **项目自定义**：
    - 弹窗标题动态切换：存在 id 显示“编辑”，无 id 显示“新增”；
    >`form.id ? updateUserApi(form.id, form) : createUserApi(form)`
    - 编辑模式下账号输入框禁用，不允许修改用户名；
    - 每次打开弹窗前，先执行 `resetForm()` 重置表单，避免上一次操作的数据残留。

**3. 删除交互逻辑**

- **标准规范**：删除为高危操作，必须弹出二次确认框，用户主动确认后才发起删除请求。
- **项目自定义**：使用 `ElMessageBox.confirm` 实现确认弹窗；删除成功后弹出成功提示，并调用 `load()` 刷新列表。

**4. 表单提交逻辑**

- **标准规范**：提交前先触发表单校验，校验失败直接终止流程；根据操作模式选择对应接口，请求成功后关闭弹窗、刷新列表。
- **项目自定义**：
    - 用三元表达式 `form.id ? updateUserApi(form.id, form) : createUserApi(form)` 自动匹配新增/编辑接口；
	    >这里，是看form.id是否存在，若存在，则是新增，若没有则是编辑
    - 单独使用 `formLoading` 控制提交按钮的加载状态，防止重复点击提交；
    - 自定义校验规则：账号必填、密码长度 3-10 位、名称必填、邮箱格式校验、手机号正则校验。

**三、易混淆概念对比**

|名称|作用|所属模块|核心注意点|
|---|---|---|---|
|`params`|存储列表查询条件（页码、每页条数、搜索关键词）|列表查询模块|仅和表格加载、分页、搜索相关|
|`form`|存储弹窗内的表单字段数据|新增/编辑弹窗模块|字段需与后端接口入参一一对应|
|`loading`|表格数据加载的加载状态|列表模块|调用列表接口时开启，请求结束关闭|
|`formLoading`|弹窗表单提交的加载状态|弹窗模块|点击保存时开启，请求结束关闭|
|`handleSearch`|触发搜索，重置页码后刷新列表|搜索功能|搜索前必须将页码重置为第 1 页|
|`handleSave`|提交弹窗表单，执行新增或更新|弹窗功能|必须先校验表单，再发起请求|

**四、高频踩坑预警（思维误区提前标注）**

1. ❌ 误区：新增和编辑必须写两个独立的弹窗、两个表单对象。 ✅ 正确：业务字段一致时复用弹窗是标准最佳实践，通过 ID 区分模式，代码更简洁、更易维护。
2. ❌ 误区：打开编辑弹窗前不需要重置表单。 ✅ 正确：必须先重置表单，否则上一次操作的残留数据会带入下一次打开，出现脏数据。
3. ❌ 误区：`prop` 随便写，只要输入框绑定了 form 字段就行。 ✅ 正确：`prop` 必须和 `form` 内的字段名完全一致，Element Plus 依靠 `prop` 匹配校验规则，写错则校验完全不生效。
4. ❌ 误区：增删改操作成功后不用刷新表格。 ✅ 正确：数据库数据已发生变化，必须重新调用 `load()` 拉取最新数据，否则页面显示与后台数据不一致。
5. ❌ 误区：编辑时可以修改账号。 ✅ 正确：账号是用户唯一标识，业务上通常禁止修改，前端需禁用输入框，后端也应做对应权限校验。

**五、辅助比喻**

【⚠️比喻只是辅助，有局限性，以上面公理为准】 把用户列表页比作一本员工花名册：

- 「新增」按钮：拿出一张空白登记表，填完信息后贴进花名册
- 「编辑」按钮：抽出某一页已有的登记表，修改内容后再放回去
- 「删除」按钮：撕掉某一页，撕之前要再确认一次避免误撕
- 弹窗：就是那张登记表，新增时是空白的，编辑时预先印好原有内容
- 操作完成后刷新列表：重新翻一遍花名册，确认最新的内容

**六、精简笔记版**

 用户管理列表页（增删改完整版）核心知识点

页面结构

- 顶部：搜索框 + 查询按钮 + 新增按钮
- 中间：数据表格，末尾固定操作列（编辑、删除）
- 底部：分页组件
- 弹窗：新增、编辑共用同一个表单弹窗

核心逻辑

1. **弹窗复用**：新增和编辑共用 `el-dialog`，通过 `form.id` 是否存在区分模式；标题动态切换，编辑时账号输入框禁用。
2. **表单重置**：打开弹窗前必须调用 `resetForm()` 清空历史残留数据。
3. **删除确认**：删除前弹出二次确认框，防止误操作；操作成功后自动刷新列表。
4. **保存逻辑**：先执行表单校验，校验通过后根据是否有 id，自动调用新增/编辑接口；成功后关闭弹窗、刷新表格。
5. **状态分离**：表格加载状态 `loading` 与弹窗提交状态 `formLoading` 分开控制，互不干扰。

规范要点

- 表单 `prop` 必须与 `form` 字段一一对应，校验规则才会生效
- 所有增删改操作完成后，必须调用 `load()` 刷新列表数据
- 编辑状态下业务唯一标识（账号）禁止修改
- 删除属于高危操作，必须增加二次确认
