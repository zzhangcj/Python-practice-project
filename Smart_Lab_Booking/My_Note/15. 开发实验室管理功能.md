## lab_service

```python
from sqlalchemy import or_
from sqlalchemy.orm import Session

from app.common.exceptions import BusinessException
from app.common.response import PageResponse
from app.models.lab import Lab
from app.schemas.lab import LabCreateRequest, LabResponse, LabUpdateRequest

def get_lab_page_list(
    db: Session, page: int, page_size: int, keywords: str | None = None
):
    query = db.query(Lab)
    if keywords:
        query = query.filter(
            or_(Lab.name.ilike(f"%{keywords}%"), Lab.location.ilike(f"%{keywords}%"))
        )
    total = query.count()
    items = (
        query.order_by(Lab.id.desc())
        .offset((page - 1) * page_size)
        .limit(page_size)
        .all()
    )
    return PageResponse(
        list=[LabResponse.model_validate(item) for item in items],
        total=total,
    )

def create_lab(db: Session, data: LabCreateRequest):
    exists = db.query(Lab).filter(Lab.name == data.name).first()
    if exists:
        raise BusinessException(message="实验室名称已存在")

    lab = Lab(**data.model_dump())
    db.add(lab)
    db.commit()
    db.refresh(lab)
    return LabResponse.model_validate(lab)

def update_lab(db: Session, lab_id: int, data: LabUpdateRequest):
    lab = db.query(Lab).filter(Lab.id == lab_id).first()
    if not lab:
        raise BusinessException(message="实验室不存在")

    payload = data.model_dump(exclude_none=True)
    if "name" in payload:
        exists = (
            db.query(Lab)
            .filter(Lab.name == payload["name"], Lab.id != lab_id)
            .first()
        )
        if exists:
            raise BusinessException(message="实验室名称已存在")

    for field, value in payload.items():
        setattr(lab, field, value)
    db.commit()
    db.refresh(lab)
    return LabResponse.model_validate(lab)

def delete_lab(db: Session, lab_id: int):
    lab = db.query(Lab).filter(Lab.id == lab_id).first()
    if not lab:
        raise BusinessException(message="实验室不存在")
    db.delete(lab)
    db.commit()
```

名称不能重复。后面有预约数据后再限制「使用中不能删」。

# 解析
## 提要
对于这一章开篇的那段话的解读

前面 第14 节做完了【用户管理模块（管理员对用户的 增删改查`CRUD`）】，这套实验室接口**完全照搬用户管理那一套写法、一套权限逻辑**，不用学新的结构

```
GET    /api/lab/list     分页列表
POST   /api/lab          新增
PUT    /api/lab/{id}     修改
DELETE /api/lab/{id}     删除
```

✅ 这就是 REST 风格的 4 个基础接口，和用户列表接口一一对应：

1. `GET /api/lab/list`：查询实验室列表，支持分页、关键词模糊搜索（比如搜实验室名字、位置），**查一堆数据**
2. `POST /api/lab`：新增一条实验室记录，往数据库 labs 表里插入一行，新增的时候实验室还没有 id
3. `PUT /api/lab/{id}`：修改**指定这一条**实验室，`{id}`就是数据库里这个实验室的主键编号，用来定位是改哪一个
4. `DELETE /api/lab/{id}`：删除**指定 id**的这条实验室


**1、都用 Depends(get_current_admin)**
👉 权限控制：**这 4 个接口，只有管理员 admin 才能访问，普通学生账号不能调用**

<br>

**2、后面预约、设备都挂在实验室上**

意思是：**实验室是父级资源**

- 以后你再写【预约记录模块】、【实验室内设备模块】的时候
- 预约单、设备表里面，都会存一个 `lab_id` 字段，用来绑定属于哪一间实验室
- 举例子： 
	- 预约记录：`lab_id:1` → 这条预约，预约的是 id=1 的人工智能实验室 
	- 设备：`lab_id:1` → 这个 GPU 电脑，放在 1 号人工智能实验室里 
- 所以**现在先把实验室表字段提前设计好**，它是后面很多功能的基础。

<br>

**3、字段清单（labs 表里面存这些信息）**

- `name`：实验室名称（比如人工智能实验室，要求不能重名）
- `location`：位置（实验楼 A301）
- `capacity`：容纳人数，最多多少学生进来
- `open_time`：开放开始时间（08:00）
- `close_time`：开放结束时间（18:00），不在这个时间段不能预约
- `description`：简介，介绍这个实验室是干嘛的
- `img`：封面图地址，就是你之前写的文件上传接口返回的图片 url
- `status`：状态 1 = 开放，可以预约；0 = 关闭，暂停使用

#### 1. 需求情景 / 使用动机

前面我们写 `User` 模型，是为了存**用户账号信息**，对应数据库 `users` 表； 现在写 `Lab` 模型，是业务上需要单独存储**实验室信息**，需要一张全新独立的 `labs` 数据表

>User 模型 → users 表，管理用户；
>Lab 模型 → labs 表，管理实验室，写法范式完全一样。


写这个 `Lab` 模型，**目的就是告诉 SQLAlchemy：我要在数据库新建一张叫 labs 的表，并且规定好这张表里面有哪些列、每一列是什么类型、能不能为空、默认值是多少**

#### 2.models重要知识点

✅ 模型模板是通用的：User、Lab、以后的预约Booking、设备Device，都是这套写法。

1. 继承 Base → 才会被ORM识别为数据表模型
2. `__tablename__`：数据库真实表名，复数命名习惯 users / labs
3. `Mapped[类型]` 配合 mapped_column 定义列，支持：
    - `nullable=False`：必填
    - `default`：数据库默认值
    - `String(长度)`：限制字符串最大长度
4. 字段完全由业务决定：用户需要账号密码角色；实验室不需要，换成位置、容纳人数、开放时间。

✅ 什么时候新建model： 
出现一类新的、需要持久化到数据库的业务实体（用户、实验室、预约记录）

✅ 区分：
User模型：登录主体，有账号密码role 
Lab模型：资源实体，没有登录能力，只有资源描述信息

✅和 User 模型规则一致：必须导入，`create_all` 才能识别这个模型、自动建 `labs` 表。 
只导入 User，只会生成 users 表；
新增 Lab 模型，一定要追加导入

#### 3. 思维误区 & 对比

❌ 误区：status字段含义全部一样 
对比：字段名一样，但是业务解释跟着实体走，用户的status是账号状态，实验室的status是场地开放状态

❌ 误区：avatar和img是同一个东西 
对比：底层都是存图片url，但是业务归属不一样，分开命名，区分用户头像、实验室封面

## （2）Schema

### Response和Request

**需求情景 / 使用动机**
 Schema 有两大职责：
1. **Request 类（XXCreateRequest / XXUpdateRequest）**：约定前端传给后端的字段、定义入参的基础校验规则，**校验前端发过来的数据**。
2. **Response 类（XXResponse）**：约定后端返回给前端有哪些字段、返回数据的类型；即**规范、过滤后端给前端的数据**
 
**所以拆分三类Schema**：
  - XXXCreateRequest：新增【请求入参】，校验前端新增提交的数据 
  - XXXUpdateRequest：修改【请求入参】，校验前端修改提交的数据
  - XXXResponse：【响应出参】，把数据库查询出来的ORM对象，过滤、整理之后返回给前端 
  
  目的：**入参校验 和 返回输出分开管控**，一套模型不混用，权限、字段可控
   > 这是 FastAPI + Pydantic 项目标准分层写法，user、lab、auth、file 全部统一这个规范

## （3）lab_service

新建 `services/lab_service.py`

**1. 需求情景 / 使用动机**
前面已经建好 Lab 数据表模型、定义好出入参 Schema。
这里是实验室的业务规则：
1. 实现实验室分页列表、模糊搜索`get_lab_page_list`；
2. 新增实验室`create_lab`：保证实验室名称不能重复；
3. 修改实验室`update_lab`：如果改了实验室名称，要校验新名称不能和别的实验室重名（排除自己本身）；
4. 删除实验室`delete_lab`：先判断这条实验室记录是否存在；

`lab_service`的作用：查询、新增、修改、删除的**业务校验 + 数据库读写


**2. 重要知识点**

1. `or_()`：多个查询条件满足任意一个就匹配；对比 `and_()` 需要全部条件满足。
2. `ilike`：忽略大小写模糊匹配；`like` 区分大小写（MySQL下大部分场景差别不大，规范用ilike）。
3. 新增重名校验：直接判断 `name == 传入名称`。
4. 修改重名校验关键点：`Lab.id != lab_id`。 
	>场景：我修改id=2的实验室名称，数据库里id=2本身这条记录名称和新名字一样，不算冲突，要排除。
5. `db.refresh()`：新增、修改后，同步数据库最新数据（自增id、默认字段）。
6. 分页逻辑：先count总数，再偏移+限制条数取当前页数据。

**3. 补充**

### 分页逻辑
对应代码：`get_lab_page_list` 里面分页查询

```python
total = query.count()
items = (
    query.order_by(Lab.id.desc())
    .offset((page - 1) * page_size)
    .limit(page_size)
    .all()
)
```

这里是数据库层面 offset + limit 分页，是正确写法
反面写法（源码里没有，是错误示范）：先 all () 查出全部，再列表切片


 **offset + limit 分页执行流程**
1. 先在数据库里执行 `ORDER BY id DESC` 排序
2. `offset`：跳过前面多少条数据 比如 `page=2，page_size=10` → `offset = (2-1)*10 = 10`，跳过前 10 条
3. `limit`：只取后面 10 条
4. 数据库只返回这 10 条给 Python 后端，不是把整张表数据全部发过来

✅ 优点：
- 数据量大的时候，内存占用很小
- 数据库本身做筛选截取，是标准方案 
> 适用：绝大多数后台列表（用户列表、实验室列表、订单列表）

**total的解读**
经过关键词搜索后，会出现一些数据，这些数据有多少呢，我们使用`total`来统计

`items` 只是拿到**当前这一页**的几条数据
>假如符合搜索条件的有26条数据，total = 26
>则第一页 10 条，第二页10条，第三页6条

>total 是给前端分页组件 `el-pagination` 使用：
>前端拿到 total、page_size，自动算出总页数，渲染页码、“共 xx 条” 文字。
>后端只负责把这个数字返回，**后端不渲染页码 UI**

### 增删改查模板
**CRUD Service 通用模板（ORM + Pydantic）**
> 适用：user / lab / booking / device 这类实体的基础增删改查service

#### 1. 分页列表函数
```python
def get_xxx_page_list(db: Session, page: int, page_size: int, keywords: str | None = None):
    query = db.query(Model)
    # 可选：关键词模糊过滤，不同实体这里字段不一样
    if keywords:
        query = query.filter( or_(...) )
    total = query.count()
    items = query.order_by(Model.id.desc()).offset((page-1)*page_size).limit(page_size).all()
    return PageResponse(
        list = [ResponseSchema.model_validate(item) for item in items],
        total = total
    )
```

#### 2. 新增函数
```python
def create_xxx(db: Session, data: CreateRequest):
    # 【业务差异化点】唯一字段查重（有的实体不需要唯一校验）
    exists = db.query(Model).filter(唯一字段 == 对应值).first()
    if exists:
        raise BusinessException("xx已存在")

    obj = Model(**data.model_dump())
    db.add(obj)
    db.commit()
    db.refresh(obj)
    return ResponseSchema.model_validate(obj)
```

#### 3. 修改函数
（局部更新 exclude_none + setattr）
```python
def update_xxx(db: Session, obj_id: int, data: UpdateRequest):
    obj = db.query(Model).filter(Model.id == obj_id).first()
    if not obj:
        raise BusinessException("数据不存在")

    payload = data.model_dump(exclude_none=True)
    # 【业务差异化点】如果修改唯一字段，需要查重，并且排除自身id
    if "唯一字段" in payload:
        exists = db.query(Model).filter(唯一字段==payload["xxx"], Model.id != obj_id).first()
        if exists:
            raise BusinessException("xx已存在")

    for field, value in payload.items():
        setattr(obj, field, value)
    db.commit()
    db.refresh(obj)
    return ResponseSchema.model_validate(obj)
```

#### 4. 删除函数
```python
def delete_xxx(db: Session, obj_id: int):
    obj = db.query(Model).filter(Model.id == obj_id).first()
    if not obj:
        raise BusinessException("数据不存在")
    db.delete(obj)
    db.commit()
```

**知识点**
1. 骨架固定，变化点只有：模型类、Schema、过滤字段、唯一校验规则
2. exclude_none=True + setattr 是局部更新标准写法
3. db.refresh()：拿到数据库自增、默认值
4. 查重分两种：新增查重、修改查重（修改多一条 id != 自身）

**思维误区**
❌ 误区：每个service都必须全部四个函数
对比：部分业务不需要删除、不需要修改，可以只写部分函数

❌ 误区：所有实体都必须有唯一字段校验
对比：比如设备备注可以重复，就不需要查重逻辑

### 利用 exclude 实现敏感字段写保护
这里补充一下，在`user_service.py`里面，修改：
```python
def update_user_info(db: Session, user: User, data: UserUpdateRequest):
    user_dict = data.model_dump(
        exclude_none=True, exclude={"role", "status"}
    )
```

1、为什么要新增` exclude={"role", "status"}`?
**普通用户修改自己资料的时候，禁止修改角色 role、账号状态 status**

<br>

2、区分两个更新接口：

1. ✅ 管理员接口 `update_user`（PUT `/api/user/{user_id}`）
>没有这个 exclude，管理员有权限修改别人的 role、status
2. ✅ 用户自助接口 `update_user_info`（PUT `/api/user/me`） 
>加上 `exclude={"role", "status"}`，锁死这两个敏感字段，用户无权改动

<br>

3、两个参数解析
1. `exclude_none=True`：只拿前端传了、不为空的字段；没传的字段不更新，实现局部更新
2. `exclude={"role", "status"}`：强制把 role、status 这两个字段直接剔除掉，就算前端偷偷传了这两个参数过来，后端直接无视，不会更新到数据库
