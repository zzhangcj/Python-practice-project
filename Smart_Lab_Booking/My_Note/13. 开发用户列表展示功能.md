```python
from operator import or_
from sqlalchemy.orm import Session
from app.common.response import PageResponse
from app.schemas.user import UserResponse,

def get_user_page_list(
    db: Session, page: int, page_size: int, keywords: str | None = None
):
    # select * from user where username like '%张%' or name like '%张%';
    query = db.query(User)
    if keywords:
        query = query.filter(
            or_(User.username.ilike(f"%{keywords}%"), User.name.ilike(f"%{keywords}%"))
        )
    total = query.count()
    items = (
        query.order_by(User.id.desc())
        .offset((page - 1) * page_size)
        .limit(page_size)
        .all()
    )
    return PageResponse(
        list=[UserResponse.model_validate(item) for item in items], total=total
    )
```

# 本章解析
## 管理员鉴权
在dependecies/auth.py
```python
from app.common.exceptions import BusinessException

def get_current_admin(current_user: User = Depends(get_current_user)) -> User:
    """只有管理员才能访问"""
    if current_user.role != "admin":
        raise BusinessException(message="无权限访问", code=403)
    return current_user
```

用户列表接口使用：`Depends(get_current_admin)`

之前写的get_current_user，目的是**确认这个人是一个有效的登录用户**，即**作用对象是用户**
（详见 06. 开发后端 JWT 用户认证 代码解析第5点）

而这里新增get_current_admin
```python
current_user: User = Depends(get_current_user)
```
✅ 它**依赖于 get_current_user**，会先走一遍原来的 JWT 校验：检查 token 是否存在、是否合法、有没有过期，拿到登录用户信息 
<br>
```python
if current_user.role != "admin":
    raise BusinessException(message="无权限访问", code=403)
return current_user
```
✅ 在登录有效的基础上，再加一层**角色权限判断**：校验当前用户角色是不是 `admin`。
✅ 两层校验合并：**必须登录 + 必须是管理员**，两个条件同时满足，才能放行接口。
<br>
👉 对比总结
- `get_current_user`：鉴权（登录校验），只要是合法登录用户就放行，普通用户、管理员都可以
- `get_current_admin`：权限控制（角色校验），先鉴权，再判断角色，只允许管理员访问

## 1、后端：写 service 业务逻辑
`services/user_service.py` 追加：

```python
from operator import or_
from sqlalchemy.orm import Session
from app.common.response import PageResponse
from app.schemas.user import UserResponse,

def get_user_page_list(
    db: Session, page: int, page_size: int, keywords: str | None = None
):
    # select * from user where username like '%张%' or name like '%张%';
    query = db.query(User)
    if keywords:
        query = query.filter(
            or_(User.username.ilike(f"%{keywords}%"), User.name.ilike(f"%{keywords}%"))
        )
    total = query.count()
    items = (
        query.order_by(User.id.desc())
        .offset((page - 1) * page_size)
        .limit(page_size)
        .all()
    )
    return PageResponse(
        list=[UserResponse.model_validate(item) for item in items], total=total
    )
```

**1、函数入参部分**

```python
def get_user_page_list(
    db: Session, 
    page: int, 
    page_size: int, 
    keywords: str | None = None
):
```

- `db: Session`：数据库会话，相当于拿到数据库的连接，所有查询都靠它
- `page`：**当前第几页**，比如 page=1 是第一页
- `page_size`：**一页展示多少条数据**，比如 page_size=10，一页10个用户
- `keywords: str | None = None`：搜索关键词，不传就是 `None`，代表不搜索、查全部用户
<br>

**2、构建基础查询对象**

```python
query = db.query(User)
```

- 等价 SQL：`SELECT * FROM user`
- ⚠️ 注意：**现在还没有去数据库查！只是把查询条件组装起来**，SQLAlchemy 是惰性查询，调用 `.all()` / `.count()` 才真正发SQL给数据库。
<br>

**3、关键词搜索逻辑**

```python
if keywords:
    query = query.filter(
        or_(User.username.ilike(f"%{keywords}%"), User.name.ilike(f"%{keywords}%"))
    )
```

- `if keywords`：有传搜索词才走过滤；关键词为空，这一段直接跳过，查全部用户
- `or_()`：或者，二选一满足就行（要先 `from operator import or_` 导入）
- `ilike`：模糊匹配，**不区分大小写**（like区分大小写）
- `f"%{keywords}%"`：SQL模糊查询语法，`%` 代表任意字符
    - 举例：keywords = "张" → `%张%`，只要用户名或者姓名里面包含“张”就匹配上
- 翻译SQL：`where username like '%张%' OR name like '%张%'`

> 重点：`query = query.filter(...)` 是**给原来的query追加条件**，不是覆盖

<br>

**4、统计总条数**

```python
total = query.count()
```

- 执行SQL：`select count(*) from user where ...`
- 拿到满足条件的**全部用户总数**，前端分页组件需要这个数字（一共有多少条、一共多少页）
<br>

**5、分页 + 排序，拿到当前页数据**

```python
items = (
    query.order_by(User.id.desc())
    .offset((page - 1) * page_size)
    .limit(page_size)
    .all()
)
```

一行一行拆开：

1. `order_by(User.id.desc())`：按id**倒序**，新注册的用户排在最前面（id越大越新）
2. `offset((page - 1) * page_size)`：跳过前面多少条
    - 例子：page=2，page_size=10 → (2-1)*10 = 10 → 跳过前10条
3. `limit(page_size)`：最多取几条，这里取10条
4. `.all()`：**真正访问数据库**，把查到的多条用户记录，放到列表 items 里面
<br>

**6、包装分页返回结果**

```python
return PageResponse(
    list=[UserResponse.model_validate(item) for item in items], 
    total=total
)
```

- `[UserResponse.model_validate(item) for item in items]` 列表推导式
    - 循环每一条数据库查出来的 user 对象
    - `model_validate`：把数据库模型 `User` → 转为我们定义的响应Schema `UserResponse`
    - 作用：过滤掉敏感字段！比如密码password，不会返回给前端
- `PageResponse`：我们项目统一的分页返回结构体，固定返回：
    - list：当前页的数据列表
    - total：总数据条数

---

7、**完整执行顺序**

1. 拿到数据库连接 db
2. 先搭基础查询：查User表
3. 如果有搜索关键词，加上 OR 模糊查询条件
4. count 算出符合条件一共有多少条（total）
5. 加上排序、分页偏移、条数限制
6. 去数据库查出当前页的数据 items
7. 循环转换模型，剔除敏感字段，封装成统一分页对象返回

<br>

8、**两个高频坑点**

1. `query` 只是查询构造器，**没调用 .count() / .all() 之前不会查库**
2. `or_` 必须导入，不能直接写 or；SQLAlchemy里面 `or` 和 `or_` 不是一回事


## 2、后端：定义入参 Schema

`common/response.py` 追加：

```python
class PageResponse(BaseModel):
    """分页的返回结果"""

    list: Any = []
    total: int = 0
```

1. `list: Any = []`
- `list`：字段名，存放当前页的数据列表
- `Any`：任意类型，里面可以放用户、实验室、文件等任意实体对象
- `= []`：默认空列表，查不到数据的时候不会报错

<br>

2. `total: int = 0`
- `total`：符合筛选条件的数据总条数（前端分页控件需要，用来算总页数：总条数 / 每页大小）
- `int`：整数类型
- `= 0`：默认 0 条

### 为什么放在 common？

**📌重点：为什么不放 schemas 文件夹，放在 common**

先区分两个文件夹的定位（这个是面试可以直接说的）

`schemas/`：**业务专属模型**，和某个业务强绑定 
举例：`schemas/user.py`、`schemas/lab.py` 里面放：`UserCreate`、`UserResponse`
特点：只给这一个业务模块用，字段是这个业务独有的（用户名、邮箱、设备编号等）


`common/`：**全局通用、跨业务复用的公共组件**
不属于某一个业务 里面放：统一返回体、异常类、常量、工具函数、分页外壳

所以：**放在 common 的理由：**

1、**PageResponse 不绑定任何业务** 
它里面只有 `list` 和 `total` 两个字段，查用户能用、查实验室能用、查预约记录也能用。 不属于用户模块，也不属于实验室模块，不属于任何单一业务，所以不属于 schemas

2、schemas 存放的是**实体内容模型**，而`PageResponse`是外层包装壳
举个例子：
- `UserResponse`（schemas/user.py）：规定**一条用户长什么样**（id、username、avatar…）
- `PageResponse`（common/response.py）：规定**一堆数据分页后外层怎么打包**，里面装什么东西它不关心

你这个项目里 `common/response.py` 一般还会放基础的 `Response`（code、message、data）全局返回模板
`Response`和`PageResponse`才是一类的，都是一种通用返回结构，所以都应该放在`common`里面，统一维护，风格一致

<br>

**一句话总结：**
`schemas` 放各个业务自己的入参、响应模型，和业务强耦合； 
PageResponse 只是通用分页外壳，只有 list 和 total，所有业务列表接口都可以复用，不属于某一个业务，属于项目公共基础设施，所以放在 common，和统一返回响应放在一起

`api/user.py` 追加：


### 后端的路由接口再理解

路由接口（api 层，也叫 控制器 / 接口层）定位：**只做「接收、校验、鉴权、转发、包装返回」，不写复杂业务逻辑**

1. 接收前端 GET 请求 `/api/user/list`
2. FastAPI 自动接收 url 查询参数：`page`、`page_size`、`keywords`，并且自动做**基础类型校验**（比如：page 必须是数字）

3. 执行 `Depends` 依赖：
    - `Depends(get_current_admin)`：鉴权 + 角色权限校验（必须是管理员）**
    - `Depends(get_db)`：拿到数据库会话 db
4. **把参数交给 service**：调用 `user_service.get_user_page_list`，真正的查询、分页、搜索逻辑都在 service 里面

> 路由本身不写查询 SQL、不写判断逻辑，只调用 service ✔

5. 拿到 service 返回的 `PageResponse` 对象，套上项目统一的成功返回体 `Response.success()` 返回给前端

## 4、 前端：封装 api 函数

```javascript
/**
 * 分页模糊查询用户列表

export function getUserPageList(params) {

    method: 'get',
    params

```

### 前端的接口再理解

1. `export function` 定义一个可复用的函数，后续页面组件直接调用这个函数，不用重复写 url、请求方式；
2. `url,method`约定请求目标地址 `/api/user/list`、请求方式 GET；
3. `getUserPageList(params)`  接收一个 `params` 对象（包含 `page、page_size、keywords`），axios 自动把它转为 url 后面的查询参数；
4. `return request` 内部交给封装好的 `request`（axios 实例）发网络请求，拿到后端返回的数据，给页面组件使用

## 6、 前端：新建页面 Vue

### vue页面模板

**Vue 页面骨架天然按业务类型分成两大类，没有一个万能单骨架同时包揽所有场景。** 后台管理绝大多数页面都逃不开这两类：

1. 【列表页骨架（查询展示）】：对应「查」，承载分页、搜索、表格、操作按钮（编辑、删除）
2. 【表单页骨架（录入提交）】：对应「新增 / 编辑 / 修改密码」，承载表单校验、提交

#### 骨架一：列表页
.vue 页面（**查，User.vue 这类**）

适用：所有数据清单页面，用户列表、预约列表、设备列表

```
【template】
el-card 卡片容器
├─ 卡片标题 header
├─ 搜索区：输入框 + 查询按钮（可选）
├─ el-table 表格，渲染数据行
└─ 底部分页 el-pagination

【script setup】
导入：api请求函数、vue基础API
固定变量：
- params：reactive，存放查询条件 page、pageSize、keywords
- loading：ref，表格加载转圈
- tableData：ref，表格数组数据
- total：ref，数据总条数

固定函数：
1. load()：核心加载函数，调用接口，赋值表格数据；finally关闭loading
2. handleSearch()：搜索事件，先重置页码 page=1，再调用 load()
生命周期：onMounted，页面打开自动执行 load()
附加逻辑（表格操作栏）：
handleEdit()：跳转到【表单页】，带上数据id
handleDelete()：弹窗确认，调用删除api，成功后调用 load() 刷新表格
```

#### 骨架二：表单页
.vue 页面（**新增 / 编辑 / 修改密码**）

适用：新增弹窗页面、编辑页面、修改密码页面

```
【template】
el-card 卡片容器
├─ 卡片标题 header
└─ el-form
    ├─ el-form-item（每一项表单输入，prop必须和form字段对应）
    └─ 提交按钮，绑定 submitting loading 防重复点击

【script setup】
导入：api请求函数、ElMessage
固定变量：
- formRef：ref，表单实例，用来触发表单校验
- submitting：ref，提交loading
- form：reactive，存放表单填写内容
- rules：校验规则对象，支持自定义校验器

固定函数：
handleSubmit()：提交函数
  ① formRef.validate() 执行表单校验，校验失败直接return
  ② 打开 submitting
  ③ try调用提交接口
  ④ 成功提示、跳转回列表页
  ⑤ finally 关闭 submitting
```
